## 1. 目的 / コア体験

### 1.1 このプロジェクトで検証したいこと(MVPの目的)

素案 §9 のとおり、検証対象は「教育ゲームとして成立するか」ではない。

> **「短時間、次々と仕事をこなすことが楽しいか」**

この一点である。したがって MVP の全設計判断は、次の基準で行う。

- **テンポを削る要素は入れない**(長いローディング、確認ダイアログ、結果画面での長い待ち)
- **1回の失敗でプレイが終わらない**(検証機会を減らすため。§4.4)
- **「もう一回」が1タップで届く**(§7.4)

### 1.2 コア体験の言語化

| 局面 | プレイヤーの内心 | 設計上の担保 |
|---|---|---|
| 業務提示(0.8秒) | 「お、次は何だ」 | 動詞1語を大きく提示(「よめ!」「とどけろ!」)。この間タイマーは止まっている |
| 理解(0.5〜2秒) | 「なるほど、これか」 | ルール説明不要。画面を見た瞬間に何をするか分かる(**設計原則5**。§4.5) |
| 判断・操作(12秒の中で3問) | 「えーと…こっち! 次!」 | 指の届く画面下半分にだけ操作対象を置く |
| 判定(0.35秒) | 「よし!」/「あー!」 | 即座で短い。**正解は提示しない** |
| 次へ | 「まだ来る!」 | 間を空けない。1ミニゲームは13.15秒だが、**速く3問終えればその時点で次へ移る** |
| 終了時 | **「もう一回やって自己ベスト更新したい」** | 結果画面の主役は「もう一回」ボタン |

### 1.3 コアの「フック」(このゲームが何で人を掴むか)

**「サンタの仕事、想像より事務作業だった」というギャップの面白さ。**

空を飛ぶ・煙突に入るといった華やかな部分ではなく、**手紙を読み、住所を確認し、積載量を合わせ、ラッピングを仕分ける**という
地味な物流業務を、高速でさばく。このギャップ自体がフックであり、ストア説明文・スクリーンショットの訴求軸もここに置く。

- 「サンタになれるゲーム」ではなく **「サンタになったら残業だったゲーム」**
- 教育要素は**結果として身につくもの**であり、**訴求の主軸に置かない**(理由は §2.2)
- 世界観は「サンタ工場は年中稼働している」。ビジュアルはクリスマス一色にする(通年配信の違和感を消す)

## 2. 市場調査と差別化の検証(素案 §13 の妥当性)

素案 §13 の「差別化の中心はサンタ業務 × マイクロゲーム × 学校で学ぶ知識」という方針が成立するかを、
実際のストア状況を調べたうえで評価した。**本節は初版のまま維持する(結論は今も有効)。**

### 2.1 調査で分かったこと

**(a) クリスマス/サンタ系カジュアルゲームは既に多数存在する**
App Store 日本には「サンタクロースのギフト配達ゲーム」「クリスマスサンタギフトシミュレーター」
「Santa Collect Gifts」「サンタのクリスマスパズル」等が並ぶ。ただしその中身は
**そり操作・アイテム収集・マッチ3パズル**が中心で、いずれも「マイクロゲーム連続処理型」ではない。
(出典: App Store 検索結果 / MWM / Google Play)

**(b) モバイルのワリオウェア型は依然として層が薄いが、2026年に状況が動いた**
モバイルのワリオウェア風作品は「Quick Fire」「Dumb Ways to Die」など散発的だったが、
**2026年5月28日に任天堂が『Pictonico!』を iOS/Android でリリース**した。
ユーザーの写真をマイクロゲーム化する基本無料+2ボリューム課金の構成。
(出典: AppleInsider / Wikipedia)

**(c) 国旗・大陸の学習アプリは完全な激戦区**
「世界の国旗と国名を覚えるアプリ」「StudyGe」「GeoExpert」「はんぷく」等が多数あり、
累計1000万DL級のタイトルも存在する。ただし**すべてクイズ形式**であり、
「制限時間内の業務処理」に落とし込んだものは見当たらなかった。
(出典: App Store 各アプリページ / app-liv / AppBank)

### 2.2 所見(プランナーとしての評価)

1. **「サンタ業務 × 高速マイクロゲーム」という組み合わせ自体は空いている。** 素案 §13 の方針は成立しうる。
   単純な色仕分けを中心に据えないという判断も正しい(そこは既存アプリと正面衝突する)。

2. **ただし「学校で学ぶ知識」を訴求の前面に出すのは推奨しない。**
   「地理が学べる」と謳った瞬間、上記(c)の巨大な学習アプリ群と同じ棚で比較される。
   → **訴求は「忙しさの快感」に置き、教育効果は副次的なメリットとして小さく書く。**
   (素案 §7 の「サンタの仕事をしている感覚」という設計思想はそのまま維持する。変えるのは**売り方**だけ。)
   **ディレクター承認済み。**

3. **『Pictonico!』の存在は両面ある。** 追い風はマイクロゲーム型の認知度向上、逆風は受け皿を任天堂が押さえたこと。
   → ストア説明文で **他社タイトル名を引き合いに出さない**(商標・比較表現の問題もある)。
     本作の売りは「1つのテーマ(サンタ業務)で世界観が統一されていること」に置く。

4. **構造的な弱点として「季節性」がある。** クリスマステーマは12月以降にダウンロードが落ちる。
   → 対策として世界観を「サンタ工場は年中稼働」に広げる方針が決定済み(§1.3)。

## 3. ゲームフロー全体像

### 3.1 起動から結果までの流れ

```
[アプリ起動]
   ↓
Boot(初期化・データロード) ※短時間のスプラッシュ
   ↓
Title(タイトル)
   ├─→ Tutorial(あそびかた / チュートリアル) … 初回起動時は自動で1回
   ├─→ Settings(設定) → Credits(クレジット)
   └─→ [しごとをはじめる]
          ↓
       GamePlay(ゲーム本編)
          ├─ Countdown(3・2・1)          ※オーバーレイ
          ├─ ミニゲーム × 6〜7(以上)      ← 1つ最大13.15秒(§4.2)
          ├─ MicroGameIntro(種目の初出時) ※オーバーレイ・タイマー停止中
          └─ Pause(一時停止)              ※オーバーレイ・バックグラウンド復帰時も
          ↓ 90秒終了
       Result(結果)
          ├─→ [もう一回] → GamePlay へ直行(タイトルを経由しない)
          └─→ [タイトルへ] → Title
```

**初版からの変更**: `Overlay_LevelUp`(レベルアップ演出)を**削除**した。レベル制を持たないため(§4.5 原則1)。
初版ではこれが「テンポの区切り」も兼ねていたが、その役割は**ミニゲームの切り替わり自体**が担う。

### 3.2 画面一覧(名前と役割のみ。詳細仕様は次段階で `docs/design/screens/` に作成)

| # | 画面名(Prefab名) | 種別 | 役割 | MVP必須 |
|---|---|---|---|---|
| 1 | `Screen_Boot` | 画面 | 初期化・データロード・ロゴ表示 | 必須 |
| 2 | `Screen_Title` | 画面 | タイトル、開始、ハイスコア表示、各種導線 | 必須 |
| 3 | `Screen_Tutorial` | 画面 | あそびかた / 初回チュートリアル(§4.6) | 必須 |
| 4 | `Screen_GamePlay` | 画面 | HUD + ミニゲーム差し替え領域 | 必須 |
| 5 | `Screen_Result` | 画面 | スコア・ランク・統計・リトライ導線 | 必須 |
| 6 | `Screen_Settings` | 画面 | 音量、リンク行(規約・ポリシー等)、データリセット、**プライバシー設定(UMP再表示)** | 必須 |

**画面数は11**(うち `Screen_Records` は MVP 除外)。初版の `Screen_HowToPlay` は `Screen_Tutorial` に置き換わり、
`Overlay_LevelUp` は削除された。

ミニゲームはそれぞれ独立したPrefabとして `Screen_GamePlay` の差し替え領域に差し込まれる。**4種**。

| # | Prefab名 | 対応ミニゲーム |
|---|---|---|
| M1 | `MicroGame_Letter` | 手紙を読んでしわけろ |
| M2 | `MicroGame_Address` | 住所でしわけろ |
| M3 | `MicroGame_Weight` | 重さでしわけろ |
| M5 | `MicroGame_Wrap` | ラッピングしわけ |

> **M4「プレゼントを数えろ」は不採用**(§5.4)。番号は素案との対応を保つため M5 のまま据え置く。

> **ガイドライン準拠メモ:** 画面1つ = Prefab1つ。シーンは薄く保つ。
> オーバーレイ・ミニゲームもすべてPrefab化し、コードで `new GameObject` して組み立てない。

## 4. コアループの具体化

### 4.1 共通の画面ゾーニング(縦画面・片手操作の前提)

基準解像度は **1080 × 1920** に固定する(ガイドライン §5.7)。
`CanvasScaler.matchWidthOrHeight = 0`(横幅基準)とし、縦は端末に応じて伸びる。

| ゾーン | 高さの目安(1920基準) | 内容 | アンカー既定 |
|---|---|---|---|
| 上部セーフエリア | 約160px | ノッチ / Dynamic Island | 上端 |
| A. HUD | 約220px | のこり時間バー、処理件数、コンボ | `(0.5, 1)` |
| B+C. コンテンツ領域 | 残り全部(目安1284px) | お題 + 操作対象 | **上下ストレッチ** |
| D. バナー予約領域 | 約160px | 広告バナー(非表示時も常に確保) | `(0.5, 0)` |
| 下部セーフエリア | 約96px | ホームインジケータ | 下端 |

**機種差への対応(必須ルール。これを守らないとどれかの機種で必ずバナーとコンテンツが被る)**

1. **下端の予約高さは実行時に計算する。設計値をハードコードしない。**
   「セーフエリア下端の実測値 + バナーの実測高さ」を起動時とセーフエリア変化時に取得して反映する。
2. **コンテンツ領域は上下ストレッチ。** HUDは上端基準、バナー予約とタップ対象は下端基準にアンカーし、
   余った縦幅はすべてコンテンツ領域が吸収する。
3. **バナーは「読み込めたら表示」ではなく「領域は常に確保、中身だけ差し替え」。**
   読み込み成否でレイアウトが動くとタップ位置がずれ、誤タップの原因になる。
4. **バナー予約領域の上に固定の余白(40px程度)を置く。** 計算誤差が出ても直接は接しないようにする。
5. **検証は最小・最大の2端末で行う。**

**タップ対象の共通ルール**

- **タップ対象は必ずコンテンツ領域の下半分に置く。** 親指が自然に届く範囲。
- **最小タップ領域は 160×160px(基準解像度)以上**、隣接要素との間隔は40px以上。
  高速連打の誤タップは「理不尽」として最も強く不満を生むため。
  M2の地図はこの制約が素材の描き方に直結する(§5.2)。

### 4.2 1ミニゲームの構成(全種目共通)

```
[1] 業務提示   0.8秒    動詞1語を大きく表示(「よめ!」等)。※この間タイマーは動かない
                       └ 問題内容(手紙・荷物・箱)は提示中からすでに表示しておく
                         → プレイヤーは読み始められる。読解系のストレスを下げる要
[2] 操作      12秒     タイマーバーが減り始める。**この中で3問正解すればクリア**
[3] 判定演出   0.35秒   ミニゲーム単位の判定
```

**1ミニゲーム = 0.8 + 12 + 0.35 = 13.15秒。** 90秒プレイなら **1プレイあたり約6〜7ミニゲーム**になる。

| # | 決定 | 理由 |
|---|---|---|
| 構造-1 | **1ミニゲーム = 3問。3問正解でクリア** | 1問ごとに種目が切り替わるのではなく、**同じルールを3回続けて処理してから次の種目へ移る**。※M5だけ 3問×3ループ = 最大9問(§5.5) |
| 構造-2 | **基準時間は全種目12秒に統一**(3問ぶん) | 1問あたり約4秒だが**配分は自由**。問題ごとに必要な時間がばらつく種目(M1・M3)の理不尽を消せる |
| 構造-3 | 誤答したとき | **次の問題へ進む。**同じ問題はやり直さない。3問正解するまで問題が供給される |
| 構造-4 | **スコア** | **正解数だけをスコアにする。**3問クリアできなくても正解したぶんは入る |
| 構造-5 | **コンボ** | **誤答したときだけリセット。時間切れは失敗としない(コンボ継続)。**あくまで誤答だけが失敗 |
| 構造-6 | **出題順** | **連続で同じミニゲームが出ないようにし、あとはランダム。**制約はこれ1つだけ |
| 構造-7 | クリアボーナス | **付けない。**3問揃えても追加点はなし。「クリア」は演出上の概念に留める |

**「12秒で3問」が解いた問題**

1. **「1問7秒では読解ゲームとして厳しい」というM1の懸念** — 12秒をまとめて配分できるため、
   易しい問題で稼いだ余裕を難しい問題に回せる。加えて時間切れがコンボを切らないので、読み切れずに終わっても罰がない
2. **「M3の12秒×3回は90秒の44%を占める」という懸念** — 全種目が12秒に揃ったのでM3だけが突出しなくなった
3. **「M5では残時間ボーナスが構造的に発生しない」というプランナーの指摘** — 3問正解した時点で
   次のミニゲームへ移れるため、**速く解くこと自体が報酬になる**。別途ボーナスを用意する必要がない

> **重要な補足(数字の読み方)**
> 「約6〜7ミニゲーム」は、**毎回12秒を使い切った場合の最小値**である。3問を速く終えれば残り時間を待たずに
> 次へ移るため、上手いプレイほどミニゲーム数は増える。仮に平均8秒で3問終える場合、
> 1サイクルは 0.8+8+0.35 = 9.15秒となり、**90秒で約9〜10ミニゲーム**になる。
> スコア上限とサンタランクの閾値(§7.2)は、この幅を踏まえて再計算する必要がある。

### 4.3 正誤の扱い(全種目共通)

| 結果 | 次にどうなるか | スコア | コンボ |
|---|---|---|---|
| 正解 | 次の問題へ。3問目なら**クリアして次の種目へ** | 加算 | +1 |
| **誤答** | **次の問題へ進む**(同じ問題はやり直さない) | なし | **リセット** |
| 時間切れ(未回答) | ミニゲーム終了 | なし | **継続**(維持) |

**「あくまで誤答だけが失敗」という設計が生むもの**

- **「分からないから飛ばす」が戦略として成立する。** 当てずっぽうで外すほうが損になるので、慎重さが報われる
- 下手な人でも**コンボが理不尽に切れない**。切れるのは自分が間違えたときだけ
- **「クリアできなかった」ことのペナルティが実質ない。** 正解した数だけが積み上がる

### 4.4 失敗ペナルティ

**コンボリセットのみ。時間ロスなし・強制終了なし。**

| 事象 | ペナルティ |
|---|---|
| 誤答 | **コンボリセットのみ**。時間は減らない |
| 時間切れ | **なし**(コンボも継続) |
| 累積ミスによる強制終了 | **なし** |

> **プランナーの推奨と異なる決定。** プランナーは「残り時間 −3秒 + コンボリセット」を推奨したが、
> ディレクター判断で**時間ロスは採用しなかった**。結果として、1プレイ時間が完全に一定になり、
> 「90秒で遊べる」という商品説明が厳密に守られる。上級者との差はコンボ倍率とミニゲーム消化数でつく。

### 4.5 難易度設計 —— レベル制を持たない

**初版の設計(経過時間ベースで Lv1〜5 に上昇し、制限時間が基準値から短縮される)は全面撤回した。**

| # | 原則 | 内容 |
|---|---|---|
| 原則1 | **レベル制を持たない** | 難易度をシステムで段階制御しない。**レベル選択の仕組みも作らない。**問題プールからランダムに引くだけで、易しい問題と難しい問題が交互に来る「当たり外れ」が緩急になる。**制限時間はプレイ中に短縮しない** |
| 原則2 | **視線の着地点を不変にする** | 選択肢の位置・サイズ・**数**を問題ごとに変えない。原則1により増減がなくなったので、この原則はより単純に守れる |
| 原則3 | **理不尽の線引き** | 「もう一度見れば分かる」は良い難しさ。**「見ても一意に決まらない」は理不尽。**ただし**「知らないものに出会う」ことは学びとして許容する** |
| 原則4 | **文字表記**(日本語版) | 教育漢字1026字まで + **全行分かち書き**。**英語版は別途ルールが必要**(§6.5) |
| 原則5 | **説明がいらないほど単純なルールにする** | **種目ごとのチュートリアルを作らなくて済む水準を目指す。**説明が必要になった時点で、そのルールは複雑すぎると考える。判断に迷ったら**ルールを削るほうへ倒す** |

**原則5は素案に立ち返るもの。** 素案 §4 は「ゲーム開始直後にプレイヤーが**何をすればいいか分かる**こと。
複雑なルール説明を必要とするミニゲームは避ける」としていた。初版の設計原則は4つだったが、
**種目ごとの遊べるチュートリアルを作らないという決定に伴い、原則5を追加した。**

**原則5に照らした4種の点検**

| 種目 | 初見で分かるか | 説明が要りそうな点 |
|---|---|---|
| M2 住所 | **分かる** | ほぼなし。**4種で最も原則5を満たしている** |
| M1 手紙 | **分かる** | 型A・B・Cでルールは変わらない(常に「読んで4択から1つ」)ので、型が増えても説明は増えない |
| M5 ラッピング | おおむね分かる | **スキップ口の使い方**。「下の広い口へ入れる」という対応づけが初見で分かるかは要検証 |
| M3 重さ | **最も説明を要する** | ①合計を目標値**ちょうど**にする ②**複数選べる** ③**取り消せる** ④オーバーしても続けられる。積載メーターが①を視覚化するが、**②③は絵で伝わりにくい** |

**M3が原則5から最も遠い。** ただし**複数選択はM3の中核**(合計を作る遊び)なので削れないため、**演出で伝えるのが現実的**。
打ち手の候補: 選んだ箱を持ち上げて「まだ確定していない」と見せる / メーターが目標値を超えたら赤くあふれさせ
「戻せる」と気づかせる / 初出カードに「もういちど おすと もどる」の1行だけ添える。

### 4.6 チュートリアルと初出カード

| いつ | 形式 | 何を伝えるか |
|---|---|---|
| チュートリアル(**初回起動時**) | **実装する** | **ゲーム全体のルール。**90秒であること、3問正解でクリアすること、コンボ、誤答だけが失敗であること |
| 初出カード(その種目が初めて出たとき) | **静的なカード1枚** | **その種目のルールだけ。**タイマー停止中に出すのでテンポを損なわない |
| 種目ごとの遊べるチュートリアル | **作らない** | 工数がかかりすぎるため(ディレクター判断)。代わりに**設計原則5**を全種目に適用する |

**両方を残す理由**: チュートリアルはゲーム全体のルール、初出カードはその種目のルールを扱う。
**守備範囲が違うので重複ではない。** ゲーム全体のルール(90秒・3問クリア・コンボ・誤答だけが失敗)は
種目を見ているだけでは分からないため、初回チュートリアルは必須。

**M2はチュートリアルに入れる種目の第一候補**(ルールがタップ1回で完結し、最も説明しやすいため)。
なお「1問目を必ずM2にする」という掴み役の設計は**不採用**(プランナー提案。ディレクター判断で却下)。

## 5. ミニゲーム4種の仕様

**MVPは M1・M2・M3・M5 の4種。M4は不採用。**

| 種目 | 業務提示 | 基準時間 | 1問とは | 使う知識 | 操作 |
|---|---|---|---|---|---|
| M1 手紙 | 「よめ!」 | 12秒 | 手紙1通 | 国語・読解 | タップ1回 |
| M2 住所 | 「とどけろ!」 | 12秒 | 荷物1個 | 地理(国→大陸) | 地図の地域をタップ |
| M3 重さ | 「はかれ!」 | 12秒 | そり1台 | 算数(加算・組み合わせ) | 複数タップ・取り消し可 |
| M5 ラッピング | 「しわけろ!」 | 12秒 | 箱1個。**3問×3ループ=最大9問** | 色・形の識別 | シュートをタップ(連続処理) |

**手作りの問題データが必要なのは M1(手紙)と M2(国)の2種だけ。** M3・M5 はプロシージャル生成できる。

> **全種目で共通する、譲れない一線**
> 生成・手作りを問わず、問題の第1条件は**「条件を満たす選択肢がちょうど1つ」= 正解の一意性**。
> 誤答時に正解を見せない以上、**「見ても一意に決まらない」問題が1つでも混ざると、プレイヤーは何が起きたか永久に分からない。**

### 5.1 M1「手紙を読んでしわけろ」

- **業務提示ワード**: 「よめ!」/ **基準時間**: 12秒(3問)/ **操作**: タップ1回で確定・取り消しなし

**画面構成(縦)**

| ゾーン | 内容 |
|---|---|
| B(お題) | 手紙のパネル。**本文のみ**。差出人の顔アイコンと名前は**置かない**(読む要素を増やさないため) |
| C(操作) | **「在庫」2列×2行の4枚固定**。位置・サイズ・枚数は問題によって変えない。**各カードは画像のみ。名前テキストは表示しない** |

> **プランナーの推奨と異なる決定が3点ある。** ①プランナーは「読む間タイマーを停止する2フェーズ制」を推奨したが、
> **ディレクター判断で単一フェーズを採用**。②プランナーは「差出人の名前+顔アイコンを必須」としたが**不採用**。
> ③プランナーは「在庫カードへの名前併記を必須」としたが**不採用**(名前はデータとしては保持してよい。正誤判定・保守・英語版で使う)。
> ②③はいずれも「読む要素を増やさない」という判断。分からないものに出会ったら**それは学びとして扱う**(原則3)。

**文字表記と文字数上限(絶対上限)**

| 項目 | 決定 |
|---|---|
| 行数 | **最大3行** |
| 1行の文字数 | **最大14文字**(全角。分かち書きのスペースを含む) |
| 合計文字数 | **最大35文字** |
| 漢字の範囲 | **小学校で習う漢字(教育漢字1026字)まで** |
| 分かち書き | **全行に一律で適用する。**漢字が入っている行も例外にしない |
| カタカナ | 通常どおり使う(「クレヨン」「ロボット」は全ひらがなより逆に読みやすい) |

**初版からの変更**: 初版の「3行 × 全角15文字(最大45文字)」から**10文字ぶん締めた**。
初版の数字は2フェーズ制を前提に置かれたもので、単一フェーズに「読む + 在庫を見る + 選ぶ」を全部収める前提では過大だった。
漢字の範囲を教育漢字まで広げたのは、かなを減らして語の切れ目を視覚的に明確にし、**読速を上げる**ため
(プランナーは全ひらがなを推奨していたが不採用)。

**ディレクターが示した基準の文面** — この分量が「ちょうどよい」:

```
きょうりゅうが 大好きです。
赤い きょうりゅうの
おもちゃが ほしい。
```

**出題文の型カタログ(3型のみ)**

レベル制を持たないため、**問題のレベル差はこの型カタログで作る。**

| 型 | 種類 | 例文 | 4択の例 | 正解 |
|---|---|---|---|---|
| A | 直接指定 | 赤い 車が ほしいです。 | 赤い車 / 青い車 / 赤い電車 / 赤いバス | 赤い車 |
| B | 否定・除外 | くまは もう 持っている。<br>ちがう どうぶつが いい。 | くま / うさぎ / くまの本 / くまのふく | うさぎ |
| C | 大量 | 車の おもちゃと トレカと<br>ゲームと ゲーム機が<br>欲しいです。 | 図かん / くつ / ボール / **ゲーム** | ゲーム |

> **プランナーの推奨と異なる決定。** プランナーは10型(推論・時系列・ひっかけ語など)を提案したが、
> **ディレクター判断で3型に絞った**。型が増えてもルールは変わらない(常に「読んで4択から1つ」)ので、
> 説明が増えないという原則5との相性がよい。

**型C「大量」の絶対条件**: 手紙にほしいものがたくさん書かれるが、**4択のうち該当するのは必ず1つだけ**。
2つ入れると正解が一意でなくなる。
この型の面白さは、**全部を理解する必要はなく拾えばいい**という気づきが起きること。
手紙を頭から丁寧に読むと間に合わず、選択肢側から照合すると速い。**読み方の戦略が生まれる**のがA・Bとの違い。

**理不尽にしないためのルール**

| # | 理不尽パターン | 対策 |
|---|---|---|
| 1 | 正解が知識に依存する | **名前を併記しなくても判断できるイラストにする。**絵の明瞭さで担保する |
| 2 | 正解が複数ありうる | 正解は必ず一意。CSVに「なぜ一意か」を書く列を設け、**全件を人間がレビュー** |
| 3 | 読み落としが避けられない文量 | **3行 / 1行14文字 / 合計35文字を絶対上限とする** |
| 4 | 決定的な条件が最終行にある | 重要条件は前半に置く |
| 5 | 絵で判別できない色差 | 使用色は**明確に違う6色**に限定(赤/青/黄/緑/白/茶)。ただし**赤と緑を同一問題内で同時に使わない**(§8.1) |
| 6 | 文字が読みにくい | 教育漢字1026字まで + **全行分かち書き** |
| 7 | レイアウトが問題ごとに変わる | フォーマットは常に固定 |

**演出**

| 段階 | 内容 |
|---|---|
| ① 選んだ演出 | **正解・不正解で共通。**押下したことが分かる演出だけを出す(押したカードが沈む・光る等)。**この時点では正誤を示さない** |
| ② 判定演出 | **中身は未確定(§12)。**確定している制約: **SEを入れる** / **画面上でも正誤が分かる演出を入れる**(音が出せない環境でも判別できるため) / **正解そのものは提示しない** / 4+として罪悪感を与えすぎない / 0.35秒 |

> **プランナーの推奨と異なる決定。** プランナーは①を正解・不正解で別演出にすることを推奨したが、**共通に統一**。
> タップへの応答(押せたという手応え)と正誤の判定は別のものであり、分けておくと操作の手触りが安定するため。

**「サンタ業務」感の扱い**: プランナーは「M1はクイズの4択そのものに見え、素案 §7 が最も避けたかった
『勉強問題を解かされている感じ』に一番近い」として受注票・出荷演出などの補正案を出したが、
**ディレクター判断で却下**(「クイズに見えることはよいと思う。分かりやすさも大事」)。
採用したのは2点のみ —— **呼称を「候補カード」→「在庫」に変更**、**手紙を実物らしく見せる**(便箋の質感。
具体的なレイアウト・素材はディレクターが用意する)。

**フォント**: **未確定。ディレクターが決める。** プランナーからは「可読性の高い丸ゴシック体を推奨、
手書き風は読速が落ちるので避ける」という意見が出ているが参考に留める。
決定時に確認が必要なのは、**商用利用・アプリ組み込みの許諾**と、**英語版で使う欧文グリフが揃っているか**。

### 5.2 M2「住所でしわけろ」

- **業務提示ワード**: 「とどけろ!」/ **基準時間**: 12秒(3問)/ **操作**: 世界地図の地域をタップ

**画面構成(縦)**

| ゾーン | 内容 |
|---|---|
| B(お題) | **荷物**。プレゼント包装のイラストは毎回同じで、そこに**国旗と国名のラベルが貼り付けられている**。変わるのはラベルだけ |
| C(操作) | **簡略化した世界地図。6地域をタップして仕分ける** |

> **プランナーの推奨と異なる決定。** プランナーは「下部に大陸ボックスを2列×3行」を推奨したが、
> **ディレクター判断で世界地図をタップする方式に変更**。ボックスを並べるより**地理としての手応えが出て、
> 位置を覚える学習が働く**。これに伴い「口の数を何個にするか」という論点自体が消滅した。

**学習をどこで担保するか(プロジェクト全体に効く基準)**

> ディレクターの判断: 「何が正解か分からなければ、**あとで自分で調べられるような内容にすればよい。**
> 国名は調べれば分かるし、今の時代 画像検索もあるからどうとでも調べられる」

ここから2つが決まる。

1. **プランナーの「不正解時にカードを正解の口へ飛ばす」案は不採用。** 学習をゲーム内で担保する必要がなくなり、根拠が消えた。
   **不正解時は押した地域が赤く沈むだけで、荷物は正解の地域へ飛ばさない。**
2. **国名は必ず表示する。** あとで調べられることが要件になった以上、調べる取っかかりを画面に残す必要がある。
   **「国旗のみ表示」で難易度を上げる案は確定的に不採用。**

**地図に描く線**

- **国境線は描かない。** 係争地域の帰属を地図上で表明することになり、特定国での配信停止・削除要求の直接的な原因になりうる
- **州(大陸)の区分線は描く。** 州が当たっていれば正解というルール上、どこからどこまでが1つの州かが見えないと押しようがない。**仕様上の必須要素**
- **地図上に国名は入れない**

区分線が通る場所は6州区分の解釈が割れる場所と一致する(ウラル山脈 / スエズ / パナマ地峡 / インドネシア周辺)が、
**これらにまたがる国はすべて出題から除外している**ため、線の引き方が正誤に影響することはない。教科書の区分に沿って引けば足りる。

**タップの当たり判定**

**各地域の輪郭の内側だけがタップできる。輪郭の外(海・区分線の上)は無反応**(不正解にはしない)。

無反応にする理由: ①外した人は押し直すぶん時間を失うので自然なペナルティになる
②**反応がないこと自体から「輪郭の内側を押すものだ」と伝わり、次に同じミニゲームが来たときの学びになる**。
これは「あとで自分で調べられればよい」という基準とも一貫している。

**地図素材に付く2つの条件(ディレクターが素材を作る前に把握が必要)**

1. **6地域をそれぞれ別の画像として書き出す。** 1枚のフラット画像では地域ごとの当たり判定・色の出し分け・カウンタ表示ができない
2. **小さい地域を実際の面積比より大きくデフォルメする。** 当たり判定が輪郭そのものになるため、
   **輪郭の大きさ = 押しやすさ**。**ヨーロッパとオセアニアが44×44ptを下回るおそれ**がある

**固定色と累積カウンタ**

- 固定色は維持する(アジア=朱、ヨーロッパ=濃青、アフリカ=黄、北アメリカ=緑、南アメリカ=赤紫、オセアニア=空色。詳細は追って整理)
- 色覚多様性への対応として**地域名テキストを地図上に併記**し、色が識別できなくても解けるようにする
- **地図の各地域に処理数を累積表示する。** プレイ終了時、世界地図の上に**「今日どこへ何個届けたか」という業務の証跡**が残る。
  演出時間ゼロで、単発のクイズとの違いを最も強く作る

**大陸区分の典拠**

**日本の小学校社会科(学習指導要領)の6州区分**を採用する。**あそびかた画面への明記はしない**(区分そのものが一般的なため)。

英語版でも問題ない。英語圏の標準は7大陸(6州 + 南極)だが、**南極を出題しない**(子どもがいないのでサンタ業務として
自然に除外できる)ため差が表面化しない。北米と南米を分ける点は日本と英語圏で一致している。
※ラテンアメリカ圏は米州を1つに数えるが、日英配信なら影響しない。スペイン語・ポルトガル語対応時のみ再検討。

**除外する国・地域(承認済み)**

問題データから**削除する**。

| 分類 | 国・地域 | 理由 |
|---|---|---|
| 主権・承認の争い | **台湾** / **パレスチナ・イスラエル** / コソボ、北キプロス、南オセチア、アブハジア、沿ドニエストル、ソマリランド | 削除要求リスク・未承認 |
| 領土問題 | **ロシア、ウクライナ** / 西サハラ | 進行中の領土問題 |
| 国旗の規制 | **北朝鮮** | 国旗表示が一部地域で規制対象になりうる |
| 2州にまたがる | **トルコ、エジプト、カザフスタン** / ジョージア、アルメニア、アゼルバイジャン / **キプロス** | **正解が一意に定まらない → 理不尽** |
| 「国」でない | 香港、マカオ、グリーンランド、英仏等の海外領土 | — |
| 知名度が不安定 | バチカン、モナコ、サンマリノ、リヒテンシュタイン等 | — |
| 保留(実質除外) | ミャンマー / イラン・イラク・シリア・アフガニスタン / 旧ユーゴ諸国 | 情勢・国名表記の議論 |

初版が「難しい」の例に挙げていた**エジプト・トルコも除外対象**。
代わりに **メキシコ・モロッコ・ニュージーランド・パナマ・サウジアラビア** を「紛らわしい国」として使う。

**難易度は設計しない**

> ディレクターの判断: 「国の認知度は人によって違うので、それだけで難易度のばらつきは再現できている」

M2は**レベル制の廃止と最も相性が良い種目**。同じ「フランス」でも知っている人には一瞬、知らない人には難問になる。
**難易度が出題側ではなくプレイヤー側にある。**
プランナーが出したLv1〜4の段階設計(知名度でLv分け・制限時間の短縮)は**すべて不要**。

ただし**出題の重み付けだけは残す** —— オセアニアは除外適用後の候補が少ないため、
オーストラリアとニュージーランドを高頻度で出し、**「オセアニアの地域が一度も使われない」事態を防ぐ**。
これは難易度調整ではなく、地図上のすべての地域が使われることを担保するための措置。

**国旗素材**

**ディレクターが用意する。**外部リポジトリ(flag-icons 等)からの調達は行わない。
**プロトタイプ作成時は画像枠だけを用意する**(実際の画像は後から差し込む)。素材の調達を待たずに実装を進められる。

*素材制作時の確認事項(ディレクター向け)*: 比率を原典どおりに保つ(スイス1:1、ネパール非長方形など。
枠に合わせて引き伸ばさない)/ **国章ありの正式版を使う**(メキシコ・スペイン等。簡略版は不正確または別国の旗になる)/
配色は原典どおり / 表裏でデザインが異なる国(パラグアイ)は表面 / 影・光沢・はためきエフェクトを付けない /
国名表記は外務省表記に準拠(**英語版の国名表記の典拠は別途決める必要がある。§12**)。

### 5.3 M3「重さでしわけろ」

- **業務提示ワード**: 「はかれ!」/ **基準時間**: 12秒(そり3台)/ **操作**: 箱をタップ(複数選択・取り消し可)

**ゲームの性質が初版から変わった。** 「そりに書かれた数値ちょうどになる荷物の組み合わせを探す」というルールになり、
単位換算の教育要素は消えて**組み合わせ探索**が中心になった。

**ルール**

| 項目 | 決定 |
|---|---|
| お題 | そりに**目標の数値**が示される(例: 7) |
| 選択肢 | **数値の書かれた荷物の箱が6個(3列×2行)**。常に6個で、問題によって数を変えない(原則2) |
| 操作 | **複数選択。タップで選び、もう一度タップで取り消せる** |
| 正解 | 選んだ箱の**合計が目標値ちょうど**になったら成立。**確定ボタンは不要**(一致した瞬間に判定) |
| 正解後 | **そりが右へ抜け、左から次のそりが入ってくる。**1回のM3で**そり3台**をさばく |
| **単位** | **なし。数値だけを表示する** |
| 箱の表示 | **箱の絵に数値を直接書き込む**(荷札を貼る方式は不採用。スペース確保のため) |

> **プランナーの推奨と異なる決定。** プランナーは「6秒で複数選択は成立しない(自動判定は誤タップが即失敗で理不尽、
> 確定ボタンは6秒に収まらない)」として単一選択を推奨したが、**ディレクター判断で複数選択を採用**。
> プランナーの懸念は ①**取り消し可にした**(誤タップが即失敗にならない)②**基準時間を6秒→12秒に拡大した**
> の2点で解消されている。プランナーの代案(箱の中身に合計を埋め込む)は不要になったため撤回。

**単位をなくしたことの効果**: 国によって使う単位が違う(kg / ポンド)ため、数値だけの表現にした。
**これは英語版に直接効き、M3は翻訳が実質ゼロになる。** 副次的に初版の「g と kg の混在」という難易度手段は消えたが、
代わりに「組み合わせを探す」という別の面白さが中心になった。

**失敗の扱い**

| 事象 | 扱い | 演出 |
|---|---|---|
| 合計が目標値を超えた | **失敗判定。ただしやり直せる。コンボは切らない** | **トナカイの表情が悲しくなる。**ゲームは止まらない |
| 合計が目標値ちょうど | 成立 | そりが右へ抜け、左から次のそりが入る |
| 12秒で3台さばけなかった | **失敗ではない。**さばけた台数ぶんのスコアが入り、**コンボも継続** | 他種目と同じ判定演出(0.35秒) |

M3は**失敗しても続けられる唯一の種目**になる。そのため「いま失敗した」ことを伝える手段が別途必要で、
それを**トナカイの表情**が担う。画面を止めずに状態だけを伝えられるので、テンポを落とさずに済む。

**オーバーしてもコンボは切らない。** やり直せる以上、他種目の「誤答」とは性質が違うため。
結果として**M3ではコンボが切れる場面が実質なくなる**(積みすぎても戻せて、時間切れも罰されない)。
数値上のペナルティは課さず、トナカイの表情だけが失敗を伝える。
※これが種目間の公平性に与える影響は §12 で扱う。

**難易度は設計しない**

> ディレクターの判断: 「人や、組み合わせの試行の噛み合わなさ次第で解けない場合が生じるため、
> ルールだけで難易度のばらつきは再現できる」

同じ「合計7」でも、最初に選んだ箱がたまたま解に含まれていれば一瞬で終わり、外していれば取り消してやり直す。
**プレイヤーの試行順序という制御できない要素が、そのまま難易度のばらつきになる。**
プランナーが出したLv1〜4の段階設計は**すべて不要**。

**問題の自動生成とバリデーション(2条件のみ)**

| # | バリデーション | 理由 |
|---|---|---|
| 1 | **目標値ちょうどになる組み合わせが、6個の箱の中にちょうど1通りだけ存在する** | **正解の一意性** |
| 2 | **同じ数値の箱が2つ以上存在しない** | 見分けがつかない箱があると混乱する。また解が複数になりやすい |

> プランナーは8条件を挙げていたが、**そのうち6条件は単位・小数に関するもの**だった。
> 単位をなくした時点ですべて不要になった。ディレクターの見立てどおり。

*実装上の注意*: 条件1は組み合わせの数え上げになる。6個の箱に対して部分集合は63通りなので、
全通り試して合計が目標値になるものが1つだけかを確認すれば足りる(計算量は問題にならない)。

**演出**

| 案 | 採否 | 内容 |
|---|---|---|
| 積載メーター | **採用** | 目標値の位置に赤い縦線。**数値が読めなくても「あとどれくらいか」が直感で分かる。**これがあると「計算問題」ではなく「積載判断」に見える |
| そりとトナカイのスライド | **採用(拡張)** | プランナー案の「そりが少し沈む」ではなく、**右へスライドして抜け、左から次が入ってくる** |
| トナカイの表情 | **採用** | 目標値を超えたときに悲しくなる。**演出ではなく仕様**(失敗の唯一の合図) |
| 文言の業務化 | **不採用** | 「つみこみ かんりょう」等は削除。**イラストの移動で正解感が分かるため文言は不要**。物が動くほうが速く伝わり、**言語にも依存しない**(英語版で有利) |

### 5.4 M4「プレゼントを数えろ」—— 不採用

**この種目は作らない。MVPは4種になる。**

**理由**: M4は**「難易度を健全に上げる軸」を構造的にほとんど持たない**。
初版 §5.4 が挙げていた難易度手段はすべて理不尽側に落ちる。

- **複合条件**(「赤くてリボンがない」)は視覚探索を並列から直列に落とし、22個×0.25秒=**5.5秒が探索だけで消える**
- **重なり**は隠れた個体を原理的に数えられない
- **動き**は数えた個体を見失う
- **個数を増やす**のは情報量が増え、時間が線形に伸びる

加えて**計数速度は成人でほぼ生理的な定数**で練習しても速くならないため、上達を実感しにくい種目でもあった。

**他の種目へ引き継ぐこと**

| 引き継ぐ内容 | 引き継ぎ先 |
|---|---|
| 包み紙の模様(水玉/ストライプ/星/無地/チェック) | **M5**。元々M4で色覚対策として導入しM5へ流用する計画だった。**M4がなくてもM5には必要**なのでM5側で用意する |
| プレゼント箱のスプライト | **M5**。M4と共有する前提だったので**M5が単独で用意する** |
| **赤 × 緑を同時に使わない** | **全種目**。妨害色は 赤/青/黄/白/紫 で運用 |
| ジッター付きグリッド配置 | **12月の新種目**。複数オブジェクトを重なりなく散らす必要が出たときに使える |

**4種になったことの影響**

- 90秒で約6〜7ミニゲームの枠に4種 → **各種目が1〜2回**出る計算。5種のときより収まりが良い
- **「毎回違う」感は薄れるリスク**がある。12月アップデートの種目追加で補う
- 「M1とM4を連続させない」という出題順の制約は**不要になった**(静的な種目がM1だけになったため)
- 「数の認識・集計」という教育軸が**MVPから消える**。算数はM3(加算・組み合わせ)が担う

### 5.5 M5「ラッピングしわけ」

- **業務提示ワード**: 「しわけろ!」/ **基準時間**: 12秒 / **構成**: **3問 × 3ループ = 最大9問**
- **操作**: シュートをタップ(連続処理)

ベルトコンベアで流れてくるラッピング済みの箱を、下部の3口へ次々と仕分ける。ゴミが混ざっているのでスキップ口へ。
**4種で唯一「常に手が動く」種目。**

**この種目の固有価値 —— 先読み**

M5は4種の中で唯一「先読み(look-ahead)」というスキルを持てる。ベルトに次の2〜3個が見えているので、
上級者は**いま指を動かしながら、目は次の箱を見て判断を済ませている**。初心者は1個ずつ「見る→決める→押す」を直列に行う。
**練習すれば必ず速くなり、しかも本人がその上達を自覚できる。**
M1(読解速度)・M2(知識の想起)・M3(暗算)はいずれも既存能力の測定に近く、上達を実感しにくい。

**ベルトに次の箱が見えていることは設計上の必須要件。** ここを削るとM5はただの「遅いM2」に堕ちる。

**構成とコンボ**

| 項目 | 決定 |
|---|---|
| 構成 | **3問 × 3ループ = 最大9問**。1問 = 箱1個 |
| **コンボ** | **3問連続で当たったら1コンボ。最大9問正解で3コンボ** |
| 基準時間 | 12秒(他3種と同じ) |

**「1問=箱1個で3問だけ」にすると12秒で3個になり、ベルトがスカスカになってM5の持ち味である先読みが失われる**ところだった。
3ループにしたことで **12秒で9個 = 1個あたり約1.33秒**となり、元の設計(1個約1秒)に近いペースが保たれている。

**コンボの重みが揃う**: 他3種は「3問正解 = 3コンボ」、M5は「9問正解 = 3コンボ」。
**1ミニゲームあたり最大3コンボという上限が全種目で一致する。** M5の1問は個別には速く簡単なので、
3問まとめて1コンボにすることで種目間の重みが釣り合う。
プランナーが懸念していた「M5がコンボの処刑場になる」も、逆の「コンボ農場になる」も**どちらも回避されている**。

**画面構成(縦)**

| ゾーン | 内容 |
|---|---|
| B(お題) | **ベルトコンベアは縦向き(上→下)。**縦画面で長い滑走路が取れ、次の2〜3個が見える |
| B下部 | **判定ゾーン。**ゾーン内で最も下の箱がアクティブ(光る輪郭 + 1.1倍拡大) |
| C(操作) | **シュート3口**(横1列・位置は不変)+ **下部に横長のスキップ口** |

- 各口には**そこへ入る箱の見本を常時表示**する(「A/B/C」のような抽象ラベルは記憶を要求するので使わない)
- **見本は業務提示フェーズ(0.8秒・タイマー停止中)に先に表示しておく。** 口を読むコストをタイマー外に追い出せる。**必須要件**

**シュートとスキップ口**

**赤・青・黄の3択 + 下部に横長のスキップ口。** たまに流れてくる**ゴミ**をスキップ口へ入れる。

> **プランナー案より優れている点。** プランナーは「こわれた箱はどのシュートにも入れず素通しする」を提案していたが、
> **「見逃したのか正解したのか分からない」**という問題があり補う演出が必要だった。
> **スキップ口へ能動的に入れる方式ならこの問題が構造的に消える。**プレイヤーは必ず何かを押すので、
> 押した手応えがそのまま「処理した」という確認になる。**「押さないでおく」という難しい抑制を要求しない**のに、
> ゴミを見分ける判断は残る。

**カテゴリと難易度**

> **【2026-09-13 ディレクター決定・一時停止】形カテゴリの出題はいったんなしにした。**
> 当面は「ゴミ」と「色違いのプレゼント(赤・青・黄)」の仕分けだけで進める。
> コード・データは削除しておらず、プリセット側のフラグで抽選対象から外しているだけなので、
> **必要になれば戻せる**(`23_MicroGame_Wrap.md` §5.3 / 決定ログ.md参照)。以下の記述は
> 形カテゴリが再開された場合のための記録として残す。

| 項目 | 決定 |
|---|---|
| カテゴリ | **色 / 形の2種類**(2026-09-13時点、形は出題を一時停止中) |
| 切り替えの単位 | **1ミニゲーム内で固定。**3問×3ループを通して同じカテゴリ |
| シュートの見本 | カテゴリに応じて中身が変わる。色なら赤・青・黄、形なら3種類の形 |
| **ゴミの個数** | **1ミニゲームに最低1個、最大3個** |

色の判別が速い人と形の判別が速い人がいるため、**どちらのカテゴリを引いたかがそのまま当たり外れになる**(原則1)。
**1ミニゲーム内で固定にしたことで、9問を通して見本が変わらず先読みが最大限に働く。**
ループの境目で見本を読み直す必要がなく、切り替えを伝える演出も不要で実装も軽い。

**ゴミが必ず1個は出ることの効果**: 最低1個が保証されるので「スキップ口を一度も使わずに終わる」ことがない。
最大3個は9問中の3分の1で、これ以上入れると「仕分け」より「ゴミ探し」のゲームになる。

プランナーが提案していた「流速を上げる」「口の数を増やす」「素通しを混入させる」といったレベル連動の難易度設計は
**すべて不要**(レベル制を持たないため)。

**スコアと失敗の扱い**

| 事象 | スコア | コンボ |
|---|---|---|
| 正解(正しい口へ / ゴミをスキップへ) | 加算 | 3問連続で **+1** |
| 誤答(違う口へ / ゴミを口へ / ゴミ以外をスキップへ) | なし | **リセット** |
| **処理しきれずに時間切れ** | さばけたぶんは加算 | **継続(リセットしない)** |

**M3と同じ方針。** これにより、プランナーが警告していた**「M5だけ失敗率が3〜4倍になり、コンボの処刑場になる」問題は完全に解消した。**
取りこぼしは罰されず、間違えたときだけ罰される。
提案されていた**しきい値方式(誤り1個までコンボ維持)は不要になった。**

**演出は2層に分ける**

| 階層 | タイミング | 演出 | 時間 | ゲームは止まるか |
|---|---|---|---|---|
| アイテム単位 | 1個処理するたび | 正: 箱が口へ吸い込まれる / 誤: 箱が灰色になり落下 / ゴミをスキップへ: 専用の反応 | 約0.2秒 | **止めない** |
| ミニゲーム単位 | 9問終了 or 時間切れ | 他3種と同じ判定演出 | 0.35秒 | 止まる |

**「演出0.35秒に揃える」という共通ルールは、ミニゲーム単位の判定にのみ適用する。**
アイテム単位のフィードバックは演出ではなく**操作の応答**であり、これを止めるとベルトの流れが破綻する。
※この切り分けの正式承認は §12 に残る。

*「正解を見せない」ルールとの整合*: アイテム単位で誤りを示すことは「正解を見せる」ことにはならない
(どこへ入れるべきだったかは示さない)。3口なら「残り2つのどちらか」までしか分からず、しかもその箱はもう二度と来ない。

### 5.6 操作の多様性についての所見

| 操作 | 該当 |
|---|---|
| 選択肢タップ | M1 手紙 / M3 重さ(複数選択・取り消し可) |
| 地図の地域タップ | M2 住所 |
| シュートタップ(連続処理) | M5 ラッピング |

**タップ中心で統一する**(ディレクター決定)。学習コストが最小で、誤操作が少なく、
「何をすればいいか分かる」という素案 §4 の要件を満たしやすい。検証したいのはテンポであり、操作の目新しさではない。
テンポの楽しさが確認できた後、12月アップデートの追加種目で多様性を担保する。

追加候補(スコープ外・将来): ドラッグ(そりに荷物を積む)/ 長押し(検品スタンプ)/ 連打(大量注文)/
なぞる(配達ルート)/ 傾け(そりのバランス。実現可能性は**開発チームに確認が必要**)。

## 6. 問題データの設計方針

### 6.1 手作りデータが必要なのは2種類だけ

| ミニゲーム | データ調達方法 | 手作り工数 |
|---|---|---|
| M1 手紙 | **手作り必須**(文面と正解の組) | 大 |
| M2 住所 | **手作り必須**(国 → 大陸の対応表 + 国旗画像) | 中 |
| M3 重さ | **プロシージャル生成**(バリデーション2条件。§5.3) | 小(生成ロジックのみ) |
| M5 ラッピング | **プロシージャル生成** | 小 |

**コンテンツ制作の負荷は M1 と M2 に集中する。** M1の真のボトルネックは素材ではなく**文面の質とレビュー工数**。

### 6.2 プロトタイプのスコープ(最重要)

> **M1・M2は10レパートリー / M3・M5は6レパートリー。**
> **まずは動くこととバランス調整が優先。**問題数を増やすのはその後。

**M1・M2だけ10に増やしてある理由**: この2種は手作りデータで、
「3問正解でクリア」+「誤答したら次の問題へ進む」の組み合わせにより
**1ミニゲーム内でプールを使い切りうる**ため(§12 で解決済み)。
M3・M5はプロシージャル生成なので、6パターンから無限に作れる。

| 種目 | プロトタイプで用意するもの |
|---|---|
| M1 手紙 | **10問**。型A / 型B / 型C を網羅すること(3型それぞれの手応えの違いをプレイテストで確認するため)。**平均20〜23文字**に抑え、毎回35文字にしないこと |
| M2 住所 | **10か国**。ただし**6大陸それぞれから最低1か国ずつ**入れること(全地域が最低1回は使われるようにする。動作確認にも都合がよい)。国旗は**画像枠だけ**を用意し、実素材は後から差し込む |
| M3 重さ | **6レパートリー**(生成プリセット。目標値と箱の数値の組) |
| M5 ラッピング | **6レパートリー**(生成プリセット。色/形の組み合わせ) |

**プールを使い切った場合は先頭に戻って繰り返す**(安全網。10問あれば実際にはほぼ到達しない)。

初版が挙げていた「手紙40問 / 国60か国」は**後回し**。本番向けの量産は10月以降に別途計画する。

> **注意(§12 で扱う論点)**: 誤答すると次の問題が供給される仕様のため、**1ミニゲーム内で最大何問使うかに上限がない**。
> レパートリーが6件しかないプロトタイプでは、1ミニゲーム内でプールを使い切る可能性がある。
> 「1ミニゲーム内での重複を許すか」「プール枯渇時にどうするか」を実装前に決める必要がある。

### 6.3 データ保持方式: CSV をソースに、Editorインポータで ScriptableObject を生成

```
docs/data/letters.csv        ← ディレクターが表計算ソフトで編集
docs/data/countries.csv
        ↓ Tools/データ/問題データをインポート
Assets/Settings/Questions/LetterQuestionTable.asset   (ScriptableObject)
Assets/Settings/Questions/CountryTable.asset
```

**理由**
1. **問題データをディレクター自身が編集・追加できる**ことが、12月アップデートに向けたコンテンツ量産の生命線
2. ランタイムで扱うのは SO なので、**Sprite参照の解決漏れがインポート時点で検出できる**(実行時に画像が出ない事故が起きない)
3. UIガイドライン §5.4 のローカライズ方針(データはScriptableObject/CSVで一元管理)と整合する
4. **CSVに言語カラムを足すだけで日英2言語に対応できる**構造になる

> **インポータの実装上の注意(developer向け)**: 既存アセットを削除して作り直すのではなく、
> **既存アセットの中身を上書き更新**すること(GUIDが変わると参照が切れるため)。

**M1のCSV列(案)**
`id, template_type, lang, line1, line2, line3, correct_item_id, distractor_ids, uniqueness_note, review_status, added_version`

- `uniqueness_note` — 「なぜこの正解が一意か」を書く列。レビューと将来の保守で最重要
- `review_status` — `draft` / `approved`。**approved のみビルドに含める**
- `added_version` — 12月追加ぶんを識別。「あたらしい しごと」バッジにも使える

### 6.4 出題の重複回避

- 1プレイ内で同じ問題を出さない(プールが許す限り)
- 直近プレイで出た問題の出現率を下げる(履歴を PlayerPrefs に保持)
- M2のみ: **誤答した国を、次にM2が出たときに再出題する**。正解を教えなくても「さっきのやつだ」と意識が向き、
  プレイ後に調べる動機になる(時間コストゼロの補助施策)。
  ※1ミニゲームあたり最大3問という制約があるため、同一ミニゲーム内での再出題は現実的でない

### 6.5 ローカライズ —— 日本語 + 英語(初回リリースから)

> **プランナーの推奨と異なる決定。** プランナーは「MVPは日本語のみ」を推奨したが、
> **ディレクター判断で初回リリースから日英両対応**となった。

| 対象 | 扱い |
|---|---|
| UI文言 | `LocalizedText` コンポーネント + キー方式(ガイドライン §5.4)。**最初から ja / en 両方を登録する** |
| 問題データ | CSVに `ja` / `en` 列。**M1のみ「対訳では成立しない」ため別設計が必要** |
| App Store 掲載情報 | **日英両方必要**(スクリーンショット + 説明文) |

**言語対応の負荷はM1に集中する。**

| 種目 | 英語対応で必要なこと | 負荷 |
|---|---|---|
| **M1 手紙** | **翻訳では成立しない。英語版の別設計が必要**(下記) | **大** |
| M2 住所 | **国名の翻訳のみ。**国旗・地図・区分は言語非依存。※英語国名表記の典拠は要決定 | 小 |
| M3 重さ | **単位をなくしたので翻訳ゼロ。**数値と絵だけ。文言の業務化を不採用にしたことも効いている | **なし** |
| M5 ラッピング | **色と形なので言語非依存。**シュートの見本も絵 | ほぼなし |

**M1の英語版で決める必要があること**

| 論点 | 内容 |
|---|---|
| 文字数上限 | 「3行 / 1行14文字 / 合計35文字」は**全角前提の数字で英語には適用できない**。語数か文字数か、1行に何語かを別途決める |
| 読解レベル | 「教育漢字1026字まで」に相当する**英語側の語彙レベル基準**が必要(学年別語彙リスト等) |
| 分かち書き | 英語は元々分かち書きなので、原則4は日本語版固有 |
| 型Cの成立 | 「大量」は**言語によって読む速度が変わる**。日本語で4個並べられる情報量が英語で同じ秒数に収まるとは限らない |
| 問題データ | プロトタイプ6問を**2言語ぶん**。同じ内容の対訳にするのか、言語ごとに別の問題にするのかを決める |

**在庫カードに名前テキストを載せない決定は、英語版にとって有利**(翻訳が不要になる。イラストの明瞭さで両言語をカバーできる)。

## 7. スコア・評価・リプレイ性

### 7.1 スコア計算式

```
1問あたりの得点 = 基本点(100) × コンボ倍率
最終スコア = Σ(1問あたりの得点)
```

| 要素 | 値 | 状態 |
|---|---|---|
| 基本点 | 100 | 維持 |
| コンボ倍率 | 0〜2連=1.0 / 3〜5連=1.2 / 6〜9連=1.5 / 10連〜=2.0(仮値) | 維持 |
| ~~レベル係数~~ | — | **削除**。レベル制を持たないため |
| ~~残時間ボーナス~~ | — | **削除**。速さは「早く終われば次のミニゲームへ移れる」構造で既に報われており、二重に加点しない |

**コンボ倍率テーブルの妥当性**: 1ミニゲームあたり最大3コンボ、1プレイ6〜7ミニゲーム(以上)なので
**理論上の最大コンボは18〜21連(以上)**。「10連〜=2.0倍」はプレイ後半をほぼノーミスで通してようやく届く水準。
ただし「誤答だけが失敗」という設計によりコンボは切れにくいため、**実際には2.0倍に届きやすいかもしれない**。プレイテストで確認する。

各係数は仮値。**ScriptableObject で調整可能にする。**

### 7.2 サンタランク —— 閾値は要再計算(実装前に確定が必要)

| ランク | 到達イメージ |
|---|---|
| 見習いサンタ | 初回プレイ |
| 一人前サンタ | ルールを理解した。**初回〜3回目で到達できることが重要**(達成感の初速) |
| ベテランサンタ | 安定してコンボが繋がる |
| スーパーサンタ | ほぼミスなし |
| サンタマスター | ほぼ完璧 |

ランクの構成は素案 §10 のまま維持する。

> **【要対応】初版の閾値(一人前1,200 / ベテラン2,200 / スーパー3,200 / マスター4,200)は、そのまま使えない。**
>
> これらは**レベル係数と残時間ボーナスが乗る前提の数字**だった。両方を削除したため、
> **現在の式では到達不可能な値になっている。**
>
> 概算: 12秒を使い切る前提なら1プレイ約20問。平均倍率1.5とすると **20 × 100 × 1.5 = 3,000点**が上限に近く、
> **マスター4,200は到達不可能。**
>
> ただしこの概算にも幅がある。①速く解けばミニゲーム数が増えるため問題数は20を大きく超えうる(§4.2の補足)
> ②**M5の1問(箱1個)を他種目の1問と同じ100点として数えるか**が未確定で、
> そのまま数えるとM5は1ミニゲームで最大900点となり、他種目(最大300点)の3倍になる(§12 論点2)。
>
> **したがって閾値は、①M5のスコア重みを決める → ②プレイテストで実測分布を取る、の順で引き直す。**
> ScriptableObjectで後から調整できる形にしておき、仮値で進めるのが現実的。

### 7.3 結果画面に表示する情報

| 項目 | 表示 |
|---|---|
| サンタランク | 最も大きく。称号アイコン + 演出 |
| スコア | カウントアップ演出(**1.2秒以内**。長い演出はリプレイの妨げ) |

| 種目別成績 | **任意。**「地理便 4/5」のような内訳。**4種ぶん** |

### 7.4 リトライ導線(リプレイ性の生命線)

- **結果画面の最下部・最大サイズのボタンが「もう一回」。** 親指の届く位置に配置

## 8. アート / サウンドの方針

### 8.1 アートの方向性

- **フラット&太線のポップなベクター調。** 影・グラデーションは最小限
- **高速で判別できることが最優先。** 短時間で複数の選択肢を見分ける必要があるため、シルエットと色のコントラストを最大化する。装飾より可読性
- 色は**地域色・分類色として意味を持たせる**ため、無闇に使わない(パレットを先に決める)
- **色のみに依存する識別を全種目で禁止する。** 特に**赤 × 緑を同時に使わない**(最も一般的な色覚特性 P型・D型で識別できない)。
  妨害色は **赤/青/黄/白/紫** で運用する
- キャラクター(サンタ・トナカイ)は HUD の隅と結果画面に登場。
  **M3ではトナカイの表情が失敗の合図という機能を持つ**ため、表情差分は演出ではなく**仕様**
- **光過敏性発作(PSE)への配慮**: 毎秒3回を超える点滅を作らない(審査要件ではないが実装ガイドとして明記)

### 8.3 サウンド

| 種別 | 点数 | 内訳 |
|---|---|---|
| BGM | 3 | タイトル / ゲーム中 / 結果 |
| ~~BGM(テンポ違い)~~ | **0** | **不要になった**(下記) |
| SE | 約14 | 正解、不正解、時間切れ、タップ、カード飛翔、コンボ更新、カウントダウン、ランク発表、ハイスコア更新、画面遷移、ボタン、ベルトコンベア、スキップ口、そり |

> **初版からの撤回 —— BGMのテンポは一定にする。**
> 初版は「BGMのテンポがレベルに応じて上がる演出は、忙しさの体感を最も安く高める手段。強く推奨する」としていたが、
> **レベル制を持たないことになったため根拠が消えた。** ディレクター判断でテンポは一定とする。

> **認識しておくべきこと —— 「だんだん忙しくなる」演出手段がすべてなくなった。**
> レベル制廃止でゲーム内容が一定になり、BGMのテンポも一定にしたため、素案 §14 が目指す
> **「めちゃくちゃ忙しいけど楽しい!」は、ミニゲーム自体のテンポだけで作る**ことになる。
> 忙しさの源は3つだけ —— **90秒という短さ / 12秒で3問という密度 / 種目が次々切り替わること**。
> プレイテストで「忙しさが足りない」となった場合の打ち手(制限時間を12秒より短くする / 1プレイを90秒より短くする 等)を
> あらかじめ考えておく。

## 12. 未確定事項(実装・プレイテストと並行して詰める)

**16項目あった初版の論点はほぼ決着した。** 以下が今も未決のもの。
確定版の妨げにはならないが、**論点1〜4は実装着手前に決める必要がある**。

### 論点1【最優先】英語版の設計

10月末リリースに間に合わせる必要があり急務。**負荷はM1に集中する**(M2は国名の翻訳、M3は単位なしで翻訳ゼロ、
M5は色と形なので言語非依存)。決めることは §6.5 の表のとおり。
併せて **①M2の英語国名表記の典拠**(日本語は外務省表記だが英語は別)、**②設定画面に言語切替UIを置くか
(端末言語追従だけでよいか)** も決める必要がある。

### 論点2【最優先】M5の1問をスコア上どう数えるか

「1問 = 基本点100」をM5の箱1個にそのまま適用すると、M5は1ミニゲームで最大900点となり、
他種目(最大300点)の**3倍**になる。同じ13.15秒に対して重みが揃わない。
コンボは「3問で1コンボ」に丸めて揃えたが、**基本点は揃っていない。**

| 案 | 内容 | 影響 |
|---|---|---|
| A. そのまま(箱1個=100点) | M5が最も稼げる種目になる | 出題運がスコアを大きく左右する。ランク閾値も上振れ |
| B. M5の1問を100/3点にする | 種目間の重みが完全に揃う | 端数が出る。HUDの「処理件数」の数え方とも整合を取る必要 |
| C. M5は「3問正解=1件」として100点 | コンボと同じ丸め方で一貫する | 処理件数の表示も自然に揃う |

> **プランナーの推奨: C。** コンボを3問で丸めた理由(1問が個別には速く簡単だから)は
> 基本点にもそのまま当てはまる。HUDの「しょり ◯けん」も種目間で意味が揃う。
> **ただしディレクター判断が必要。** §7.2 のランク閾値はこの決定を待って引き直す。

### 論点3【最優先】サンタランクの閾値

論点2の決定後、**仮値を置いてプレイテストで実測分布を取る。**
「一人前サンタ」に初回〜3回目で到達できることが達成感の初速として重要。ScriptableObjectで調整可能にする。

### 論点4【最優先】1ミニゲーム内の問題供給の上限とプール枯渇時の扱い

誤答すると次の問題が供給される仕様のため、**1ミニゲーム内で何問使うかに上限がない。**
プロトタイプは問題数が少ないため、**1ミニゲーム内でプールを使い切る可能性がある。**

決めること: ①1ミニゲーム内で同じ問題を再出題してよいか ②プールが尽きたらどうするか
(繰り返す / そのミニゲームを打ち切る / 供給問題数に上限を設ける)。
**M2はタップ1回で即判定されるため特に起きやすい**(適当に押せば1〜2秒で1問消費する)。M1・M2を10レパートリーに増やしたのはこのため。

### 論点5 90秒の枠に4種をどう割り当てるか

現在の制約は「連続で同じ種目を出さない」のみ。**全種目を必ず1回は出すのか**、完全ランダムでよいのかが未決。
完全ランダムだと、ある種目が1プレイで一度も出ないことが起こりうる。

### 論点6 バナーをゲームプレイ中にも表示するか

本作は**操作対象が画面下部に集中する**設計であり、その直下にバナーがあると誤タップが起きやすい。

| 選択肢 | 収益 | リスク |
|---|---|---|
| A. 全画面で常時表示 | 最大 | **誤タップ多発 → 無効クリック → 広告アカウント停止。ユーザー体験も最悪** |
| B. **ゲームプレイ中のみ非表示**(タイトル/結果/設定/あそびかたで表示) | 中 | 低。結果画面は毎プレイ必ず通るので表示機会は十分 |
| C. ゲーム中も表示するが、操作エリアとの間に120px以上の緩衝帯 | 中〜大 | 中。緩衝帯のぶん操作エリアが狭くなる |

> **プランナーの推奨: B。** 1プレイ90秒で結果画面に必ず到達するため、リプレイ回転率が高い本作では
> 結果画面のインプレッションだけでも十分な露出が得られる。
> **どの選択肢でも「レイアウト上のバナー予約領域は全画面で常に確保する」**(§4.1)。

### 論点7 M1の判定演出②の中身

「SEを入れる / 画面上でも正誤が分かる演出を入れる / 正解そのものは提示しない / 罪悪感を与えすぎない / 0.35秒」
という制約だけが決まっている。具体案が未着手。**4種すべての判定演出の基準になる。**

### 論点8 チュートリアルの中身

何種目を扱うか / いつ出すか / スキップできるか / いつでも見返せるか / **触る形式か読み物形式か**。

調査結果(参考): メイドインワリオもリズム天国も「読み物だけの説明機能」は持たず、両方とも**遊べる形式**
(ワリオウェアのIndex = 遊び直せる一覧 / リズム天国のPractice = 遊べる練習パート)。
触るチュートリアルへの一本化を後押しする材料。ただし「種目ごとの遊べるチュートリアルは作らない」という決定があるため、
**全体ルールだけを触って覚える形にできるか**が論点になる。

### 論点9 初出カードの表示時間

`Overlay_MicroGameIntro` は「業務提示と同じくタイマー停止中に出す」とされているが、
**業務提示は0.8秒しかなく、カード1枚を読むには足りない。**
初出時のみタイマー停止時間を延長するのか、別のタイミングで出すのかが未定義。

### 論点10 M3にコンボが切れる場面が実質ない件

M3はオーバーしても取り消せてコンボが切れず、時間切れも罰されない。
結果として**M3はコンボが絶対に切れない種目**になり、他3種と失敗リスクが揃っていない。
「M3を引くとコンボ維持が容易」という偏りをそのままにするかは、プレイテストで判断する。

### 論点11 各種目の細部

| 種目 | 未決の内容 |
|---|---|
| M1 | 文面の量産方法(本番実装時)。型AとBはテンプレート化しやすく、**型Cは人が書く必要がある** |
| M2 | 6地域の固定色の具体値 |
| M3 | 目標値と箱の数値の範囲 / 3台の難易度をそろえるか(1台目を易しくするか、3台とも同じプールか) |
| M5 | ベルトの流速と投入間隔(12秒で9個の配分)/ 色と形それぞれの種類数 / **「ゴミ」のビジュアル定義** / **色カテゴリのとき形はどうするか(全部同じ形か)** / フィードバック2層構成の正式承認 |

### 論点12 画面下端の予約領域の実測値

2回の壁打ちで256px / 280pxと割れている。**実行時取得にすれば問題は消える**が、設計時の確保量は決める必要がある。
実機検証が必要(§13 の開発確認 #2)。
