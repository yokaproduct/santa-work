## 1. 目的

新規Unityプロジェクトにおいて、次の2つを**同時に**成立させるための設計方針を定める。

1. **AI(developerエージェント)が画面を高速に作れる** — ディレクターがスクリーンショット(モックアップ)を
   渡せば、そのとおりの画面が短時間で立ち上がる。
2. **ディレクター(コードを書かない人)がUnity Editor上で位置・サイズを手作業で微調整でき、
   その調整が後の作業で消えない** — AI側が別の機能追加をしても、手で動かしたボタンの位置は動かない。

現状の素朴なやり方(=Editor拡張がシーン全体をコードから毎回再生成する)では、1は満たせるが2が壊れる。
本ドキュメントはその構造的な原因を明らかにし、代替となる設計パターンと、それを新規プロジェクトの
立ち上げ時にどう仕込むかを定める。

### 1.1 このガイドラインが守るべき体験(コア体験)

> ディレクターがUnityのSceneビューやInspectorでボタンをドラッグして「ここ」と決めたら、
> **その決定は以後、誰にも(AIにも)勝手に上書きされない。**
> AIは「レイアウトの初期案を出す係」と「ロジックを実装する係」であって、「レイアウトの最終決定者」ではない。

この一文が本ドキュメント全体の判断基準になる。迷ったときはここへ戻ること。

## 2. 事例研究: 何が起きたのか(biseibutsuの実測)

同じ失敗を新規プロジェクトで繰り返さないため、実際のコードを読んで確認した事実を記録する。
(以下はすべて2026-09-05時点の実測値。**このプロジェクトを直すための記述ではない。**)

### 2.1 「シーンを再構築」が実際に行っていること

`Tools > 画面遷移プロトタイプ > シーンを再構築` の実体は、次の1行から始まる。

```csharp
var scene = EditorSceneManager.NewScene(NewSceneSetup.EmptyScene, NewSceneMode.Single);
```

つまり **既存シーンを一切参照せず、空のシーンを新規作成して全部を作り直し、同じパスへ上書き保存する**。

- 既存GameObjectの有無をチェックする処理は**存在しない**(冪等性はゼロ)。
- UI要素はすべて `new GameObject(name, typeof(RectTransform), typeof(Image), ...)` で新規生成され、
  `rect.anchoredPosition` / `rect.sizeDelta` にコード内のハードコード値が直接代入される。
- したがって、**手作業の調整はレイアウトに限らず、シーン上のあらゆる変更が消える**
  (位置・サイズだけでなく、色、フォントサイズ、要素の追加、参照の差し替えも同様)。

これは「レイアウトが上書きされる」という現象の説明であると同時に、
**シーンファイルが『成果物(build artifact)』として扱われている**という設計上の本質を示している。
ソースコードだけが正であり、シーンは毎回捨てて作り直される中間生成物になっていた。

### 2.2 規模(なぜ後から直すのが重い構造なのか)

| 対象 | 規模 |
|---|---|
| `Assets/Editor/Prototype/**` のC#合計 | 約 8,900 行 |
| 中心のシーンビルダー | `ScreenFlowSceneBuilder.cs` 2,112 行 |
| 共通UIヘルパー | `MainSceneContentBuilder.cs` 913 行 |
| 画面別ビルダー | Preparats 988 / Settings 967 / Records 723 / Shop 554 / BottomNavBar 350 / MainScreenEnhancer 332 / Title 90 / Credits 62 行 |
| 生成されるシーン内の名前付きGameObject | 約 2,000 個 |
| プロジェクト内の自作Prefab | **0個**(Prefabは外部SDK同梱のもののみ) |

「レイアウト値がコードのどこに書かれているか」を人間が追う難易度が、行数に比例して上がる。
例えば1つのパネルの高さを決める根拠が、80行を超えるコメント(過去の調整履歴)とともに
コード中に埋め込まれている状態になっていた。**これはコメントの書きすぎではなく、
「本来Inspectorで見れば一目で分かる値」をコードで管理していることの必然的な帰結**である。

### 2.3 コードでUIを組むことで派生していた副作用(見落としやすい)

新規プロジェクトで方式を選ぶ際、レイアウト以外にも次の副作用が付いてくることを知っておく。

1. **実行時生成UIはそもそもInspectorで触れない**
   図鑑セル・保管リスト行・確認ダイアログ等は、Editorではなく**実行時**に
   `new GameObject(...)` で組み立てられている(5ファイル・約38箇所)。
   これらはシーンにもPrefabにも存在しないため、ディレクターは**原理的に一切調整できない**。
   → 新規プロジェクトでは「動的リストの1行」も必ずPrefab化すること(§5.6)。

2. **アセット化されていないSprite/Textureがシーンへ埋め込まれる**
   角丸スプライトは `new Texture2D(...)` + `Sprite.Create(...)` で実行時/エディタ時に生成されている。
   これらはアセットではないため、シーン保存時にシーンファイル内へ**埋め込みオブジェクトとして
   複製保存**される(実測: シーンファイル内にSprite/Texture2Dのオブジェクトが168個)。
   再構築のたびにIDが振り直され、Gitの差分が巨大かつレビュー不能になる。
   → 新規プロジェクトでは、9-sliceの角丸などは**事前にpngアセットとして用意**すること(§5.5)。

3. **参照配線がEditor専用APIに強く依存する**
   コンポーネント間の参照は `new SerializedObject(x).FindProperty("field").objectReferenceValue = y`、
   ボタンのクリックは `UnityEventTools.AddPersistentListener(...)` で焼き込まれている。
   これ自体は正しい手法だが、「配線もレイアウトも全部コード」だと両者が同じ関数の中で混ざり、
   **レイアウトだけを守る**ことができなくなる。
   → 新規プロジェクトでは**所有権を分離**する(§4)。

### 2.4 教訓(新規プロジェクトへ持ち込む結論)

> **シーンとPrefabは「生成物」ではなく「ソース(資産)」である。**
> コードから丸ごと再生成してよいのは、人間が二度と触らないと保証できるものだけ。
> UIレイアウトは、人間が最後まで触り続けるものなので、**絶対に再生成の対象にしてはならない。**

## 3. 方式の比較検討

新規プロジェクトで採り得る方式を4案挙げ、比較する。
評価軸は「ディレクターの調整体験」「AIの実装しやすさ」「初期コスト」「事故りやすさ」「差分レビューのしやすさ」。

### 案A: Prefab-first(画面ごとPrefab化+コードは配線のみ・冪等)

**概要**
- 画面1つ = Prefab1つ(`Screen_Title.prefab` など)。シーンにはそのインスタンスを置くだけ。
- AIの役割は次の2つに限定する。
  1. **初回のみ**、スクリーンショットを元にPrefabを生成する「スキャフォールド(足場)ツール」を実行する。
  2. 以後は、**RectTransformに触れず**、コンポーネントの追加・参照配線・ロジックのみを行う。
- ディレクターはPrefab Modeで自由にドラッグ・数値入力し、Ctrl+Sで保存。以後その値が正。

**長所**
- Unityの標準的なワークフローそのもの。ネットの情報・将来の人員追加とも噛み合う。
- ディレクターの操作が**最も直感的**(Sceneビューでドラッグ、Inspectorで数値入力、その場でGameビュー確認)。
- Prefabは差分が局所化されるため、Gitでも「どの画面をいじったか」が分かりやすい。
- 動的リストの行Prefab化・アセット化など、他の副作用(§2.3)も同時に解決できる。

**短所 / 注意点**
- **Prefabの中からシーン上のオブジェクトを直接参照できない**という制約がある。
  現行のような「ボタンのonClickにシーン上のManagerのメソッドを焼き込む」書き方はPrefabでは不可能。
  → 解決策は確立している(§5.3の `ScreenNavButton` パターン/サービスロケータ/イベント)。
  ただし**プロジェクト初期に決めておかないと後から効く**ため、立ち上げ時の必須項目とする。
- AI側は「毎回全部作り直す」より慎重な作業(既存Prefabへの外科的な追加)を要求される。
  規約(§6)で縛る必要がある。

**初期コスト**: 中(共通ツール・規約の整備に数日程度。ただし新規プロジェクトなら移行コストはゼロ)

---

### 案B: レイアウト値の外部データ化(ScriptableObject / JSON)

**概要**
- 生成コードは従来どおり全部作り直すが、`anchoredPosition` / `sizeDelta` などのレイアウト値だけを
  外部アセット(`UiLayoutOverrides.asset` 等)に切り出す。
- 初回はコードの既定値で生成し、以後は外部データを正として適用。
- 「現在のシーンのレイアウトを外部データへ取り込む」Editorメニューを用意し、
  ディレクターが手調整 → 取り込み → 再構築しても値が保たれるようにする。

**長所**
- 既存の「全部コードで組む」スタイルを大きく変えずに済む(**既存プロジェクトの応急処置としては有効**)。
- 共通ヘルパー1箇所にフックを挿すだけで、画面別ビルダーを改修せずに広く効かせられる。

**短所**
- **「取り込み」を忘れると調整が消える**。ディレクターに手順の記憶を要求する時点で、
  §1.1のコア体験を満たしていない。事故は必ず起きる。
- キーがヒエラルキーパス(例 `Canvas/Screen_Settings/VolumeSlider`)になるため、
  AIが要素をリネーム・階層変更した瞬間に**静かに紐付けが切れる**。
- 「位置は外部データ、色やフォントはコード」という**二重管理**になり、
  ディレクターから見て「Inspectorで変えたのに戻る値/戻らない値」が混在する。最も混乱を生む。
- 動的リストの行など、シーンに存在しないUIは相変わらず調整不能。

**初期コスト**: 小〜中 / **事故りやすさ: 高**

---

### 案C: UI Toolkit(UXML + USS)への全面移行

**概要**
- uGUI(Canvas/RectTransform)をやめ、UI Toolkitで画面を`.uxml`/`.uss`として記述する。
- AIはテキストファイル(UXML/USS)を直接編集でき、ディレクターはUI Builderで視覚的に編集する。

**長所**
- レイアウトが**テキストファイルとして独立**するため、AIの編集とGit差分が非常に扱いやすい。
- CSSライクなスタイル分離により、テーマ変更とレイアウト調整が構造的に分かれる。

**短所**
- **ディレクターの「ドラッグで微調整」体験がuGUIより弱い**。UI Builderは主にフレックスボックス的な
  レイアウト指定であり、「その場でつまんで20px下げる」という操作感はuGUI+Sceneビューに劣る
  (絶対配置も可能だが、UI Toolkitの流儀からは外れる)。
- 3Dシーンとの重ね合わせ・ワールド空間UI・既存のuGUI資産/ノウハウとの相性で追加検証が必要。
  **この点は開発チームに確認が必要**(採用予定のUnityバージョンでのUI Toolkitランタイム機能の
  成熟度、および3D演出との合成方法)。
- チーム全員(AI含む)にとって学習コストが発生する。

**初期コスト**: 大 / **将来性: 高**

---

### 案D: 完全手動(AIはUIを一切生成しない)

**概要**
- 画面はすべて人間がUnity Editor上で手作りし、AIはMonoBehaviourの実装のみ行う。

**長所**: 上書き事故は原理的にゼロ。
**短所**: §1の目的1(スクリーンショットを渡せば画面が立ち上がる)を完全に放棄することになる。
ディレクターの作業負荷が最大化し、AIを使う意味が薄れる。

| 観点 | 案A Prefab-first | 案B 外部データ化 | 案C UI Toolkit | 案D 完全手動 |

| ディレクターの調整体験 | ◎ ドラッグ即反映・保存で確定 | △ 「取り込み」操作が必須 | ○ UI Builderだが操作感は劣る | ◎ |

| 事故りやすさ | 低 | **高** | 低 | 最低 |
| Unity標準プラクティス適合 | ◎ | △ | ○ | ◎ |

## 4. 推奨案と、その理由

### 推奨: **案A(Prefab-first + ワンショット・スキャフォールド)**

理由は次の4点。

1. **§1.1のコア体験を「手順」ではなく「構造」で保証できる唯一の現実的な案。**
   案Bは「取り込みを忘れなければ守られる」に留まる。人間の記憶に依存する仕組みは必ず破れる。
   案Aは、AIがRectTransformを書き換えるコードを実行しない限り、レイアウトは物理的に変化しない。

2. **ディレクターの操作感が最良。** 目的はそもそも「ドラッグして微調整したい」なので、
   uGUI + Prefab Mode(Sceneビューでのドラッグ、Inspectorでの数値入力、Gameビューでの即時確認)が
   最も要求に忠実。

3. **副次的な問題(§2.3)がまとめて解決する。**
   動的リストの行Prefab化、スプライトのアセット化、差分レビュー性が同時に改善する。

4. **新規プロジェクトなら移行コストが存在しない。**
   案Aの主な短所は「既存の大量コードを書き換える負担」だが、立ち上げ時に採用すればそれは発生しない。
   むしろ**最初にやっておかないと後から入れるのが最も高くつく**種類の設計判断である。

### 補足: 案Cを将来採る場合

UI Toolkitは有力だが、「ドラッグで微調整」要求との相性と3D演出との合成方法に不確実性がある。
**新規プロジェクトの立ち上げ時に小さな検証(スパイク)を1〜2日行い、
その結果で案A/案Cを選ぶ**のが安全。検証しない場合は案Aを既定とする。

### 補足: 案Bの限定的な使いどころ

**既に案A以外で走ってしまったプロジェクトの応急処置**としてのみ価値がある。
新規プロジェクトで最初から案Bを選ぶ理由はない。

## 5. 新規プロジェクトへの適用方法(実装ガイドライン)

ここからが本体。新規プロジェクトの立ち上げ時に、そのまま適用できる形で書く。

### 5.1 大原則: 所有権(Ownership)の分離

**すべてのUIの属性について、「コードが正」か「Prefabが正」かを、あらかじめ表で決めておく。**
迷いが生じたらこの表に従い、表にない項目が出たら表を更新してから作業する。

| 属性 | 所有者 | 補足 |
|---|---|---|
| `RectTransform` の anchorMin/Max, pivot, anchoredPosition, sizeDelta, localScale, rotation | **Prefab(人間)** | AIは初回生成時のみ設定してよい。以後**書き換え禁止** |
| ヒエラルキーの並び順(描画順) | **Prefab(人間)** | ただし新規要素の追加位置はAIが決めてよい |
| GameObjectの存在(追加・削除)・名前 | コード/AI(**要相談**) | 削除・リネームは参照を壊すため、必ず事前にディレクター合意 |
| コンポーネントの付与・削除 | コード/AI | |
| `[SerializeField]` の参照配線 | コード/AI | |
| ボタンのonClick等のイベント配線 | コード/AI | §5.3のコンポーネント方式で行う |
| フォント・色・角丸などのテーマ | **UiThemeアセット** | §5.5。個別Prefabに焼き込まない |
| 文字列(表示テキスト) | ローカライズデータ | §5.4。Prefabにはキーだけ持たせる |
| フォントサイズ | **Prefab(人間)** | 見た目の調整なので人間側 |
| 動的に生成される行・セルの見た目 | **行Prefab(人間)** | §5.6 |

> **AIへの一行ルール:**
> 「既存のPrefabに対して、RectTransformの値を書き換えるコードを書いてはならない。
>  位置・サイズの変更が必要だと判断したら、実装せずに取りまとめ役へ報告して指示を仰ぐ。」

### 5.2 フォルダ構成のテンプレート

```
Assets/
  Art/                         … 画像・フォント等の素材
    UI/
      Sprites/                 … 角丸9-slice等、事前に用意したpng(実行時生成しない)
  Prefabs/
    UI/
      Screens/                 … 画面1つ = Prefab1つ
        Screen_Title.prefab
        Screen_Home.prefab
        Screen_Settings.prefab
      Parts/                   … 画面をまたいで使う部品
        Part_PrimaryButton.prefab
        Part_Dialog.prefab
      Rows/                    … 動的リストの1行/1セル(§5.6)
        Row_InventoryItem.prefab
        Cell_EncyclopediaEntry.prefab
  Scenes/
    Main.unity                 … 画面Prefabのインスタンスを並べるだけの薄いシーン
  Settings/
    UiTheme.asset              … 色・フォント・角丸半径などのテーマ(ScriptableObject)
    LocalizationTable.asset    … 文言
  Scripts/
    Runtime/
      UI/                      … MonoBehaviour(*ScreenRefs, *Controller, ScreenNavButton 等)
      Core/
    Editor/
      Scaffold/                … ★一度きりの画面生成ツール置き場(§5.7)
      Tools/                   … 継続的に使う検査ツール(§5.8)
docs/
  design/
    screens/                   … 画面仕様書(plannerが書く。スクショもここに置く)
  reviews/
```

**命名規則**

| 種別 | 規則 | 例 |
|---|---|---|
| 画面Prefab | `Screen_<画面名>.prefab` | `Screen_Settings.prefab` |
| 部品Prefab | `Part_<部品名>.prefab` | `Part_PrimaryButton.prefab` |
| 行/セルPrefab | `Row_<内容>` / `Cell_<内容>` | `Row_InventoryItem.prefab` |
| 参照集約コンポーネント | `<画面名>ScreenRefs` | `SettingsScreenRefs` |
| ロジック | `<画面名>ScreenController` | `SettingsScreenController` |
| Prefab内の要素名 | `<役割><種別>` のパスカルケース | `StartButton` / `TitleText` / `VolumeSlider` |
| スキャフォールド | `Scaffold_<画面名>.cs`(実行後に削除) | `Scaffold_Settings.cs` |

**要素名は「コードとの契約」である。** 一度作った要素のリネームは、参照を壊す可能性があるため
ディレクター合意が必要(§5.1の表)。逆に言えば、**AIはPrefab内の要素を名前(`transform.Find`)で
探してはならない**。必ず`[SerializeField]`参照(§5.3)を使う。名前検索は、リネームで静かに壊れるため。

### 5.3 画面Prefabの標準構造(最重要パターン)

Prefabはシーン上のオブジェクトを直接参照できないため、次の3層に分ける。

```
Screen_Settings (Prefab root)
├─ [SettingsScreenRefs]        … Prefab内の要素への参照だけを持つ(レイアウトは持たない)
├─ [SettingsScreenController]  … ロジック。Refs経由で要素を操作する
├─ Background (Image)
├─ HeaderText (Text)
├─ VolumeSlider (Slider)
└─ BackButton (Button)
   └─ [ScreenNavButton]        … 遷移先をenumで指定。実行時にManagerを解決する
```

**(1) Refsコンポーネント** — 「どの要素がどの役割か」だけを持つ、ロジックのない入れ物。

```csharp
/// 画面Prefab内の要素への参照だけを集約する。ロジックは持たない。
/// レイアウト値(RectTransform)には一切触れないこと。
public class SettingsScreenRefs : MonoBehaviour
{
    [SerializeField] private Slider volumeSlider;
    [SerializeField] private Button  backButton;
    [SerializeField] private Text    headerText;

    public Slider VolumeSlider => volumeSlider;
    public Button BackButton   => backButton;
    public Text   HeaderText   => headerText;
}
```

こうしておくと、AIが後から機能を足すときは
「Refsにフィールドを1つ増やし、Prefabの該当要素をドラッグ配線するワンショットEditorスクリプトを実行する」
という**追加のみの操作**で済み、既存レイアウトに触れずに済む。

**(2) 画面をまたぐ参照はコンポーネント+実行時解決にする** — onClickにシーン上のメソッドを焼き込まない。

```csharp
/// ボタンに付けて、遷移先の画面をInspectorのenumで指定するだけのコンポーネント。
/// Prefab内で完結するため、Prefab単体で保存・編集できる。
///
/// 【注意】ここでは例として静的Instanceでの解決(ScreenFlowManager.Instance)を示しているが、
/// これは確定した方式ではない。実際に採用する解決方式(静的Instance / ServiceLocator / DI /
/// ScriptableObjectイベント等)は、§8-2のとおり新規プロジェクトの開発チームで別途決定すること。
[RequireComponent(typeof(Button))]
public class ScreenNavButton : MonoBehaviour
{
    [SerializeField] private ScreenId target;

    private void Awake()
    {
        // シーン上のManagerは実行時に解決する(Prefabにシーン参照は保存できないため)。
        // ↓ これは一例(静的Instance)。実際の解決方式は§8-2で確定させること。
        GetComponent<Button>().onClick.AddListener(() => ScreenFlowManager.Instance.ShowScreen(target));
    }
}
```

> **この一点を立ち上げ時に決めておくことが、Prefab-firstの成否を分ける。**
> 「シーン上のシングルトンをどう解決するか」(静的Instance / ServiceLocator / ZenjectなどのDI /
> ScriptableObjectイベント)は**開発チームに確認が必要**。どれでもよいが、**1つに統一**すること。

**(3) シーンは薄く保つ** — シーンには「画面Prefabのインスタンス」「常設サービス」「カメラ/ライト」だけを置く。
シーン自体もコードから再生成しない。シーンに要素を足す必要が出たら、それは新しいPrefabにできないか先に検討する。

### 5.4 文言(ローカライズ)

- **日本語の原文をそのままキーに使わない。** 原文を1文字直すたびにキーが切れるため。
- Prefabには `LocalizedText` コンポーネントを付け、Inspectorで**キー**(例 `settings.header`)を指定する。
- 文言データはScriptableObject/CSVで一元管理し、実行時に流し込む。
- **フォントサイズ・折り返し・ボックスサイズはPrefab側(人間の所有)**。
  文言が長い言語であふれる問題は、AIが勝手にサイズを変えるのではなく、ディレクターへ報告する。

### 5.5 テーマ(色・フォント・角丸)

- 色・フォント・角丸半径などは `UiTheme.asset`(ScriptableObject)に集約する。
- 適用は `ThemedImage` / `ThemedText` のような小さなコンポーネントで行い、
  `[ExecuteAlways]` でEditor上でも見た目が反映されるようにする(**要検証**: Prefab Modeでの挙動)。
- **角丸などのスプライトは、必ず事前に`.png`アセットとして用意する。**
  実行時/エディタ時に`new Texture2D`で生成すると、シーン/Prefabへ埋め込み保存されて
  Git差分が壊滅する(§2.3-2)。9-sliceのborder設定はImport Settingsで行う。
- テーマ変更は全画面に一括で効くため、**「テーマの変更」と「個別レイアウトの調整」は別作業**として扱う。

### 5.6 動的に増減するリスト・グリッド

**コードで `new GameObject` して行を組み立てることを禁止する。**

- 1行/1セルは必ず `Row_*.prefab` / `Cell_*.prefab` として用意する。
- 実行時は `Instantiate(rowPrefab, container)` し、Refs経由でテキスト/画像を差し込むだけにする。
- 行の並び(等間隔・折り返し)は `VerticalLayoutGroup` / `GridLayoutGroup` に任せる。
  → **ディレクターは行Prefabを1つ直せば全行に反映される**という、コードでは得られない体験が手に入る。

**LayoutGroupの使いどころ(重要な注意)**
- LayoutGroupの配下に置かれた子は**ドラッグで動かせなくなる**(親が位置を上書きするため)。
  ディレクターが「つまんで動かしたい」と考える要素には**LayoutGroupを使わない**。
- 原則: **可変長の繰り返し(リスト・グリッド)にだけLayoutGroupを使い、
  固定の画面レイアウトは素直な絶対配置(アンカー+anchoredPosition)にする。**

### 5.7 新しい画面を作るときの手順(AI=developer向けテンプレート)

ディレクターがスクリーンショットを送ってきたときの標準フロー。

```
[1] planner   : スクショを読み、画面仕様書を docs/design/screens/<画面名>.md に作成
                (目的・コア体験・要素一覧(役割/状態)・必要な機能一覧・未確定事項)
[2] developer : Assets/Scripts/Editor/Scaffold/Scaffold_<画面名>.cs を書き、1回だけ実行
                → Assets/Prefabs/UI/Screens/Screen_<画面名>.prefab を生成
                → 併せて <画面名>ScreenRefs / <画面名>ScreenController を実装・配線
[3] developer : シーンにPrefabインスタンスを1つ配置し、遷移導線をつなぐ
[4] developer : ★スキャフォールドスクリプトを削除してコミット(二度と実行させないため)
[5] ディレクター: Prefab Modeで位置・サイズ・フォントサイズを微調整して保存
[6] 以降の変更 : developerはRectTransformに触れず、要素の追加・ロジック・配線のみ行う
```

**スキャフォールドの実装規約**

```csharp
// Assets/Scripts/Editor/Scaffold/Scaffold_Settings.cs
// 【一度きりの足場スクリプト】Screen_Settings.prefab を新規生成する。
// 実行後、このファイルは削除してコミットすること(再実行はレイアウトの手調整を破壊する)。
public static class Scaffold_Settings
{
    private const string PrefabPath = "Assets/Prefabs/UI/Screens/Screen_Settings.prefab";

    [MenuItem("Tools/Scaffold/画面Prefabを新規作成/Settings")]
    public static void Create()
    {
        // ★必須ガード: 既に存在する場合は何もしない(手調整の上書きを構造的に防ぐ)
        if (AssetDatabase.LoadAssetAtPath<GameObject>(PrefabPath) != null)
        {
            Debug.LogError($"[Scaffold] 既に存在するため中断しました: {PrefabPath}\n" +
                           "レイアウトの手調整を保護するため、上書き生成は行いません。");
            return;
        }
        // …ここで new GameObject / RectTransform 設定を行い、PrefabUtility.SaveAsPrefabAsset する…
    }
}
```

- **ガード節は例外なく必須。** 「既にあれば何もしない」を全スキャフォールドの先頭に置く。
- メニューパスは `Tools/Scaffold/…` に統一し、**「シーンを再構築」のような、
  広範囲を一括で作り直す名前のメニューを作らない**(誤爆の温床になるため)。

**スクリーンショットからの座標変換の約束事**
- プロジェクト開始時に `CanvasScaler.referenceResolution` を1つ決めて固定する(例 1080x1920)。
- AIはスクショのピクセル座標を、この基準解像度へ線形変換して初期値にする。
- **アンカーの決め方の既定ルール**(手調整と相性がよい形):
  - 画面上部の要素 → アンカー `(0.5, 1)` 基準
  - 画面下部の要素 → アンカー `(0.5, 0)` 基準
  - 全画面背景・パネル → `stretch`
  - 中央の主役要素 → `(0.5, 0.5)`
  こうしておくと、端末の縦横比が変わってもディレクターの調整意図が壊れにくい。
- ノッチ・ホームインジケータ対策(Safe Area)は、**最初の画面を作る前に**方針を決める(§8)。

### 5.8 レイアウト保護のためのツール(任意だが強く推奨)

構造だけに頼らず、事故を検知する仕組みを最小限持っておく。

1. **`Tools/検査/Prefabのレイアウト差分を確認`** —
   直近のコミットと比較して、`.prefab` 内のRectTransform関連プロパティが変更されていないかを一覧表示する。
   → maintainerエージェントのレビュー項目に組み込む(§6)。
2. **バックアップ** — 破壊的操作を伴うEditorツールを実行する前に、対象Prefab/シーンを
   `Backups/<日時>/` へコピーする共通ヘルパーを用意する。
3. **Gitの設定** — プロジェクト作成直後に必ず以下を済ませる。
   - `Edit > Project Settings > Editor > Asset Serialization = Force Text`
   - `Version Control Mode = Visible Meta Files`
   - `UnityYAMLMerge`(Smart Merge)を`.gitattributes`と`.git/config`へ設定
   → Prefab/シーンのマージ競合が現実的に扱えるようになる(§8の未確定事項に関連)。

## 6. コーディング規約・エージェント定義への落とし込み

新規プロジェクトの `CLAUDE.md` と各エージェント定義に、次の文面をそのまま入れることを推奨する。

### 6.1 CLAUDE.md へ追記する文面(案)

```markdown
## UIレイアウトの取り扱い(厳守)

- 画面のUIは、Editor拡張でシーンを再生成する方式ではなく、**画面ごとのPrefab**で管理する。
- **Prefab/シーンは「ソース(資産)」であり、コードから丸ごと再生成してはならない。**
- レイアウト値(RectTransformのanchor/pivot/anchoredPosition/sizeDelta/scale)と
  フォントサイズは**ディレクターの所有物**であり、AIは初回生成時を除いて書き換えない。
- 位置・サイズの変更が必要だと判断した場合は、実装せず取りまとめ役へ報告し、指示を仰ぐ。
- 画面Prefabを新規作成するEditorスクリプト(スキャフォールド)は、
  「既にPrefabが存在する場合は何もせず中断する」ガードを必ず持ち、実行後は削除する。
- 動的に増減するリストの行は、コードで組み立てず必ず行Prefabをインスタンス化する。
- 実行時/エディタ時に生成したTexture2D/Spriteをシーン・Prefabへ割り当てない
  (アセットとして事前に用意する)。
```

### 6.2 developerエージェントへ追記する文面(案)

```markdown
- 既存Prefabを変更する場合は「追加のみ」を原則とする(要素の追加・コンポーネント付与・参照配線)。
- 既存要素のRectTransform・名前・削除に関わる変更は、必ず事前に取りまとめ役の合意を得る。
- Prefab内の要素は transform.Find などの名前検索で取得せず、Refsコンポーネントの
  [SerializeField] 参照を経由する。
- Prefabの編集は PrefabUtility.LoadPrefabContents / SaveAsPrefabAsset を使い、
  対象と変更範囲を明示した一度きりのEditorスクリプトで行い、実行後に削除する。
```

### 6.3 maintainerエージェントへ追記する文面(案)

```markdown
- レビュー時、`.prefab` / `.unity` の差分に RectTransform 関連プロパティ
  (m_AnchorMin / m_AnchorMax / m_AnchoredPosition / m_SizeDelta / m_Pivot / m_LocalScale)の

- シーン・Prefabを一括再生成するEditorメニューが追加されていないかを確認する。

```

## 9. まとめ(1ページ要約)

- 問題の本質は「レイアウト値がコードに書かれている」ことではなく、
  **「シーン/Prefabを、コードから再生成してよい生成物として扱っていた」**こと。
- 新規プロジェクトでは **Prefab-first(案A)** を採用する。
  画面1つ=Prefab1つ、シーンは薄く、AIは**初回生成のみ**行い、以後レイアウトに触れない。
- 成否を分けるのは、立ち上げ時に決めておくべき次の4点。
  1. **所有権の表**(§5.1)をチーム全員(AI含む)で共有する
  2. **シーン依存をPrefabから排除する方式**(§5.3)を1つに統一する
  3. **スキャフォールドは必ず「既にあれば中断」ガード付き・実行後削除**(§5.7)
  4. **動的リスト行・スプライトもアセット化**して、調整不能な領域を作らない(§5.5、§5.6)
- あわせて、**ストア審査・法務要件(仮)**(§7)を実装着手前に仮置きし、
  そこから逆算して必要な画面(クレジット・購入の復元・広告枠・同意UI等)を初期の画面一覧に含める。
