## 1. 目的 / この種目の役割

**子どもからの手紙を読み、条件に合うプレゼントを在庫4枚から1つ選ぶ。4種で唯一「読む」ゲーム。**

- 使う知識: 国語・読解
- 業務提示ワード: **「よめ!」**(`micro.letter.prompt`)
- 操作: **タップ1回で確定・取り消しなし**
- 1件 = 手紙1通(`questionsPerUnit = 1`)

**この種目が抱える既知の弱点**: M1だけ操作密度が極端に低く、大半が「読んでいる=手が止まっている」時間になる。
90秒という短い枠ではこの「止まり」がテンポを壊しうる。
**打たれている対策は3つ** —— ①文字数上限を35文字に締めた ②教育漢字を許して読速を上げた
③12秒を3問で共有できるので1問あたりの時間が固定でない。**加えて時間切れがコンボを切らない**ため、
読み切れずに終わっても罰がない。**これがこの種目にとって最も重要な緩和。**

### 1.1 差し込まれる場所

`Screen_GamePlay` の `MicroGameSlot`(共通仕様 §4)。**単独の画面ではない。**
HUD・12秒バー・業務提示・判定演出は `Screen_GamePlay` 側が持つ。**このPrefabは持たない。**

### 3.1 ★手書きフォントと罫線(2026-09-08 モックアップ反映)

**ディレクター決定: 手紙の本文は手書きフォント。便箋には罫線を入れる。**

> **プランナーは以前「可読性の高い丸ゴシック体を推奨、手書き風は読速が落ちるので避ける」としていた。**
> **ディレクターはこれを承知のうえで手書きフォントを選択した。**
> **ただし懸念自体は有効なので、検証項目として残す(§8-2)。**

**実装上の要件**

| # | 要件 | 理由 |
|---|---|---|
| 1 | **罫線の間隔と `LetterText` の行間(line height)を一致させる** | ずれると文字が罫線にまたがり、**手書きフォントの可読性がさらに落ちる** |
| 2 | **罫線は最大4本**(3行ぶん + 余り1本)。**行数が1〜3行で変わっても罫線の本数は変えない** | 問題ごとにレイアウトが変わらないこと(理不尽パターン#7) |
| 3 | **`LetterText` は上詰め**(1行の問題も2行の問題も、1本目の罫線から始まる) | 視線の着地点を不変にする(設計原則2) |
| 4 | **フォントが教育漢字1026字を欠けなく持つこと** | 欠字は豆腐(□)になる。**手書き系フォントは収録字数が少ないものがある** |
| 5 | **英語版の欧文グリフが揃っていること** | 日英2言語対応のため |
| 6 | **商用利用・アプリ組み込みが許諾されていること** | ライセンス。クレジット画面への記載要否も確認 |

### 3.2 ★「重なった紙」の表現について

モックアップでは便箋が**2枚重なって**描かれている。**これは装飾として扱う。**

> **⚠ 重なりの枚数を「残り問題数」と連動させない。**
> 一見よさそうだが、**M1だけが独自の進捗表示を持つことになり、4種で揃わなくなる。**
> **進捗は共通の `Part_UnitProgressDots`(●●○)が担う**(共通仕様 §6.5)。
> 種目ごとにバラバラの進捗表示を持つのをやめた経緯(M3の `SledProgressText` 廃止)と同じ判断。

**L3の状態**

| 状態 | いつ | 見た目 |
|---|---|---|
| 通常 | 操作フェーズ中 | 既定 |
| **押下** | タップした瞬間 | **正解・不正解で共通。**押したカードが沈む・光る等。**この時点では正誤を示さない** |
| 非活性 | `Begin()` 前 / `Finish()` 後 / ポーズ中 | `Button.interactable = false`。**見た目は変えない**(~~業務提示中に読ませるため~~ ★2026-09-15: `[Play]` 開始で背景が消えた瞬間に見た目が切り替わらないようにするため) |

> **① 選んだ演出を正解・不正解で共通にする**のは確定事項。
> タップへの応答(押せたという手応え)と正誤の判定は別のものであり、分けておくと操作の手触りが安定する。
> **② 判定演出は共通の `Part_JudgeEffect`(中身は保留)が担う。この種目は持たない。**

### 3.3 ★タップ判定(赤い四角枠。2026-09-13 developer対応)

**`StockCard0`〜`3` 自身が持つ `Image`(赤い乗算色)と `Button` が、カード全域(480×290)のタップ判定を持つ。**
子要素(`CardInner` / `CardIconBase` / `DebugLabel`)は `raycastTarget = false` にしてあり、
タップは常に子を素通りしてカード本体の `Button` が受ける。これにより、アイコン画像の上をタップした場合も含め、
**カードの赤い枠の内側ならどこを押しても選択できる**(隙間が無い)。

**在庫アイコンの素材方式**: ~~L4/L5 の2レイヤー着色方式(24形状×2レイヤー=48ファイル)~~ は
**2026-09-13 ディレクター決定で廃止。1アイテム(`item_id`)1枚の完成画像方式に変更した(§5)。**
名前テキストを載せないぶん、**絵の明瞭さで判別できることが必須**であることは変わらない。

## 4. 処理内容(`MicroGameBase` の実装)

### 4.1 `Prepare(MicroGameContext context)`

```
1. context.Definition.questionSource を LetterQuestionTable にキャスト
2. 現在の言語(ja / en)の問題プールを取得
   ※プールはセッション開始時に ShuffledPoolCursor でシャッフル済み(共通仕様 §8.7)
3. 1問目を取り出す
4. LetterText に line1〜line3 を流し込む(空行はスキップ)
5. 在庫4枚を組み立てる
   ・correct_item_id + distractor_ids(3件)= 4件
   ・★4件の並び順をシャッフルする(context.Rng を使う)
   ・各カードに `icon`(完成画像)を設定。**画像が設定されている間は色を乗算しない**(`Image.color = white`)。
     未設定の間は `baseColor` によるプレースホルダ色で塗る(2026-09-13変更。§5)
6. 全カードの Button.interactable = false(まだ押せない)
7. ★この時点で手紙と在庫を配置し終えている。
   ~~業務提示0.8秒の間に読み始められる~~ ★2026-09-15: 業務提示(1.5秒)中は Screen_GamePlay の PromptBackdrop が覆うため、
   読めるのは [Play] 開始から。読む時間はすべて12秒の中に入る(10_Screen_GamePlay.md §12.6)
```

> **【2026-09-07 承認・必須】在庫4枚の並び順を毎回シャッフルする。**
> プロトタイプは10問しかないため、データ順のまま出すと**「この問題は右下」と位置で覚えられてしまい、
> 読解ゲームとして成立しなくなる。** 設計原則2「視線の着地点を不変にする」は
> **枠の位置・サイズ・枚数**についての原則であり、**中身の並びは対象外**。

### 4.2 `Begin()`

```
1. 全カードの Button.interactable = true
2. 入力受付を開始
```

### 4.3 カードをタップしたとき(この種目の中核)

```
1. se_tap を再生し、押下演出(正誤共通)を出す
2. 全カードの interactable を false にする(連打による二重回答を防ぐ)
3. 正誤を判定
   ・正解 → OnUnitCleared を発火
   ・誤答 → OnMissed を発火
4. 成立件数を数える
   ・3件に達した → OnAllUnitsCleared を発火して終了
   ・達していない → 次の手紙を Prepare と同じ手順で用意し、interactable を true に戻す
     ※誤答でも次の手紙へ進む。同じ手紙はやり直さない
```

**次の手紙への切り替えは即座に行う(待ち時間ゼロ)。** テンポを削らない。
**切り替えの演出時間を入れない**(判定演出はミニゲーム単位のみ)。

> **プールの枯渇**: 3件正解するまで手紙が供給され続けるため、**1ミニゲーム内で10問すべてを使い切りうる。**
> `ShuffledPoolCursor` が**末尾に達したら先頭に戻る**(共通仕様 §8.7)ので、供給が止まることはない。

### 4.4 `SetPaused(bool paused)`

```
paused = true  : 全カードの interactable = false。押下演出のアニメーションを止める
paused = false : Begin() 済みなら interactable = true に戻す
```

**M1は自前のタイマー・アニメーションをほとんど持たない**ため、この実装は最も単純になる。

### 4.5 `Finish(MicroGameFinishReason reason)`

```
1. 全カードの interactable = false
2. 進行中の押下演出を即座に完了状態にする
3. ★OnUnitCleared / OnMissed を発火しない(共通仕様 §4.3)
   → 時間切れで読み切れなかった手紙は「無かったこと」になる。失敗ではない
```

### 4.6 `GetSummary()`

```csharp
new MicroGameSummary {
    UnitsCleared     = 正解した手紙の数(0〜3),
    UnitsMissed      = 誤答した手紙の数,
    QuestionsAnswered = UnitsCleared + UnitsMissed,   // M1は問=件なので一致する
}
```

## 6. 出題文の型カタログ(3型のみ。**問題のレベル差はこの型で作る**)

| 型 | 種類 | 性質 |
|---|---|---|
| **A** | 直接指定 | 「赤い車がほしい」。**最も短く易しい。平均文字数を下げる役割を持つ** |
| **B** | 否定・除外 | 「くまはもう持っている。ちがう動物がいい」。**一段の推論が要る** |
| **C** | 大量 | ほしいものが複数書かれるが、**4択のうち該当するのは必ず1つだけ** |

**型Cの絶対条件**: 手紙に書かれたもののうち、**4択に入っているのは1つだけ**。
2つ入れると正解が一意でなくなる。この型の面白さは「全部を理解する必要はなく、拾えばいい」という気づきが
起きること。手紙を頭から丁寧に読むと間に合わず、**選択肢側から照合すると速い**。読み方の戦略が生まれる。

**理不尽にしないためのルール(確定)**

| # | パターン | 対策 |
|---|---|---|
| 1 | 正解が知識に依存する | **名前を併記しなくても判断できるイラストにする** |
| 2 | 正解が複数ありうる | 正解は必ず一意。`uniqueness_note` を書き、**全件を人間がレビュー** |
| 3 | 読み落としが避けられない文量 | **3行 / 1行14文字 / 合計35文字を絶対上限** |
| 4 | 決定的な条件が最終行にある | **重要条件は前半に置く** |
| 5 | 絵で判別できない色差 | 使用色は**明確に違う6色**(赤/青/黄/緑/白/茶)。**赤と緑を同一問題内で同時に使わない** |
| 6 | 文字が読みにくい | 教育漢字1026字まで + **全行分かち書き** |
| 7 | レイアウトが問題ごとに変わる | フォーマットは常に固定 |
