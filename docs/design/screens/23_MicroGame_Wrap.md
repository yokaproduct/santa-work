## 1. 目的 / この種目の役割

**ベルトコンベアで流れてくるラッピング済みの箱を、下部の3口へ次々と仕分ける。ゴミが混ざっているのでスキップ口へ。**

- 使う知識: 色・形の識別
- 業務提示ワード: **「しわけろ!」**(`micro.wrap.prompt`)
- 操作: **シュートをタップ(連続処理)。タップ統一。フリックは使わない**
- **1問 = 箱1個。3問 × 3ループ = 最大9問**
- **1件 = 1ループ(3問)。`questionsPerUnit = 3`**

**4種で唯一「常に手が動く」種目。** そして**4種で唯一「先読み(look-ahead)」というスキルを持てる種目。**
ベルトに次の2〜3個が見えているので、上級者は**いま指を動かしながら、目は次の箱を見て判断を済ませている**。
M1(読解速度)・M2(知識の想起)・M3(暗算)はいずれも既存能力の測定に近く上達を実感しにくいが、
**M5だけが「ゲームとしての上達」を提供する。**

> **ベルトに次の箱が見えていることは設計上の必須要件。ここを削るとM5はただの「遅いM2」に堕ちる。**

### 1.1 差し込まれる場所

`Screen_GamePlay` の `MicroGameSlot`。HUD・12秒バー・業務提示・判定演出は `Screen_GamePlay` 側が持つ。

## 2. ★M5の構造(他3種と唯一違う点)—— 固定グルーピング

> **【2026-09-07 ディレクター決定】1ループ = 固定の3箱。**
> **箱1-3 が第1ループ、箱4-6 が第2ループ、箱7-9 が第3ループ。**
> **3箱すべて正解なら 1件100点 + 1コンボ。誤答が1つでも含まれるループは 0件・コンボなし。**

プランナーは「連続カウント」(正解が3つ続くたびに1件)を推奨したが**不採用**。
採用理由は「3問×3ループ」という元の言葉に忠実で、**プレイヤーにとって構造が分かりやすい**ため。

### 2.1 この決定が生む帰結(**承知のうえで受け入れる。プレイテストで観察する**)

1. **誤答したループの残りの箱も、プレイヤーは処理し続ける必要がある**が、**得点には結びつかない。**
2. **1回の誤答で最大2箱ぶんの「処理はするが点にならない区間」が生まれる。**
3. **8/9問正解でも、誤答の位置によってスコアが変わる。**
   - 箱1で誤答 → ループ1が0件、ループ2・3が成立 → **200点(2件)**
   - 箱9で誤答 → ループ1・2が成立、ループ3が0件 → **200点(2件)**
   - **1個誤ると必ず1件(100点)を失う。**
4. **「全問正解型」ではない。判定はループ単位であって、ミニゲーム単位ではない。**
   9問中3問誤っても、誤りが**1ループに固まっていれば 200点(2件)**が残る。
   逆に**3ループに1つずつ散らばると 0点(0件)**になる。

### 2.2 契約への乗せ方(共通仕様 §4.5)

| | M1 / M2 / M3 | **M5** |
|---|---|---|
| `questionsPerUnit` | 1 | **3** |
| `OnUnitCleared` の発火 | 1問正解するたび | **ループの3箱目を処理し終えた時点で、そのループに誤答が1つも無ければ発火** |
| `OnMissed` の発火 | 1問誤答するたび | **箱1個を誤って処理するたび**(ループごとに最大3回発火しうる) |
| 1ミニゲームの最大件数 | 3件 | **3件** |
| 最大スコア | 300点 | **300点** |
| HUDの件数表示 | 正解数と同じ | **9箱さばいても「3けん」** |

**共通側(`GameSessionController`)にM5用の分岐を1行も書かない。**

### 4.1 アクティブな箱

- **判定ゾーン内で最も下にある箱**がアクティブ。
- アクティブな箱には **光る輪郭 + 1.1倍拡大** が付く。
- **シュートをタップすると、アクティブな箱がその口へ飛ぶ。**
- 判定ゾーンに箱が1つも無いときは、シュートをタップしても**何も起きない**(SEも鳴らさない)。

### 4.2 ベルトの流れ方(★既存文書に定義がなかったため本書で定義する)

> **【2026-09-07 ディレクター決定】ベルトは一定速度で流れる。箱を処理すると、後続の箱が「詰める」
> (前の位置まで加速して移動し、通常速度に戻る)。**

**なぜこの方式か**

| 方式 | 問題点 |
|---|---|
| A. 完全に一定速度(処理しても後続は早く来ない) | **M5だけ早期クリアが構造的に起きない。**常に約12秒かかり、**「速く解けば次のミニゲームへ移れる」という本作の唯一の速度報酬(企画書 §4.2)がM5では機能しない。**M5を引くとセッションのミニゲーム総数が減る |
| B. 完全にステップ式(処理するまで動かない) | ベルトコンベアに見えない。「流れてくる」という圧力が消える |
| **C. 一定速度 + 処理時に詰める(★採用)** | **速く処理すれば早く終わる**ので速度報酬が働く。**先読みも維持される**(常に次の2〜3個が見えている)。見た目もベルトとして自然 |

**この方式により、共通仕様 §14-5 で挙げた「M5だけ早期クリアが起きない」問題が解消する。**

**Cを採ったことの副次的な効果 —— 「見逃し」が原理的に消える**

箱は**処理されない限り前へ進まない**(先頭の箱は判定ゾーンの下端で止まる)。
したがって**箱が判定ゾーンを通り過ぎてしまう「見逃し」は発生しない。**
時間切れになったとき、**未処理の箱はベルト上に残ったまま `Finish()` を迎える**だけである。

> **`OnMissed` は「プレイヤーが明確に誤った選択をしたとき」だけ発火する**(共通仕様 §3.4)。
> 見逃しが存在しない以上、M5で `OnMissed` が発火する経路は**タップによる誤答のみ**に限定される。**実装が単純になる。**

**先頭の箱が止まったときの見せ方**: 判定ゾーンの下端に**物理的な仕切り(ストッパー)**を置き、
「そこで箱が止まる」ことを絵で説明する。**`JudgeLine` がその役割を兼ねる。**

**投入と速度の初期値(仮値。`WrapGeneratorSettings` で調整可能に)**

| 項目 | 初期値 | 根拠 |
|---|---|---|
| 箱の間隔 | 180px | 箱200px + 余白。**次の2〜3個が見える** |
| ベルト速度 | 135 px/秒 | 180px ÷ 1.33秒 = 135。**12秒で9個 = 1個あたり1.33秒** |
| 詰めるときの加速 | 通常速度の3倍 | 一瞬で詰まるとワープに見えるので、動きは見せる |
| **開始時の配置** | **`Prepare()` の時点で、箱1が判定ゾーンの下端に、箱2・3がその上に並んでいる** | **★必須。**空のベルトから流し始めると、最初の箱が判定ゾーンに届くまで約4秒を空費する |

### 4.3 `Prepare(MicroGameContext context)`

```
1. context.Definition.questionSource を WrapGeneratorSettings にキャスト
2. プリセットを1件取り出す(ShuffledPoolCursor。共通仕様 §8.7)
   ・カテゴリ(色 / 形)
   ・シュート3口の見本
   ・9箱のシーケンス(通常箱 or ゴミ)
3. ★シュートの見本(ChuteSampleImage ×3)とスキップ口を先に表示する(必須要件)
   → ~~業務提示フェーズ(0.8秒)に読ませる~~ ★2026-09-15: 業務提示(1.5秒)中は Screen_GamePlay の PromptBackdrop が
     覆うため、プレイヤーが見本を読めるのは [Play] 開始から(10_Screen_GamePlay.md §12.6)。
     それでも Prepare で表示し終えておくのは、[Play] 開始の瞬間に完成した画面を一気に見せるため
4. 箱1〜3を Instantiate して初期配置(箱1が判定ゾーンの下端)
5. LoopProgress を「ループ 1 / 3」、ドットを3つとも「未処理」に
6. 全シュート・スキップ口を非活性
7. ベルトのアニメーションは停止しておく
```

### 4.4 `Begin()`

```
1. 全シュート・スキップ口を活性化
2. ベルトのアニメーションと箱の移動を開始
3. se_belt をループ再生
```

### 4.5 シュート / スキップ口をタップしたとき(★この種目の中核)

```
1. アクティブな箱が無ければ何もしない(SEも鳴らさない)
2. se_tap を再生し、押下演出(正誤共通)を出す
3. 正誤を判定
   ・通常箱 かつ 対応するシュート          → 正解
   ・ゴミ   かつ スキップ口                → 正解
   ・通常箱 かつ 違うシュート              → 誤答
   ・通常箱 かつ スキップ口                → 誤答
   ・ゴミ   かつ どれかのシュート          → 誤答
4. ★アイテム単位のフィードバック(約0.2秒・非ブロッキング。§6)
5. その箱を消し、後続を詰める。次の箱を Instantiate してベルト上端に追加
6. ループ内の位置を進める
   ・誤答だった → OnMissed を即座に発火(コンボリセット)+ このループを「失敗」とマーク
   ・LoopDot を更新
7. ループの3箱目を処理し終えたら
   ・このループに誤答が1つも無い → ★OnUnitCleared を発火
   ・誤答が含まれる               → ★何も発火しない(OnMissed は既に発火済み)
   ・LoopProgress を次のループへ更新、ドットをリセット
8. 3ループ目を終えたら → OnAllUnitsCleared を発火して終了
```

**`LoopDot` の表示**

| 状態 | 見た目 |
|---|---|
| 未処理 | 白い枠 |
| 正解 | 塗りつぶし |
| **誤答** | **灰色の ×** |

> **【2026-09-07 ディレクター決定】ループの失敗を見せる。ループ進行ドット(●●○ 等)で表示する。**
> **理由**: 表示しないと、**8/9正解なのに200点だった理由がプレイヤーに永久に伝わらない**。
> 共通仕様の「正解は提示しない」は**何が正解だったか**を隠すルールであって、
> **自分が誤ったこと自体**を隠すルールではない。
> **承知のうえで受け入れる副作用**: 「このループはもう死んだ」と分かるので、残り2箱を**投げやりに処理する**
> 動機になる。これは §2.1 の帰結2が最も表面化する場面であり、**プレイテストの最重要観察項目**とする。

### 4.6 `SetPaused(bool paused)`

```
paused = true  : ベルトの移動・箱の移動・アイテム単位の演出を止める。全口を非活性
                 se_belt のループ再生を止める
paused = false : Begin() 済みなら再開
```

**M5は自前のアニメーションが最も多い種目**なので、**この実装が4種で最も重要**。
止め漏れがあると、ポーズ中に箱が流れて見逃しになる。

### 4.7 `Finish(MicroGameFinishReason reason)`

```
1. 全口を非活性化
2. ベルト・箱の移動を停止、se_belt を停止
3. 進行中のアイテム単位の演出を即座に完了状態にする
4. ★OnUnitCleared / OnMissed を発火しない
   → 途中までしか処理できなかったループは「無かったこと」になる。失敗ではない
```

> **時間切れで途中までしか流れなかったループは、`OnUnitCleared` も `OnMissed` も発火しない。**
> 共通仕様 §3.4 の「時間切れは失敗としない」がそのまま適用される。

### 4.8 `GetSummary()`

```csharp
new MicroGameSummary {
    UnitsCleared      = 全3箱正解だったループの数(0〜3),
    UnitsMissed       = 誤答を含むループのうち、3箱目まで処理し終えたものの数,
    QuestionsAnswered = 処理した箱の総数(0〜9),   // ★件ではなく問。統計・チューニング用
}
```

> **`QuestionsAnswered` だけが他3種と桁が違う(最大9)。**
> これは**統計・チューニング専用の参考値**であり、スコア・コンボ・HUD件数には一切使わない。
> **結果画面の「◯/◯ 件 成功」には `UnitsCleared` / (`UnitsCleared` + `UnitsMissed`) を使う**(共通仕様 §6.1)。

### 5.1.1 箱の完成画像方式(★2026-09-13変更)

> **変更前**: 白い箱の土台(`Part_WrapBoxItem` の `BoxBackground`)にコードで `WrapSample.color` を乗算し、
> `Pattern` スロットに `patternSprite`(模様)を重ねていた。
>
> **変更後**: ディレクターが**赤・青・緑(★2026-09-16 黄から変更)それぞれの完成した1枚絵**(リボン・影・色覚対策の模様も絵に描き込み済み)を
> `WrapGeneratorSettings` の `redBoxSprite` / `blueBoxSprite` / `greenBoxSprite` に設定する。
> **1か所で3枚設定すれば、それを使う全プリセットの箱・シュート見本の両方に反映される**
> (プリセットごとに同じ画像を何度も割り当てる必要はない)。
>
> - 画像が設定されている色は、`Image.color` を白のまま・`Pattern` を非表示にして絵をそのまま出す
>   (色の乗算も模様の重ね表示もしない)。
> - **シュートの見本にも同じ完成画像を表示する**(箱と見本が同じ絵の方が仕分けが直感的、という考え方を既定案とする)。
> - 画像が未設定の間は、従来どおり `Image.color` を `WrapSample.color` にする + `Pattern` に
>   `patternSprite` を重ねるプレースホルダ表示にフォールバックする(遊べる状態を保つ)。
> - **色覚対策(色と模様はセットで固定対応)という要件は変えていない。** ★2026-09-16: 対応は **赤=ハート柄 / 青=丸柄 / 緑=四角柄**
>   (旧: 赤=水玉/青=ストライプ/黄=チェック)。完成画像方式では、この模様を**絵の中に描き込むこと**で要件を満たす(素材要件は §8 参照)。
> - どのプリセットのどのサンプルがどの完成画像を使うかは、`WrapSample.colorId`(`Red`/`Blue`/`Green`)で
>   指定する。`WrapSample.color` は完成画像が無い間のプレースホルダ表示にのみ使われる(見た目の色そのものは
>   完成画像側が持つため、実質的な「正」は絵の方)。
> - 正解/誤答時のアイテム単位フィードバック(§6)は、引き続き `Background.color` を緑/灰色に変える実装のまま
>   (完成画像の上から乗算される)。**挙動は変えていない**が、完成画像の色味によっては色フラッシュの見え方が
>   プレースホルダ時と変わる可能性がある。0.2秒と短時間のため大きな破綻は無いと判断しているが、
>   **実機での見え方はディレクター確認を推奨する**(§8 未確定事項に追記)。

色カテゴリの3色が **赤・青・緑** になり、シュート3口の見本とベルト上の箱で**赤と緑が同じ画面に並ぶ**。

| 項目 | 内容 |

| **例外とする理由** | ①このルールの目的は「P型・D型の色覚特性の人が**色だけで区別させられない**こと」。**M5は模様(ハート / 丸 / 四角)だけでも正解できる**ため、目的は満たされる ②ディレクターが赤・青・緑で完成画像を描き、模様の描き込みを取りまとめ役が画像で確認したうえで正式に採用した |

| 適用範囲 | **M5の色カテゴリだけ。**M1(赤と緑を同一問題に並べない)など他の種目のルールは変えない |

## 6. 演出は2層に分ける(★共通仕様との切り分け)

| 階層 | タイミング | 演出 | 時間 | ゲームは止まるか | 持ち主 |
|---|---|---|---|---|---|
| **アイテム単位** | 1個処理するたび | 正: 箱が口へ吸い込まれる / 誤: 箱が灰色になり落下 / ゴミをスキップへ: 専用の反応 | **約0.2秒** | **止めない** | **M5の内部** |
| **ミニゲーム単位** | 9問終了 or 時間切れ | **共通の `Part_JudgeEffect`**(中身は保留) | 0.35秒 | 止まる | **`Screen_GamePlay`** |

> **「演出0.35秒に揃える」という共通ルールは、ミニゲーム単位の判定にのみ適用する。**
> アイテム単位のフィードバックは演出ではなく**操作の応答**であり、これを止めるとベルトの流れが破綻する。

**「正解を見せない」ルールとの整合**: アイテム単位で誤りを示すことは「正解を見せる」ことにはならない
(どこへ入れるべきだったかは示さない)。3口なら「残り2つのどちらか」までしか分からず、
**しかもその箱はもう二度と来ない。行動可能な情報は一切漏れない。**

| ゴミをスキップ口へ(正解) | `se_skip` |
| 箱1個が正解 | **`se_item_ok`**(アイテム単位の軽い音)。`se_correct`(件成立の音)とは**別**。2026-09-07 承認 |
| 箱1個が誤答 | `se_wrong` |
| **1ループ成立(件成立)** | `se_correct`(共通側が `OnUnitCleared` で鳴らす) |

> **M5は1.33秒に1回タップされる。** 同一SEの重なりで音割れしないこと(共通仕様 §11.3)。
