## 0. この文書の使い方(最初に読むこと)

### 0.1 レイアウト値の所有権 —— 本書で最も重要なルール

> **本書に書かれている数値(px・秒・サイズ・位置)のうち、レイアウトに属するものは
> 「初回生成時の初期値」であって、確定値ではない。**
> Prefabが一度生成された後は、**それらの値はディレクターの所有物**であり、
> developer(および取りまとめ役・planner)は書き換えてはならない。

ガイドライン §1.1 / §5.1 / CLAUDE.md「UIレイアウトの取り扱い(厳守)」に基づく。判断に迷ったらここへ戻る。

| 区分 | 例 | 所有者 | 本書の数値の意味 |
|---|---|---|---|
| **レイアウト値** | anchor / pivot / anchoredPosition / sizeDelta / scale / フォントサイズ | **ディレクター(Prefab)** | **初回生成時の初期値のみ。以後は参考値** |
| **ゲームバランス値** | 90秒 / 12秒 / **1.5秒**(業務提示。2026-09-15 0.8から変更)/ 0.35秒 / **1.5秒**(終了演出)/ 基本点100 / コンボ倍率 / ランク閾値 | ディレクター(**ScriptableObject**) | **仮値。SOでEditorから変更できること** |
| **演出値**(★2026-09-15 追加) | 業務提示・終了演出のタイムライン秒数・倍率・揺れ幅・`AnimationCurve` | ディレクター(**`PromptEffectSettings` 等のSO**) | **仮値。**レイアウト値ではないので、AIが初期値を入れてよく、ディレクターが自由に変えてよい |
| **構造・契約** | フェーズの順序、イベントの種類、件の数え方、保存キー名 | **仕様(本書)** | **確定値。変更は仕様変更として扱う** |
| **技術方式** | シングルトン解決 / Text vs TMP / Safe Area方式 | **開発チーム** | 本書は決めない(§13) |

**レイアウト値だけを例外的に実行時に上書きしてよい箇所が2つある。** §7.4 に明記する。それ以外は一切上書きしない。

### 0.2 本書が扱う範囲

扱う: プロジェクト構造 / 画面遷移 / ゲームループ / ミニゲーム差し替え契約 / スコア / HUD / レイアウト共通ルール / 問題データ / ローカライズ / セーブ / 音声。

扱わない: 各画面の要素一覧と挙動(→ `01_Screen_Boot.md` 以降で個別に定義)、各ミニゲームの内部仕様(→ `M1_MicroGame_Letter.md` 以降)。

### 1.2 シーン構成(ガイドライン §5.3-(3)「シーンは薄く保つ」)

- `CanvasScaler.uiScaleMode = ScaleWithScreenSize` / `referenceResolution = 1080 × 1920` / `matchWidthOrHeight = 0`(横幅基準)。**この3つは確定値。**
- 画面Prefabを常駐させるか都度 Instantiate するかは **開発チームの判断**(§13-6)。

### 1.3 画面Prefabの標準構造(ガイドライン §5.3 準拠)

**全画面が同じ骨格を持つこと。** 個別の画面仕様書は、この骨格の `ContentRoot` 以下だけを定義する。

```
Screen_<画面名>                 (RectTransform: stretch 全面 / anchorMin(0,0) anchorMax(1,1) offset 0)
├─ [<画面名>ScreenRefs]         … 参照だけを持つ。ロジックなし。RectTransformに触れない
├─ [<画面名>ScreenController]   … ロジック。Refs経由でのみ要素を操作する
├─ SafeAreaRoot                 (stretch。Safe Area を反映する対象。方式は開発チーム判断 §13-3)
│   ├─ Background               (Image / stretch)
│   ├─ HudRoot                  (anchor (0.5, 1) / pivot (0.5, 1))  ※GamePlayのみ。他画面はHeaderRoot
│   ├─ ContentRoot              (上下ストレッチ: anchorMin(0,0) anchorMax(1,1))
│   │   └─ …画面固有の要素…
│   └─ BottomReserve            (anchor (0.5, 0) / pivot (0.5, 0))  ★高さは実行時計算(§7.4)
└─ (オーバーレイは画面Prefabの内部に置かない。OverlayLayer に別Prefabとして出す)
```

**`Screen_GamePlay` のみ、`ContentRoot` の直下に差し替え領域を持つ。**

```
ContentRoot
└─ MicroGameSlot               (stretch。ここに MicroGame_*.prefab が Instantiate される)
    └─ (実行時のみ子が入る。Prefab上は空)
```

### 3.2 タイマーは2層ある(★ここは既存文書に定義の穴があった。本書で確定させる)

既存文書は「タイマー」を1つのものとして書いているが、**実際には性質の違う2つが必要**である。

|---|---|---|---|---|
| **T1** | **セッションタイマー** | **90秒** | 1プレイの長さ。商品説明「90秒で遊べる」を厳密に守る | **HUDの「のこり時間バー」** |
| **T2** | **ミニゲームタイマー** | **12秒** | 1ミニゲームの制限時間 | **差し替え領域の上辺(`Part_MicroGameTimerBar`)** |

**T1の挙動(確定)**

- **業務提示(★1.5秒。2026-09-15 0.8から変更)・判定演出0.35秒の間も T1 は動き続ける。**
  → 90 ÷ 13.85 = 6.50 という「約6〜7ミニゲーム」の計算が成立するのはこの前提のときだけ。
  → **業務提示を1.5秒に延ばしても T1 は止めない**(`10_Screen_GamePlay.md` §12.8-b)。
- **★終了演出(1.5秒。§3.9)は T1 が0になった後なので、T1 の外側にある。**
  → 「1プレイ時間が完全に一定になる」(企画書 §4.4)もこの前提で成立する。
- T1 が止まるのは **`Overlay_Pause` 表示中** と **`Overlay_MicroGameIntro` 表示中** の2つだけ。

**T2の挙動(確定)**

- 業務提示フェーズの間、T2 は **開始していない(0秒消費)**。既存文書の「業務提示中はタイマー停止」はこの T2 を指す。
- 操作フェーズの開始と同時に T2 が 12秒 から減り始める。
- 3件クリア時、または T2 が0になった時に操作フェーズを終了する。

> **【2026-09-07 ディレクター決定】時間バーは2本見せる。**
> **HUDに90秒バー(T1)、ミニゲーム領域の上辺に12秒バー(T2)。**
> 既存文書はHUDに「のこり時間バー」を1本しか定義していなかったが、
> ①T1が無いと「あと何秒で終わるか」が分からず90秒という商品性が伝わらない
> ②T2が無いと1ミニゲームの切迫感がゼロになり「忙しさ」の主要な源(企画書 §8.3)が失われる
> という理由で、プランナー提案どおり2本立てが採用された。
> T2バーは共通部品 `Part_MicroGameTimerBar` として用意し、**全ミニゲームPrefabが同じものを使う**。

### 3.3 1ミニゲームのフェーズ遷移(全種目共通)

```
[Prepare]  ─ 0秒 ─────────  ミニゲームPrefabをInstantiate、問題を用意、画面に配置
    ↓                        ※問題内容(手紙・荷物・箱)はこの時点ですでに表示する
[Intro]    ─ 0秒 or 待ち ──  ★初出時のみ Overlay_MicroGameIntro(T1停止・タップで閉じる)
    ↓
[Prompt]   ─ ★1.5秒 ─────  業務提示。動詞1語を中央に大きく表示。T1稼働 / T2未開始
    ↓                        ★問題は背景で覆って見せない([Prepare] から [Play] 開始フレームまで)
    ↓                        ★演出(2026-09-15): パンチイン0.22秒 → グルーヴ1.10秒 → ズームスルー0.18秒
    ↓                          + フラッシュ1回・揺れ・集中線・背景色。se_microgame_start を t=0 で1回
    ↓                        ★2026-09-16 ディレクター決定: 黒背景・白文字・動きなし・フラッシュなし
    ↓                          (仕組みは残し値で停止。残る動きは最後の0.18秒の文字フェードアウトだけ)
    ↓                          詳細は 10_Screen_GamePlay.md §12
    ↓                        入力は受け付けない
[Play]     ─ 最大12秒 ────  操作フェーズ。T1稼働 / T2稼働。入力受付
    ↓                        ・3件クリアで即終了(残り時間は待たない)
    ↓                        ・T2が0で終了(時間切れ。失敗ではない)
[Judge]    ─ 0.35秒 ──────  ミニゲーム単位の判定演出。T1稼働 / 入力は受け付けない
    ↓
[Teardown] ─ 0秒 ─────────  ミニゲームPrefabを破棄
    ↓
次のミニゲームの [Prepare] へ

    ※セッションが終わるとき(§3.5)は、どこからでも
[Finish]   ─ ★1.5秒 ─────  ★終了演出(2026-09-15 新設。§3.9)。T1停止済み / 入力遮断
    ↓
Screen_Result へ
```

- **[Prepare] と [Teardown] は1フレーム内で完了させる。** 待ち時間を入れない(テンポを削らない)。
  重い生成処理(M3のバリデーション等)がここに入るため、**フレーム落ちしないことを実機で確認する**(§13-11)。
- ~~**[Prompt] の間、問題内容はすでに読める状態にしておく。** これは「読解系のストレスを下げる要」であり **必須要件**。~~
  **★2026-09-15 ディレクター決定で廃止。新しい要件: 問題内容は `[Prepare]` で用意し切るが、`PromptBackdrop` で覆い、`[Play]` 開始フレーム(T2開始・入力受付開始と同じフレーム)まで見せない。**
  `[Intro]`(初出カード)の間と、`[Prompt]` / `[Intro]` 中に入ったポーズとその復帰カウントダウンの間も覆ったままにする。
  背景はフェードせずハードカットで消す(`10_Screen_GamePlay.md` §12.2-C / §12.6)。**読む時間はすべて T2(12秒)の中に入る。**
- **[Prompt] と [Judge] の間は入力を捨てる**(先行入力を次のフェーズへ持ち越さない)。誤爆防止。

### 3.4 正誤・時間切れの扱い(全種目共通。**ここが本作の設計の芯**)

| 事象 | ミニゲームの進行 | スコア | コンボ | 件数(HUD) |
|---|---|---|---|---|
| **正解**(件が成立) | 次の問へ。3件目なら**クリアして次の種目へ** | **加算** | **+1** | +1 |
| **誤答** | **次の問へ進む**(同じ問題はやり直さない) | なし | **リセット(0)** | 増えない |
| **時間切れ**(T2が0) | ミニゲーム終了 | なし | **継続(維持)** | 増えない |
| **セッション終了による中断** | ミニゲーム終了 | なし | **継続(維持)** | 増えない |
| M3の「積みすぎ(オーバー)」 | やり直せる。**契約上のイベントを発生させない** | なし | **切らない** | 増えない |

**あくまで誤答だけが失敗。** これを実装レベルで言い換えると:

> **`Missed` イベントを発火してよいのは「プレイヤーが明確に誤った選択をしたとき」だけ。**
> 時間切れ・中断・M3のオーバーでは絶対に発火しない。

### 3.5 セッション終了処理(★既存文書に定義がなかったため本書で定義する)

T1(90秒)が 0 になった瞬間の扱いを、フェーズごとに定める。

> **★2026-09-15 改訂: `Result` へ行く前に、どのケースでも終了演出 `[Finish]`(1.5秒。§3.9)を必ず通る。**
> **`[Play]` 中に尽きた場合は `[Judge]` を飛ばす**(終了演出が役割を兼ねる。中断を判定演出で見せると失敗に見えるおそれがあるため)。

| T1が0になった時のフェーズ | 処理 |
|---|---|
| `[Prompt]`(業務提示中) | 業務提示を打ち切り、**そのミニゲームは開始しない**(集計に入れない)→ **`[Finish]`** → `Result`。※閾値 > 業務提示の長さなら通常は起きない |
| `[Play]`(操作中) | 操作を即座に打ち切る(**中断。失敗ではない**)→ ★**`[Judge]` を飛ばして `[Finish]`** → `Result` |
| `[Judge]`(判定演出中) | 演出を最後まで再生 → **`[Finish]`** → `Result` |
| `[Intro]` / ポーズ中 | T1が止まっているので発生しない |

- **T1(90秒)の実プレイ時間は 90.00 〜 90.35秒 に収まる。** その後に終了演出1.5秒が続く。
- **新しいミニゲームを開始するかの判定**: `[Teardown]` 完了時に **T1の残りが ★2.7秒未満なら新規開始せず `[Finish]` へ移る**
  (業務提示だけ見せて何もできずに終わるのを避けるため。**2.7 = 業務提示1.5 + 最低操作1.2秒**。旧値2.0 = 0.8 + 1.2)。
  **仮値。`GameBalanceSettings` に置く。** 要ディレクター確認(§14-2)。
  **この値が業務提示の長さより大きい限り、`[Prompt]` 中に T1 が0になることは起きない。**

### 3.6 出題順(確定 = 制約は1つだけ)

> **連続で同じミニゲームが出ないようにし、あとはランダム。**

```
1本目 : 4種から一様ランダム
2本目〜: 「直前に出した種目」を除いた3種から一様ランダム
```

- **「全種目を必ず1回は出す」という保証はしない**(企画書 §12 論点5 は未決のまま。bag方式は入れない)。
- 乱数は `UnityEngine.Random` を直接使わず、**セッション専用の `System.Random` インスタンス**を持つこと。
  デバッグ機能で**シードを固定して同じ出題順を再現できる**ようにする(§13-10)。

### 3.7 数字の整合性(実装が前提にしてよい値・してはいけない値)

> **★2026-09-15 改訂: 業務提示1.5秒で再計算。**(括弧内は旧0.8秒の値)

| 条件 | 1ミニゲームの長さ | 90秒あたりのミニゲーム数 |
|---|---|---|
| **毎回12秒を使い切る(最も遅い)** | 13.85秒(13.15) | **6.50 → 6本完走 + 7本目が中断**(6.84) |
| 平均8秒で3件終える | 9.85秒(9.15) | 約 **9本**(9.14。旧9〜10本) |
| 平均5秒で3件終える(かなり上手い) | 6.85秒(6.15) | 約 **13本**(13.1。旧14本) |

- **「6〜7ミニゲーム」は最小値であって平均ではない。**
- **実装はミニゲーム数を固定長として扱ってはならない。** 配列・リストのサイズを7で確保するような書き方をしない。
  種目別成績の集計も動的に行う。
- 1セッションの件数(= 最大スコア対象)の理論上限は **ミニゲーム数 × 3件**。上の表なら 18件 〜 **39件**(旧42件)。

## 4. ミニゲームの差し替え契約(★本書で最重要)

### 4.1 責務の分界(これを破ると12月の種目追加が破綻する)

| 責務 | 持ち主 |
|---|---|
| セッションタイマー(T1)・出題順の決定・ミニゲームPrefabの生成/破棄 | **`GameSessionController`** |
| フェーズ進行(Prompt / Play / Judge)・ミニゲームタイマー(T2) | **`GameSessionController`** |
| スコア加算・コンボ管理・HUD更新・セーブ | **`GameSessionController` 配下の共通クラス** |
| **問題の生成・選択・保持** | **各ミニゲーム(内部で完結)** |
| **1問の正誤判定** | **各ミニゲーム(内部で完結)** |
| **問 → 件 への換算** | **各ミニゲーム(内部で完結)** |
| 種目固有の演出(アイテム単位フィードバック等) | **各ミニゲーム(内部で完結)** |

> **`GameSessionController` は「問題」という概念を一切知らない。**
> 知っているのは「件が成立した」「誤答が起きた」の2つのイベントだけ。
> これにより、**新種目がどんな内部構造(1問=1タップでも、連続処理でも、時間制のミニゲームでも)を
> 持っていても、共通側のコードを1行も変えずに追加できる。**

### 4.2 種目の登録データ(`MicroGameDefinition` / `MicroGameCatalog`)

**種目の同一性は enum ではなく ScriptableObject アセットで表す。**
理由: enum を使うと種目追加のたびに共有コードを編集することになり、「1種追加 = 1Prefab + 1スクリプト + データ追加」という
必須要件から外れるため。

```csharp
[CreateAssetMenu(menuName = "Santa/MicroGame Definition")]
public class MicroGameDefinition : ScriptableObject
{
    [SerializeField] private string        id;              // ★安定ID。セーブキー・統計に使う("letter" 等)
    [SerializeField] private MicroGameBase prefab;          // MicroGame_*.prefab のルートに付いたコンポーネント
    [SerializeField] private string        promptTextKey;   // 業務提示の動詞("micro.letter.prompt")
    [SerializeField] private string        titleTextKey;    // ★HUDに常時出すミニゲーム名(§6.1.1)
    [SerializeField] private string        shortTitleTextKey; // ★結果画面の内訳用(4文字以内。§15.6-74)
    [SerializeField] private string        introCardTextKey;// 初出カードの本文
    [SerializeField] private Sprite        introCardImage;  // 初出カードの図
    [SerializeField] private ScriptableObject questionSource; // ★問題データ or 生成器設定(種目ごとに型が違う)
    [SerializeField] private int           questionsPerUnit = 1; // ★M5だけ 3
    [SerializeField] private bool          enabled = true;  // 12月アップデート前は false で仕込んでおける
}
```

```csharp
[CreateAssetMenu(menuName = "Santa/MicroGame Catalog")]
public class MicroGameCatalog : ScriptableObject
{
    [SerializeField] private List<MicroGameDefinition> definitions;
    // enabled == true のものだけが出題対象になる
}
```

- `id` は**セーブデータのキーに埋め込まれる**ため、**一度決めたら変更しない**。
  MVPの4種は `letter` / `address` / `weight` / `wrap`。
- `questionSource` の型が種目ごとに違う点は、`ScriptableObject` 型で受けて各ミニゲームがキャストする。
  **型安全にしたい場合の代替設計(ジェネリクス等)は開発チームの判断に委ねる(§13-9)。**

### 4.3 ライフサイクルAPI(`MicroGameBase`)

各ミニゲームPrefabのルートには `MicroGameBase` を継承したコンポーネントが1つだけ付く。

```csharp
/// 全ミニゲームの共通基底。MicroGame_*.prefab のルートに付ける。
/// ★ここに書かれた5つのメソッド以外を GameSessionController から呼んではならない。
public abstract class MicroGameBase : MonoBehaviour
{
    /// 件が成立した(= スコア加算 + コンボ+1)
    public event Action OnUnitCleared;
    /// 誤答した(= コンボリセット)。★プレイヤーが明確に誤った選択をしたときだけ発火する
    public event Action OnMissed;
    /// 必要件数に達した(= 3件クリア)。共通側はこれを受けて操作フェーズを即終了する
    public event Action OnAllUnitsCleared;

    /// [1] 準備。Instantiate 直後、業務提示の前に1回だけ呼ばれる。
    ///     問題の生成・選択と初期表示をここで完了させる。★入力は受け付けない状態にする。
    ///     ★問題内容(手紙・荷物・箱)はこの時点で画面に見えていること(業務提示中に読ませるため)
    ///     重い処理は避ける。1フレームで完了させること。
    public abstract void Prepare(MicroGameContext context);

    /// [2] 開始。操作フェーズの開始と同時に呼ばれる。入力受付を開始する。
    public abstract void Begin();

    /// [3] 一時停止 / 再開。ポーズ・初出カード表示中に呼ばれる。
    ///     内部のアニメーション・ベルトの流れ・自前のタイマーを止める。
    public abstract void SetPaused(bool paused);

    /// [4] 終了。3件クリア / 時間切れ / セッション終了のいずれでも必ず呼ばれる。
    ///     入力受付を止め、判定演出(0.35秒)に入れる状態にする。
    ///     ★ここで OnMissed / OnUnitCleared を発火してはならない。
    public abstract void Finish(MicroGameFinishReason reason);

    /// [5] このミニゲームの結果サマリ。Finish の後に共通側が1回だけ読む。
    ///     種目別成績・結果画面の集計に使う。
    public abstract MicroGameSummary GetSummary();
}

public enum MicroGameFinishReason
{
    AllUnitsCleared,   // 3件クリア(残り時間を待たずに終わる)
    TimeUp,            // T2が0(★失敗ではない)
    SessionEnded,      // セッション90秒が尽きた(★失敗ではない)
}

/// 共通側からミニゲームへ渡す情報。★ここに無いものをミニゲームが参照してはならない
public readonly struct MicroGameContext
{
    public MicroGameDefinition Definition { get; }  // questionSource / questionsPerUnit を含む
    public int    RequiredUnits { get; }            // = 3(GameBalanceSettings から)
    public float  PlayDuration  { get; }            // = 12.0秒(表示用。時間管理は共通側が行う)
    public System.Random Rng    { get; }            // ★セッション共通の乱数。シード固定でリプレイ可能にする
    public int    SessionPlayIndex { get; }         // このセッションで自分が何本目か(0始まり)

    /// ★この種目がセッションを通じて保持したい状態を取得する(§4.7)。
    /// 無ければ factory で生成して保持し、次に同じ種目が出たとき同じインスタンスを返す。
    /// ★これが State への唯一の読み書き経路である。
    public T GetOrCreateState<T>(Func<T> factory) where T : class, IMicroGameSessionState;
}

/// 中身は各ミニゲームが自由に定義する。共通側は型を知らない。
public interface IMicroGameSessionState { }

public readonly struct MicroGameSummary
{
    public int UnitsCleared { get; }   // 成立した件数(0〜3)
    public int UnitsMissed  { get; }   // 誤答で失った件数
    public int QuestionsAnswered { get; } // 参考値。種目内部の問数(統計・チューニング用)
}
```

**呼び出し順序の契約(共通側が守ること)**

```
Instantiate(prefab, MicroGameSlot)
  → Prepare(context)
  → (初出なら Overlay_MicroGameIntro。その間 SetPaused(true) → 閉じたら SetPaused(false))
  → (業務提示 ★1.5秒。この間 Begin() は呼ばない。問題は背景で覆われている)
  → Begin()
  → …プレイ中。ミニゲームが OnUnitCleared / OnMissed / OnAllUnitsCleared を発火…
  → Finish(reason)
  → GetSummary()
  → (判定演出 0.35秒。★reason == SessionEnded のときは再生しない)
  → Destroy(★セッション終了時は終了演出1.5秒の最後まで遅らせる。その間ミニゲームは止まったまま画面に残る)
```

**ミニゲーム側が守ること**

1. `OnUnitCleared` / `OnMissed` は **`Begin()` から `Finish()` までの間にだけ**発火する。
2. `Prepare()` で問題を用意し切る。**`Begin()` 以降に問題プールへアクセスしない**(フレーム落ちの原因になる)。
3. **T2(12秒)を自分で管理しない。** 残り時間の表示が必要なら共通の `Part_MicroGameTimerBar` を使う。
4. **自分から画面遷移・スコア加算・セーブを行わない。** できるのはイベントを発火することだけ。
5. **`MicroGameSlot` の RectTransform を書き換えない。** 自Prefabのルートは stretch で親に合わせる。

### 4.4 通知イベントとスコアの対応

| イベント | 共通側の処理 |
|---|---|
| `OnUnitCleared` | ①コンボ +1 ②スコア += 100 × コンボ倍率(**加算後のコンボ数で引く**。§5.2)③HUD件数 +1 ④正解SE ⑤最大コンボ更新 |
| `OnMissed` | ①コンボを 0 にリセット ②スコア加算なし ③HUD件数は増えない ④誤答SE |
| `OnAllUnitsCleared` | 操作フェーズを即終了 → `Finish(AllUnitsCleared)` → 判定演出へ |

`OnAllUnitsCleared` は `OnUnitCleared` の**直後**に(同一フレームで)発火してよい。共通側は
`OnUnitCleared` の処理を先に済ませてから `OnAllUnitsCleared` を処理すること。

### 4.5 M5(`MicroGame_Wrap`)の構造差をどう吸収するか ★

M5だけ内部構造が違う。**しかし契約は一切変えない。** 差分はすべてM5の内部と `questionsPerUnit` に閉じる。

| | M1 / M2 / M3 | **M5** |
|---|---|---|
| 1ミニゲームの問数 | 3問(+誤答時に追加供給) | **最大9問**(箱9個。追加供給なし) |
| `questionsPerUnit` | **1** | **3** |
| `OnUnitCleared` の発火条件 | 1問正解するたび | **3問連続正解するたび** |
| `OnMissed` の発火条件 | 1問誤答するたび | **箱1個を誤って処理するたび** |
| 1ミニゲームの最大件数 | 3件 | **3件** |
| 最大スコア | 300点 | **300点** |
| 最大コンボ | 3 | **3** |
| HUDの件数表示 | 正解数と同じ | **9箱さばいても「3けん」** |

**この吸収が成り立つ理由**: 契約の通貨を「問」ではなく「**件**」にしたから。
共通側は `OnUnitCleared` を数えるだけで、その1件が裏で1問だったか3問だったかを知る必要がない。

**M5の件の数え方 = 固定グルーピング(★2026-09-07 ディレクター決定)**

> **1ループ = 固定の3箱。** 箱1-3 が第1ループ、箱4-6 が第2ループ、箱7-9 が第3ループ。
> **3箱すべて正解なら 1件100点 + 1コンボ。誤答が1つでも含まれるループは 0件・コンボなし。**

プランナーは「連続カウント」(正解が3つ続くたびに1件)を推奨したが、**不採用**。
採用理由は「3問×3ループ」という元の言葉に忠実で、**プレイヤーにとって構造が分かりやすい**ため。

**この決定が生む帰結(承知のうえで受け入れる)**

1. **誤答したループの残りの箱も、プレイヤーは処理し続ける必要がある。**
   放置すると見逃しになり、ベルトが詰まる/流れてしまう。**しかし得点には結びつかない。**
2. したがって **1回の誤答で最大2箱ぶん(約2.7秒)の「処理はするが点にならない区間」が生まれる。**
   これは**既知のトレードオフとして受け入れる**が、**プレイテストで観察する対象**とする
   (プレイヤーが「もう無駄だ」と感じて手を止めないか、という点)。
3. **8/9問正解でも、誤答の位置によってスコアが変わる。**
   - 箱1で誤答 → ループ1が 0件、ループ2・3が成立 → **200点(2件)**
   - 箱9で誤答 → ループ1・2が成立、ループ3が 0件 → **200点(2件)**
   - つまり **1個誤ると必ず1件(100点)を失う。**
4. **「全問正解型」ではない。判定はループ単位であって、ミニゲーム単位ではない。**
   9問中3問誤っても、誤りが1ループに固まっていれば **200点(2件)** が残る。
   逆に3ループに1つずつ散らばると **0点(0件)** になる。

**実装上の要点**

- ループ内の誤答は **その場で `OnMissed` を発火する**(コンボは即リセット)。
  ループ終了を待たない。**`OnMissed` はループごとに最大3回発火しうる**が、共通側はコンボを0にするだけなので問題ない。
- ループの3箱目を処理し終えた時点で、**そのループに誤答が1つも無ければ `OnUnitCleared` を発火する。**
- **誤答が確定したループでも、残りの箱の処理は続ける**(`OnMissed` は誤るたびに発火してよい)。
  **`OnUnitCleared` は発火しない。**
- 3ループ目の3箱目を処理し終えた時点、または時間切れで `Finish` に入る。
- **時間切れで途中までしか流れなかったループは、`OnUnitCleared` も `OnMissed` も発火しない**(未確定のまま破棄)。

**この方式でも共通契約は一切変わらない。** 変わるのは `OnUnitCleared` の発火タイミングだけで、
`GameSessionController` 側にM5用の分岐は一切書かない。

**M5に固有の追加ルール**

- 箱9個は**固定のペースで流れる**ため、M5は他種目と違って**早期クリアがほぼ起きない**(常に約12秒使う)。
  → **種目間の時間効率が揃っていない。** M5を引くとそのセッションのミニゲーム総数が減る。§14-5 に残す。
- アイテム単位フィードバック(0.2秒・**非ブロッキング**)は M5 の内部演出であり、契約の `Judge` フェーズ(0.35秒・ブロッキング)とは別物。**混同しないこと。**

### 4.6 種目を1つ追加する手順(12月アップデート。**この手順で済むことが必須要件**)

### 4.7 種目ごとのセッション永続状態(★2026-09-07 追加。M2の仕様検討で判明した契約の不足)

**問題**: ミニゲームPrefabは**1回ごとに `Destroy` される**。しかし
**M2の「地図の累積カウンタ」はセッションを通じて蓄積される。**
Prefabの中に持つと、次にM2が出たときに0へ戻ってしまう。

**解決**: `MicroGameContext` に **`GetOrCreateState<T>(factory)`** を追加した(§4.3)。

```csharp
/// M2の実装例
public class AddressSessionState : IMicroGameSessionState
{
    public Dictionary<string, int> DeliveredPerRegion = new();  // "asia" → 5
}

// M2の Prepare() の中で:
var state = context.GetOrCreateState(() => new AddressSessionState());
// 1回目のM2 → 新規生成して保持される
// 2回目のM2 → 1回目と同じインスタンスが返る(累積カウンタが引き継がれる)
```

**契約(★2026-09-08 修正。developer の指摘により明確化)**

| 項目 | 内容 |
|---|---|
| **唯一の読み書き経路** | **`GetOrCreateState<T>(factory)` のみ。**これ以外に State を取得・設定する手段を用意しない |
| 挙動 | **取得する。無ければ `factory` で生成して保持し、次に同じ種目が出たとき同じインスタンスを返す** |
| キー | `definition.id`。**`GameSessionController` は `id` → `IMicroGameSessionState` の辞書を持つだけ** |
| 型の知識 | **共通側は具象型を一切知らない。**ジェネリクスとキャストはミニゲーム側で閉じる |
| 破棄 | **セッション終了時**(`Screen_Result` へ遷移する時点)。「もう一回」では初期化される |

> **【修正の経緯】初版は「ミニゲーム側が生成して入れる」と書いていたが、
> `MicroGameContext` は readonly struct でゲッターしか持たず、「入れる」ための操作が定義されていなかった。**
> **このままだと1回目のM2で状態を書き込めず、累積カウンタに永久に何も貯まらない。**
> `GetOrCreateState` は**取得と生成を1つの操作にまとめる**ことで、
> 「入れ忘れ」も「二重生成」も構造的に起こらないようにしている。**設計意図はそのまま保たれている。**

- **MVPでこれを使う種目はM2だけ**だが、**12月の新種目が必要とする可能性が高い**ため契約に含める。
  **この仕組みが無いと、M2の累積カウンタを実装するために共通側へM2専用のコードを書くことになり、
  「1種追加 = 1Prefab + 1スクリプト + データ追加」という必須要件が崩れる。**

## 5. スコアとコンボの管理

### 5.1 計算式(確定)

```
1件あたりの得点 = 基本点(100) × コンボ倍率
最終スコア      = Σ(1件あたりの得点)
```

- レベル係数・残時間ボーナス・クリアボーナスは **すべて無し**(削除済み。復活させない)。
- **速く解くことの報酬は「セッション内のミニゲーム数が増える」という構造そのもの**で担保される。

### 5.2 コンボ倍率(仮値。**`GameBalanceSettings.asset` で調整可能にすること**)

| 連続件数 | 倍率 |
|---|---|
| 0〜2 連 | 1.0 |
| 3〜5 連 | 1.2 |
| 6〜9 連 | 1.5 |
| 10 連〜 | 2.0 |

**倍率を引くタイミング(★既存文書に定義がなかったため本書で確定させる)**

> **件が成立したとき、まず**コンボを +1 してから**、その値で倍率を引く。**

```
1件目 → combo = 1 → 倍率 1.0 → 100点
3件目 → combo = 3 → 倍率 1.2 → 120点   ← HUDに「3れんぞく」が出るのと同時に倍率が上がる
```

こうすることで **HUDのコンボ表示(3以上で出る)と倍率の上昇タイミングが一致する**。
プレイヤーから見て「表示が出た = 倍率が上がった」と分かる。

**データ構造**: 閾値と倍率の**配列**として持つこと(4段固定でハードコードしない)。段数の増減を SO で行えるようにする。

```csharp
[Serializable] public struct ComboTier { public int minCombo; public float multiplier; }
// GameBalanceSettings に ComboTier[] を持ち、minCombo の降順に探索して最初に一致したものを使う
```

### 5.3 コンボのリセット条件(確定)

| 事象 | コンボ |
|---|---|
| **誤答**(`OnMissed`) | **リセット(0)** |
| 時間切れ | **継続** |
| セッション終了による中断 | **継続** |
| ミニゲームの切り替わり | **継続**(★種目をまたいで積み上がる) |
| M3の積みすぎ(オーバー) | **切らない** |
| ポーズ / 初出カード | **継続** |

- **最大コンボ**はセッションを通じての最大値を別途保持し、結果画面に「最高 ◯連続」として出す。
- 理論上の最大コンボ = ミニゲーム数 × 3。§3.7 の表なら 18〜42。

### 5.4 M5のスコア丸め(確定。決定ログ 構造-12)

> **M5は3問正解 = 1件100点。** HUDの件数表示も同じ数え方(9箱さばいても「3けん」)。

§4.5 のとおり `OnUnitCleared` の発火単位で自動的に成立する。**共通側に M5 用の分岐を書かないこと。**

### 5.5 サンタランク(閾値は**プランナーの仮値**。`RankTable.asset` で調整可能にすること)

| ランク | 仮閾値 |
|---|---|
| 見習いサンタ | 0 |
| 一人前サンタ | **800** |
| ベテランサンタ | **1,800** |
| スーパーサンタ | **3,000** |
| サンタマスター | **4,200** |

**算出根拠**(§3.7 の前提から逆算):

- ノーミスで10ミニゲーム(30件)= 100×(2×1.0 + 3×1.2 + 4×1.5 + 21×2.0) = **5,360点**
- ノーミスで7ミニゲーム(21件、最も遅いプレイ) = **3,560点**
- → **マスター4,200 は「速く回して、ほぼノーミス」でようやく届く水準**になり、到達可能。
  企画書 §7.2 が「現在の式では到達不可能」と警告していた問題は、
  §3.7 の「速く解けばミニゲーム数が増える」を織り込むことで解消する。

> **これは仮値であり、プレイテストの実測分布で引き直す前提。**
> 特に「一人前サンタに初回〜3回目で到達できること」(達成感の初速)は実測でしか確認できない。

> **★2026-09-15 注記**: 上の算出根拠は業務提示0.8秒の頃のもの。**1.5秒にしたことで同じ腕前でも回せる本数が約7%減る**(さらに業務提示中に問題を読めなくなった)
> (例: ノーミス10本ペースの人が約9本 → 約4,760点)。**マスター4,200 はまだ到達可能だが、閾値の引き直し時にこの差を織り込むこと。**

### 6.1.2 ★90秒バーは「HUDの下辺」を兼ねる(新規)

- **HUDとコンテンツ領域の境界線が、そのまま残り時間バーになる。**

  **残量が0に近づいてもバーが消えないようにする** —— 消えると**HUDとコンテンツの境界線そのものが失われ、
  画面の構造が崩れて見える。**
- 色は 残り100〜50%=緑 / 50〜20%=黄 / 20〜0%=赤 + 点滅(**毎秒2回まで**)。
- **減る向き**(左→右 / 右→左)は**ディレクターが決める**(§15.6-77)。

> **「処理件数」の定義(★既存文書が曖昧だったため本書で確定させる)**
> **HUDの「しょり ◯けん」= 成立した件数(`OnUnitCleared` の累計)。** 誤答・時間切れは含めない。
> 結果画面の「◯件 処理した」も**同じ値**。
> 結果画面の「◯/◯ 件 成功」は **成立件 / (成立件 + 誤答件)**。時間切れで未回答のぶんは分母に入れない。

> **スコア数値をHUDに置かない件は、既存文書に明記がなかったためプランナーの提案。**
> 理由: ①HUDの情報量を減らして視線を守る(設計原則2)②結果画面のカウントアップ演出が主役になる。
> **要ディレクター確認(§14-9)。**

### 6.2 レイアウトを動かさないための実装ルール(★重要)

## 7. 画面レイアウトの共通ルール

### 7.1 基準解像度とゾーニング(**初期値**。以後ディレクターの所有物)

- 基準解像度 **1080 × 1920** / `matchWidthOrHeight = 0`(横幅基準)。**この2つは確定値。**

| ゾーン | 高さの初期値(1920基準) | アンカー既定 |
|---|---|---|
| 上部セーフエリア | 約160px(ノッチ / Dynamic Island) | 上端 |
| **A. HUD** | **約200px**(★2026-09-08 変更。220 → 200) | `(0.5, 1)` |
| **B+C. コンテンツ領域** | 残り全部(**1264px**) | **上下ストレッチ** |
| **D. バナー予約領域** | 296px(バナー160 + 下部SA96 + 余白40。**非表示時も常に確保**) | `(0.5, 0)` |

> **HUDを 220 → 200px に縮めた理由**(2026-09-08):
> **90秒バーがHUDの下辺(区切り線)になり、独立した1行を占めなくなったため**(§6.1.2)。

### 7.1.1 ★`Screen_GamePlay` の縦の内訳(2026-09-08 更新。**全ミニゲームの前提**)

```
  0 〜  160   上部セーフエリア            何も置かない
160 〜  360   HudRoot(200px)             名前 / 件数 / コンボ / ポーズ
                                          └ 下辺 12px = 90秒バー
360 〜 1624   ContentRoot(1264px)
              ├ 360 〜 1494  MicroGameSlot(1134px) ★ミニゲームが入る
              ├ 1494 〜 1534 (余白 20 + ドット)
              ├ 1554 〜 1594 UnitProgressDots(●●○)
              └ 1594 〜 1624 MicroGameTimerBar(12秒。24px + 余白)
1624 〜 1920   BottomReserve(296px)       バナー + 下部SA。何も置かない
```

**`MicroGameSlot` の高さ = 1134px。** 4種すべてのレイアウトはこの値を前提に検算する。

> **★変更前後の比較**: 旧 1124px → 新 **1134px(+10px)**。
> **12秒バーと進捗ドットを上から下へ移しただけなので、ミニゲーム領域の高さはほぼ変わらない。**
> HUDを20px縮めたぶん、わずかに広くなっている。**M2の地図とM5のベルトへの悪影響は無い**(§15.6-78)。

> 換算根拠: 1080px ÷ 393pt = 2.75px/pt。上部SA 59pt≒162px / 下部SA 34pt≒94px /
> アダプティブバナー 50pt≒138px(安全側に160px)。**実機検証が必要**(§13-4)。
> 下端の合計見積もりが 256px / 280px で割れていた件は、**§7.4 の実行時計算で解消する**。

### 7.2 アンカーの既定ルール(ガイドライン §5.7)

| 要素 | アンカー |
|---|---|
| 画面上部の要素(HUD・ヘッダ) | `(0.5, 1)` |
| **画面下部の要素(タップ対象・バナー予約・主要ボタン)** | `(0.5, 0)` |
| 全画面背景・パネル | `stretch` |
| **コンテンツ領域** | **上下ストレッチ** |
| 中央の主役要素 | `(0.5, 0.5)` |

**余った縦幅はすべてコンテンツ領域が吸収する。** これで端末の縦横比が変わってもHUDとボタンの位置関係が崩れない。

### 7.3 バナーの扱い(確定)

1. **領域は常に確保、中身だけ差し替え。** 広告の読み込み成否でレイアウトが動いてはならない(タップ位置がずれると誤タップ→無効クリック→広告アカウント停止のリスク)。
2. **バナー本体はネイティブのオーバーレイ**として画面下端に出る(Unity Canvas の子ではない)。
   Unity側の `BottomReserve` は「そこに被らないための予約高さ」を確保するだけ。
3. **バナー予約領域の上に固定の余白(40px程度)を置く。** 計算誤差が出ても操作対象と直接接しないようにする。
4. 画面ごとの表示可否は `AdDisplayPolicy.asset` で切り替えられるようにする。
   **既定は「ゲームプレイ中は非表示、それ以外の画面で表示」**(企画書 §12 論点6 のB案)。
   **表示しない画面でも予約領域は確保したままにする。** → §14-10 でディレクター確定を取る。

### 7.4 下端予約高さの実行時計算(★レイアウト所有権の唯一の例外)

> **下端の予約高さは実行時に計算する。設計値をハードコードしない。**(決定ログ 画面-1)

常設サービス `BottomInsetProvider` が次を算出し、現在表示中の画面へ反映する。

```
bottomInset = Screen.safeArea の下端インセット(px換算)
            + バナーの実測高さ(非表示時は 0 ではなく "表示された場合の高さ" を使う)
            + 固定余白 40px(基準解像度換算)
```

- 算出タイミング: **起動時 / セーフエリア変化時(回転は無いが、機種・OS更新で変わりうる)/ 画面遷移時 / バナー読込完了時**。
- 反映先は **各画面の2つの値だけ**:

| 対象 | 実行時に上書きされる値 |
|---|---|
| `BottomReserve` | `sizeDelta.y`(高さ) |
| `ContentRoot` | `offsetMin.y`(下端オフセット) |

> **これは §0.1 の所有権ルールに対する明示的な例外である。**
> **ディレクターがInspectorでこの2つの値を変えても、実行時に上書きされる。**
> 上書きしてよいのはこの2値だけで、**他のRectTransform値には絶対に触れない**(x方向・他の要素も含む)。
> 実行時のみの変更であり、**Prefabアセットを書き換えてはならない**(`PrefabUtility.RecordPrefabInstancePropertyModifications` 等を呼ばない)。
> この制約を `BottomInsetProvider` のクラスコメントに明記すること。

**検証は最小・最大の2端末で行う。** セーフエリアが最も小さい機種と最も大きい機種の両方で、
タップ対象がバナーに被らないことを確認する(§13-4)。

### 7.4.1 ★演出用ラッパー —— 実行時に動かしてよい RectTransform(2026-09-15 追加)

**揺れ・パンチイン(拡大縮小)のような演出は、RectTransform を実行時に動かさないと作れない。**
しかし §0.1 のとおり**ディレクターが調整した位置・サイズを書き換えてはならない。** これを両立させるため、次の規約を置く。

| 規約 | 内容 |
|---|---|
| 1 | **動かしたい要素の親に、演出専用の空の RectTransform を1枚挟む。**名前は `<対象>Anim`(例 `PromptTextAnim` / `FinishTelopAnim`) |
| 2 | ラッパーは**親と同じ矩形(stretch・offset 0)、または固定の中央配置**で作り、**静止時の値は scale (1,1,1) / anchoredPosition のずれ 0 / 回転 0** とする |
| 3 | **コードが動かしてよいのはラッパーの `localScale` / `anchoredPosition` / `localEulerAngles` だけ。**ディレクターが調整するのは**ラッパーの親や中身**の値 |
| 4 | **演出が終わったら必ず静止時の値へ戻す**(中断・ポーズ・画面遷移を含む)。**Prefabアセットを書き換えない**(実行時のみ) |
| 5 | ラッパーそのものの位置・大きさ(規約2の値)をディレクターが変えるのは自由。コードは**演出開始時の値を保存し、そこからの相対で動かして、終了時にその値へ戻す** |

> **§7.4 の「実行時に上書きしてよい2値」の例外リストには加えない。** ラッパーは「ディレクターのレイアウト値を持たない、演出のための部品」と定義することで、所有権ルールと衝突しない。
> **先例**: ~~`Screen_ModeSelect`~~ **`Screen_Title`(★2026-09-17 統合)** の初回案内の脈動(`02_Screen_Title.md` §4.5)も「元の値を保存して必ず戻す」方式。

### 7.5 タップ対象の共通ルール(確定)

| 項目 | 値 |
|---|---|
| **最小タップ領域** | **160 × 160px**(基準解像度。≒58×58pt。Apple推奨44ptを上回る) |
| **隣接要素との間隔** | **40px 以上** |
| **配置** | **ゲームの操作対象は必ずコンテンツ領域の下半分**(親指が自然に届く範囲) |
| 例外 | HUDのポーズボタン(§6.4)/ M2の地図の地域(輪郭がそのまま当たり判定になるため、**素材側で小さい地域を大きめにデフォルメして 160px を確保する**) |

高速連打での誤タップは「理不尽」として最も強い不満を生む。**このルールを下回る要素は作らない。**

### 7.6 LayoutGroup の使いどころ(ガイドライン §5.6)

- **可変長の繰り返し(設定画面のリンク行、種目別成績行、クレジット行)にだけ LayoutGroup を使う。**
- **固定の画面レイアウト(HUD・ミニゲームの選択肢・ボタン)には LayoutGroup を使わない。**
  LayoutGroup 配下の子はドラッグで動かせなくなり、ディレクターの調整体験が壊れるため。
- 動的な行は必ず `Row_*.prefab` を `Instantiate` する。**`new GameObject` で組み立てるコードを書かない。**

### 7.7 ★文字色は背景素材との組み合わせで決める(2026-09-16 追加)

> **経緯**: ディレクターから「文字の色が背景と同化して読みにくいものが多い」と指摘された。
> 原因の一つは、**背景を暗い色で作っていたころの文字色のまま、背景だけを白地の素材(HUD背景 `hud_bg.png` など)に差し替えた**こと。
> (業務提示は一度「白背景・黒文字」にしたが、ディレクター再指示で**黒背景・白文字**に決まった。**どちらの向きでも、背景と文字の明るさの差をはっきり取る**ことが要点)

**ルール(全画面・全ミニゲーム共通)**

| # | ルール |
|---|---|
| 1 | **文字色は、その文字の真下に来る背景(背景画像・背景色・下の要素)との組み合わせで決める。**文字色だけを単独で決めない |
| 2 | **背景の素材や色を差し替えたら、その上に載っている文字の色も必ず見直す。**「画像を割り当てただけ」「色を変えただけ」で作業を終えない。**同じことは、背景の上で光らせる・線を描く演出(フラッシュ・集中線など)にも当てはまる** |
| 3 | **明るい背景には黒などの暗い文字、暗い背景には白などの明るい文字**を基本にする。**色味の違い(赤と緑など)だけで読ませない**(全種目ルール「色だけに頼らない / 赤×緑を並べない」) |
| 4 | **仮画像を置いたときも同じ。**仮画像が白地(透過なし)なら、白地の上で読めるかを確認する。**透過版に上書きしたときは、透けて見える下の背景とあわせてもう一度確認する** |
| 5 | 背景が変わる画面(スライド・演出で背景が動くもの)は、**最も読みにくくなる瞬間**で確認する |

**確認のしかた**: 実機または Game ビューで、**実際の素材を入れた状態**で見る。**迷ったら取りまとめ役経由でディレクターに確認する**(色はレイアウト値ではないが、見た目の判断はディレクターが行う。§0.1)。

**2026-09-16 に見直した箇所**

| 箇所 | 背景 | 文字色 | 仕様書 |
|---|---|---|---|
| HUD(ゲーム名・件数・コンボ。★ポーズボタンの仮の文字は未変更) | `hud_bg.png`(白地) | **黒**(developer 対応済み) | `10_Screen_GamePlay.md` §3.1.2 |
| 業務提示 `PromptText` | `PromptBackdrop`(暗い紺 → 白(撤回)→ **黒**) | ~~黒~~ → **白**(★ディレクター再指示で黒背景・白文字に。動きもなし) | 同 §12.5 / §12.5.1 |
| M3 目標の数字 `TargetValueText` | そりの画像の上 → **そりと箱の間**へ移動 | **黒** | `22_MicroGame_Weight.md` §3.3.1 |

> **アセット一覧**: 素材を差し替えるときの注意として、`アセット一覧_画像・SE.md` §3.1-9 にも同じ趣旨を書いた。

3. **Sprite参照の解決漏れをインポート時点で検出**し、エラーとして表示する(実行時に画像が出ない事故を防ぐ)。
4. インポート結果のサマリ(件数・スキップ数・エラー)を必ずログに出す。
5. **文字コードは UTF-8(BOM付き)。** 区切りはカンマ、値はダブルクォートで囲む。
   → **分かち書きのスペースは半角スペース(U+0020)に統一する。** 全角スペースを混ぜない(§15-6)。

### 8.3 M1(手紙)のCSV列

```
id, lang, template_type, line1, line2, line3, correct_item_id, distractor_ids,
uniqueness_note, review_status, added_version
```

- **主キーは `id` + `lang` の複合。** M1は英語版が対訳ではなく**別問題**になりうるため、
  同じ `id` でも `lang` 行ごとに内容が違ってよい(§9.3)。
- `template_type`: `A`(直接指定)/ `B`(否定・除外)/ `C`(大量)
- `line1`〜`line3`: **最大3行 / 1行14文字 / 合計35文字(全角。分かち書きのスペースを含む)**。
  **平均は20〜23文字に抑える**(決定ログ 構造-13)。**インポータで文字数上限を検証し、超えたらエラーにする。**
- `distractor_ids`: 誤答3つ。`|` 区切り。**在庫カードは常に2列×2行の4枚固定**(正解1 + 誤答3)。
- `uniqueness_note`: **なぜ正解が一意かを書く列。**空欄なら `approved` にできない(インポータで検証)。

### 8.4 M2(住所)のCSV列

```
id, name_ja, name_en, flag_sprite_id, region_id, weight, review_status, added_version
```

- **M1と違い、言語は「行」ではなく「列」で持つ**(国名は対訳が成立するため)。**この非対称は意図的。**
- `region_id`: `asia` / `europe` / `africa` / `north_america` / `south_america` / `oceania`(6州区分)
- `weight`: 出題の重み。**オセアニアは候補が少ないため高めにする**(全地域が使われることを担保)。
- **除外国リスト(企画書 §5.2)に該当する国はCSVに書かない。**
  インポータに**除外国のブラックリスト検証**を入れ、混入したらエラーにする(将来の追加時の事故防止)。
- `flag_sprite_id`: **プロトタイプでは実画像を用意せず、画像枠だけを表示する**(素材はディレクターが後から差し込む)。
  未解決の `flag_sprite_id` は**警告(エラーではない)**として扱い、プレースホルダ画像を割り当てる。

### 8.5 M3(重さ)の生成器とバリデーション

| # | 条件 | 内容 |
|---|---|---|
| 1 | **正解の一意性** | **目標値ちょうどになる組み合わせが、6個の箱の中にちょうど1通りだけ存在する** |
| 2 | **同一数値の禁止** | 同じ数値の箱が2つ以上存在しない |

計算量は問題にならない。

- 生成が条件を満たさない場合はリトライする。**リトライ上限(例: 50回)を設け、超えたら静的なフォールバック問題を使う。**
  無限ループでフレームが止まる事故を防ぐ。
- **生成は `Prepare()` の中で1フレーム内に完了させること。** 実機で計測する(§13-11)。
- 目標値・箱の数値の範囲は**未確定**(企画書 §12 論点11)。
  **プランナーの仮案**: 箱の数値は 1〜9 から相異なる6個、目標値は 2〜4個の和。`WeightGeneratorSettings.asset` で調整可能にする。
  **★2026-09-16 更新(ディレクター決定)**: 上の仮案は `22_MicroGame_Weight.md` §5 に置き換わっている。**選べる箱は最大3個**(解は2〜3個。「4個の和」は使わない)、
  **目標値は最大20(テストプレイ用の暫定。`WeightGeneratorSettings.maxTargetValue`、Inspectorで調整可)**。
  生成は**先に答えの箱(2〜3個、合計 ≤ `maxTargetValue`)を決めてから残りの箱を埋める方式**に変更済み。詳細は `22_MicroGame_Weight.md` §4.3 / §5。

## 9. 文言とローカライズ

### 9.1 方針(確定)

> **日本語 + 英語。初回リリースから両対応。UI文言・問題データを最初から言語キー化する。**

### 11.3 実装ルール

- `AudioManager` に集約。**各画面・各ミニゲームが `AudioSource` を直接持たない**(音量設定が効かなくなるため)。
- BGM / SE の音量は独立して設定でき、`santa.volume.bgm` / `santa.volume.se` に保存する。
- **端末の消音スイッチに従うか**、**バックグラウンド移行時に音を止めるか**の実装方式は**開発チームの判断**(§13-13)。
- **SEの多重再生対策**: M5は1.33秒に1回タップされうるため、同一SEの重なりで音割れしないようにする(実装方式は開発チーム判断)。
- **★長いSEの停止(2026-09-15 追加)**: `se_microgame_start`(1.42秒)・`se_finish`(0.75秒)は、ポーズ・中断・画面遷移で**途中で止められること。**
  現状の `PauseAll()` は `PlayOneShot` の単発SEを止めない。**止める手段を `IAudioManager` に足す**(方式は開発チーム判断)。
- **★BGMのフェードアウト(2026-09-15 追加)**: 終了演出で `bgm_gameplay` を0.15秒で絞って止める。`StopBgm` にフェード秒数を渡せるようにする等(方式は開発チーム判断)。
- **★全体倍率(2026-09-16 追加)**: `AudioManager` が鳴らす**すべての音(BGM・単発SE・ループSE・長いSE)に全体倍率(既定 0.7)を掛ける。**§11.4。

### 11.4 ★音量の計算(2026-09-16 追加)

> **【2026-09-16 ディレクター決定】全体の音量を約7割にする。**
> `AudioManager` に**全体倍率(既定 0.7)**を追加し、BGM・SE のすべてに掛ける。

```
実際のBGM音量 = BGMスライダーの値(santa.volume.bgm) × BGMの基準倍率 bgmBaseVolumeScale(0.6) × 全体倍率(0.7)
実際のSE音量  = SEスライダーの値(santa.volume.se)  ×                                          全体倍率(0.7)
```

| 値 | 既定 | 置き場所 | 誰が変えるか |
|---|---|---|---|
| BGM / SE スライダーの値 | **1.0** | `santa.volume.bgm` / `.se`(§10) | プレイヤー(設定画面) |
| BGMの基準倍率 | **0.6** | `AudioManager.bgmBaseVolumeScale`(2026-09-15 追加。暫定値) | ディレクター(Inspector) |
| **全体倍率** ★ | **0.7** | **`AudioManager.masterVolumeScale`**(Inspector。2026-09-16 developer 実装) | ディレクター(Inspector) |

> **★実装(2026-09-16 developer)**: `masterVolumeScale` は **BGM・単発SE・ループSE** に掛かり、BGMでは `bgmBaseVolumeScale` と掛け合わせる。
> 長いSE(`se_microgame_start` / `se_finish`)は単発SEと同じ `PlaySe`(`sePool`)で鳴るので、**同じく掛かっている**(プランナーがコードを読んで確認。変更はしていない)。

**スライダーが初期値 1.0 のときの実際の音量: BGM = 1.0 × 0.6 × 0.7 = 0.42 / SE = 1.0 × 0.7 = 0.70**

**実装ルール**

- **全体倍率はプレイヤーに見せない・保存しない。**設定画面のスライダーの表示と保存値は、倍率を掛ける前の 0.0〜1.0(`04_Screen_Settings.md` §4.5)。
- **掛け漏れを作らない。**BGM の再生開始・フェードアウトの開始値と終了後の戻し値・一時停止からの再開・音量設定の反映、単発SE・ループSE・長いSE(`se_microgame_start` / `se_finish`)の**すべてで同じ計算**を使う(計算を1か所にまとめる)。
- **スライダーの初期値は 1.0 のまま変えない。**音量を下げるのは全体倍率の役目(理由: すでに音量を保存している端末にも効く / 「最大 = 1.0」の見た目を保てる / 保存値の移行が要らない)。
- 実機で大きすぎる・小さすぎる場合は、**全体倍率(全体)またはBGMの基準倍率(BGMだけ)を Inspector で調整する。**§14-58。
