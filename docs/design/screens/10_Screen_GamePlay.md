## 1. 画面の目的

**90秒のセッションを回し、ミニゲームを次々と差し替えながら、スコアとコンボを積み上げさせる画面。**
本作の検証対象「短時間、次々と仕事をこなすことが楽しいか」が成立するかどうかは、この画面がすべてを担う。

**この画面が持つ責務(共通仕様 §4.1 の再掲)**

- セッションタイマー(90秒)の管理
- 出題順の決定とミニゲームPrefabの生成/破棄
- フェーズ進行(業務提示**1.5秒** → 操作12秒 → 判定演出0.35秒)**★2026-09-15 0.8 → 1.5秒**
- **業務提示の演出(§12)と終了演出(§13)の再生** ★2026-09-15 追加
- ミニゲームタイマー(12秒)の管理
- スコア加算・コンボ管理・HUD更新
- オーバーレイ(Countdown / MicroGameIntro / Pause)の差し込み
- セッション終了時の集計とセーブ、**終了演出(1.5秒)**、`Screen_Result` への遷移

**この画面が持たない責務**

- **問題の生成・選択・正誤判定**(各ミニゲームの内部)
- 判定演出の中身(`Part_JudgeEffect` に委譲。中身は保留)

### 3.1 ★90秒バーが「HUDの下辺」になったことの実装上の注意

- **背景トラック(満タン時の色の帯)を必ず置くこと。**
  **残量が0に近づいてもバーが消えないようにする** —— 消えると**HUDとコンテンツの境界線そのものが失われ、
  画面の構造が崩れて見える。**
- バーは **1080px 全幅**(HUDの内容は左右40pxのマージンを持つが、バーは端まで引く)。
- **減る向き**(左→右 / 右→左)は**ディレクターが決める**。既定は左端固定で右へ減る。

**H1の点滅**: **毎秒2回を上限**とする(光過敏性発作への配慮)。点滅は `alpha` の往復で行い、
**RectTransform を動かさない**(scale の往復も避ける。ディレクターの調整値と干渉するため)。

**H3の表示切替**: コンボが 3 に到達した瞬間に `alpha` を 0→1、0にリセットされた瞬間に 1→0。

## 4. 処理内容(操作 → 何が起きるか)

### 4.1 画面に入ったとき

```
1. GamePlayScreenRefs を取得、HUDを初期化(件数0 / コンボ非表示 / T1バー満タン)
2. GameSessionController.StartSession(mode: GameModeDefinition, retry: bool) を呼ぶ
   ├─ セッション状態を初期化
   │   ・残り時間 = ★mode.sessionDuration(90秒モードなら90。0 なら無制限)
   │   ・スコア 0 / コンボ 0 / 最大コンボ 0 / 成立件数 0 / 誤答件数 0
   │   ・種目別集計を空にする
   │   ・乱数 System.Random を新規生成(デバッグ時はシード固定)
   │   ・各ミニゲームの問題プールをシャッフル(共通仕様 §8.7)
   ├─ BGM を bgm_gameplay に切り替える
   ├─ AdDisplayPolicy に従いバナーの表示/非表示を切り替える(予約領域は確保したまま)
   └─ Overlay_Countdown を表示(retry なら 1.5秒、通常は 3.0秒)
3. カウントダウン終了 → T1 の計測を開始 → 最初のミニゲームへ
```

> **★2026-09-17 ディレクター決定と実装の要件(詳細は `30_Overlay_Countdown.md`)**
> - **カウントダウン「3・2・1・スタート!」(「もう一回」「はじめから」は「2・1・スタート!」)を表示する。長さは 3.0秒 / 1.5秒のまま。**`se_countdown` / `se_start` は素材が入るまで無音でよい。**押してから操作できるまで 4.5秒 /「もう一回」3.0秒は了承済み。**

> - **カウントダウン中、`PromptBackdrop` は出さない**(ミニゲームがまだ無く、隠すものが無い)。**黒い背景はカウントダウン終了直後の `[Prepare]` で初めて出る**(§12.6 の表の「`[Prepare]`」行)。

```
  ・入力は受け付けない(microGame.Begin() をまだ呼んでいない)
  ・★ポーズ中はフェーズ経過時間を進めない(§12.7)。バックグラウンドから復帰したら Prompt を最初からやり直す

[Play] 最大12秒
  ・★同じフレームで PromptBackdrop を消す(ハードカット)。ここで初めて問題が見える(§12.2-C)
  ・microGame.Begin() を呼ぶ
  ・T2 の計測を開始(12秒 → 0)
  ・PauseButton を活性にする
  ・以下のいずれかで抜ける:
      (a) OnAllUnitsCleared を受け取った  → Finish(AllUnitsCleared)
      (b) T2 が 0 になった                → Finish(TimeUp)  + se_timeup
      (c) T1 が 0 になった                → Finish(SessionEnded)

[Judge] 0.35秒
  ・★(c) SessionEnded で抜けた場合は [Judge] に入らず、集計だけして即 [Finish] へ(§13.2)
  ・PauseButton を非活性にする
  ・MicroGameTimerBar を非表示
  ・summary = microGame.GetSummary()
  ・種目別集計に summary を加算(SaveManager へはまだ書かない)
  ・JudgeEffect.Play(summary) を呼ぶ(中身は保留。共通仕様 §3.8)
  ・T1 は稼働したまま。★この間に T1 が0になっても判定演出は最後まで再生し、その後 [Finish] へ

[Teardown]
  ・イベントの購読を解除
  ・★T1 の残りが minRemainingTimeToStartNewMicroGame(★推奨 2.7秒。§9-4 / §12.8-c)未満 または T1 = 0 なら
      → ミニゲームを破棄せずに [Finish](終了演出。§13)へ。破棄は終了演出の最後に行う
    そうでなければ
      → Destroy(microGame.gameObject) → 次のミニゲームの [選定] へ
```

### 4.3 ミニゲームからのイベント受信

| イベント | 処理 |
|---|---|
| `OnUnitCleared` | ① `combo += 1` ② `maxCombo = max(maxCombo, combo)` ③ `gained = 100 × 倍率(combo)`(**加算後のコンボで倍率を引く**)、`score += gained` ④ `unitCount += 1` → H2 更新 ⑤ **`UnitProgressDots` を1つ埋める**(§3.4-A)⑥ **`ScorePopup` に `+{gained}` を出す**(§3.4-B)⑦ `se_correct` ⑧ combo が 3 以上なら H3 を表示し `se_combo` ⑨ 種目別集計の `cleared += 1` |
| `OnMissed` | ① `combo = 0` ② H3 を非表示 ③ `se_wrong` ④ 種目別集計の `missed += 1` ⑤ **スコア・件数は変えない** |
| `OnAllUnitsCleared` | 操作フェーズを即終了(`OnUnitCleared` の処理を先に済ませてから) |

**`OnMissed` と `OnUnitCleared` の処理順**: 同一フレームで両方来ることはない(M5でも別の箱の処理)。

### 4.4 セッション終了(T1 が 0)

共通仕様 §3.5 のとおりフェーズごとに扱いが違う。

> **★2026-09-15 改訂: どのケースでも、`Screen_Result` へ行く前に必ず終了演出 `[Finish]`(1.5秒。§13)を通る。**
> また **`[Play]` 中に T1 が0になった場合は `[Judge]` を再生しない**(終了演出が判定演出の役割を兼ねる)。

| T1が0になった時 | 処理 |
|---|---|
| `[Prompt]` 中 | 業務提示の演出と `se_microgame_start` を止め、`microGame` を `Finish(SessionEnded)` せずに破棄。**そのミニゲームは無かったことにする**(集計に入れない)→ **`[Finish]`**。※`minRemainingTimeToStartNewMicroGame > promptDuration` である限りこのケースは通常起きない(§12.8) |
| `[Play]` 中 | **その瞬間に** `Finish(SessionEnded)` → `GetSummary()` を集計に加算 → **`[Judge]` を飛ばして `[Finish]`**。ミニゲームは破棄せず、止まった状態で背後に残す |
| `[Judge]` 中 | 判定演出を最後まで再生(最大0.35秒)→ **`[Finish]`**。ミニゲームは破棄せず背後に残す |
| `[Teardown]` で残り **2.7秒**(推奨値。§9-4)未満 | ミニゲームを破棄せず **`[Finish]`**。T1バーは終了演出の最初の0.2秒で0まで流し込む(§13.2) |

**終了処理**(★2026-09-15 改訂。**旧手順の 1〜7 は §13.2 の終了演出タイムラインの中に組み込まれた**)

```

1. T1 を停止(以後 T1 は動かない)
2. 入力を遮断(FinishBlocker の raycastTarget を有効に)。PauseButton を非活性

4. BGM(bgm_gameplay)を 0.15秒でフェードアウトして停止
5. se_finish を再生
6. rank = RankEvaluator.Evaluate(score)   … RankTable.asset の閾値
   isNewRecord = score > SaveManager.HighScore

```

### 4.7 ★`GameSessionController` は常設サービス —— リセット漏れに注意(2026-09-08 追加)

**§10-G1 の決定により、`GameSessionController` は `Screen_GamePlay` のPrefabではなく
`Main.unity` の `Services` 配下に常駐する。**

**採用理由**: `SessionResult` を `Screen_Result` へ渡すとき、**画面Prefabの生存期間に依存しなくて済む。**
`Screen_GamePlay` を破棄しても結果が消えない。

> **★副作用: 前回のセッション状態がインスタンスに残る。リセット漏れが起きうる。**
>
> Prefabに載せる方式なら**画面ごと破棄されるので自動的に初期化されていた**が、
> 常設サービスは**同じインスタンスが使い回される。**
> **`StartSession()` の先頭で、セッション状態を「明示的に」全部初期化すること。**

**`StartSession()` で必ずリセットするもの(★チェックリスト)**

| # | 対象 | リセット漏れたときに起きること |
|---|---|---|
| 1 | `RemainingTime` | 前回の残り時間から始まる |
| 2 | `Score` | **前回のスコアが加算され続ける。ハイスコアが壊れる** |
| 3 | `Combo` / `MaxCombo` | 前回のコンボが継続する |
| 4 | `ClearedUnits` / `MissedUnits` | **HUDの件数と結果画面の統計が壊れる** |
| 5 | `PreviousDefinition` | **前回の最後の種目が「直前」として残り、1本目に出なくなる**(気づきにくい) |
| 6 | `PerMicroGame`(種目別集計) | 種目別成績が累積する |
| 7 | `Rng`(乱数) | シードを固定していると同じ出題順が繰り返される |
| 8 | **各ミニゲームの `IMicroGameSessionState`**(§4.7 / 共通仕様 §4.7) | **M2の地図カウンタが前回のプレイから引き継がれる** |
| 9 | 各ミニゲームの問題プール(`ShuffledPoolCursor`) | シャッフルされず、前回の続きから出題される |
| **10** ★ | **終了演出の状態**(「保存済み」フラグ / 破棄を遅らせているミニゲームの参照 / `PhaseElapsed`)。2026-09-15 追加 | **2回目のセッションで保存がスキップされる**、前回のミニゲームが残る |

> **8 と 9 は特に見落としやすい。** `SessionState` の中ではなく、
> **辞書やミニゲーム側に置かれているため、`SessionState = new()` だけでは消えない。**

**「もう一回」でも `StartSession()` を通る**(`10_Screen_GamePlay.md` §4.1)ので、
**このリセットが効いていないと、リプレイのたびに数値が壊れていく。**
**プレイテストの初期に必ず「2回続けて遊んで数値が正しいか」を確認すること。**

## 12. ★業務提示フェーズの演出(2026-09-15 新設)

### 12.1 目的とコア体験

**「次の仕事が来た!」を、音と画面の「パンチ」で体に叩き込む。**

ディレクターの狙いは **「YouTube Shorts で流行っている、テンポが速く刺激の強い編集」**(ズームのパンチイン・揺れ・フラッシュ・背景の切り替え)。
本作は「忙しさの快感」が訴求の主軸だが、レベル制とBGMテンポ変化の廃止で**「だんだん忙しくなる」演出手段がすべて失われている**(決定ログ 全体-3)。
**ミニゲームが切り替わる瞬間の「刺激」は、残された数少ない「忙しさ」の演出手段**であり、ここに投資する価値は高い。

> **設計の芯は「衝撃は最初の0.22秒に全部詰め、残りは文字を見せるグルーヴ、最後は文字が抜けた瞬間に問題が現れる」こと。**
> 刺激を1.5秒間ずっと続けると、①90秒で約9回繰り返されて疲れる ②光過敏性のリスクが上がる。

> **【2026-09-15 ディレクター決定】①業務提示は 1.5秒(1.4秒案は不採用)②業務提示中は背景で問題をずっと隠し、操作開始の瞬間まで見せない。**
> **これにより共通仕様 §3.3 の旧必須要件「業務提示中に問題が読める」は廃止した。**

> **★【2026-09-16 ディレクター決定】業務提示は「黒背景・白文字・ズームなどの動きなし」にする。白フラッシュも無効化する。**
> **本節と §12.2 の「パンチ」「高刺激」の設計は、仕組みとしては残っているが、現在の設定値では再生されない。**現在の見え方は §12.5.1。経緯は §12.1.1。

### 12.2 タイムライン(★1.5秒。秒は `[Prompt]` 開始からの経過時間)

> **★2026-09-16 注意: 以下の A〜C の表は「仕組み」と当初の値(2026-09-15)を示す。現在の設定値では拡大縮小・揺れ・ビートバンプ・フラッシュは0/1に固定されており、実際の見え方は次のとおり**(値の一覧は §12.5.1)。

### 12.8 ゲーム体験への影響

**(a) 90秒で遊べる本数が減る**

| プレイ | 旧(0.8秒) | **新(1.5秒)** | 差 |
|---|---|---|---|
| 毎回12秒使い切る | 6.84本 | **6.50本** | 完走6本は変わらない(7本目が中断) |
| 平均8秒で3件 | 9.84本 | **9.14本** | **約0.7本減** |
| 平均5秒で3件(上手い) | 14.6本 | **13.1本** | **約1.5本減**(上手い人ほど影響が大きい) |

- **1本あたり0.7秒、90秒で約6〜9秒ぶんの操作時間が業務提示に回る**(90秒の約7〜10%)。**業務提示が90秒に占める割合は 約9% → 約15%**(平均9.1本 × 1.5秒 = 13.7秒)。

- **サンタランクの到達しやすさが下がる。** 例: ノーミスで10本回せていたペースの人が約9本になり、スコアは 5,360 → 約4,760点(−11%)。
  **マスター 4,200 はまだ到達可能**だが、仮値の閾値はプレイテストで引き直す前提(共通仕様 §5.5)。
- **M5(常に約12秒使う)を引いたときの1本の長さは 13.85秒。**

**(b) T1 との関係 —— T1 は止めない(既定)**

| 案 | 内容 | 評価 |
|---|---|---|
| **A. T1は稼働(★既定)** | 業務提示の1.5秒もT1を消費する | **「90秒で遊べる」が厳密に守られる。**決定ログ 仕様-1 と一貫。操作時間は減る |
| B. 業務提示中はT1停止 | 1.5秒×約9本 = 約14秒ぶん実時間が延びる | **1プレイが約104秒になり、商品説明「90秒」が崩れる**(仕様-1で否決された案と同じ) |
| C. 延長分の0.7秒だけT1停止 | 0.8秒ぶんだけ消費 | 90秒のバーが業務提示の途中で止まって見え、**2本のバーの意味が分かりにくくなる** |

**(c) 残り時間の閾値との関係 —— ★推奨値 2.7秒**

- **`minRemainingTimeToStartNewMicroGame` > `promptDuration` である限り、`[Prompt]` 中に T1 が0になることは起きない**
  (開始時点で1.5秒より多く残っており、`[Intro]` とポーズでは T1 が止まるため)。
- **推奨値は 2.7秒**(= 業務提示1.5 + 最低操作1.2秒。旧2.0 = 0.8 + 1.2 と同じ意味を保つ)。**1.5 < 2.7 なので条件は必ず成り立つ。**
- **§3.5 の「`[Prompt]` 中の打ち切り」は安全網として実装は残す。**ディレクターが閾値を 1.5秒以下に下げた場合に限り発生しうる。

**(d) 刺激と疲労**

> **★2026-09-16: ディレクター決定でフラッシュ・揺れ・拡大縮小を値で止めたため、下の3点は「仕組みを再び有効にした場合」の注意として残す。**現在の業務提示に刺激の強い要素は無い(§12.5.1)。

- **フラッシュは1回の業務提示につき1回だけ**(0.12秒。**現在は `flashAlpha = 0` で0回**)。フラッシュとフラッシュの間は、どれだけ速く3件を終えても少なくとも1.85秒空く(業務提示1.5 + 判定演出0.35 + 操作時間)ので、**「毎秒3回を超える点滅」には構造上ならない。**
- 揺れは位置と回転だけで明滅を伴わない。**揺らすのは文字だけ**(現在は振幅0)。
- 90秒で約9回繰り返される。~~MVPはこの強さで暫定的に進め、プレイテストで観察する~~ **→ 2026-09-16 に演出を止めた。逆に「始まった感が弱い」「1.5秒が長い」と感じないかをプレイテストで見る**(§9-22)。

**(e) 初出カード後のカウントダウン廃止の効果**

- 初出時の「OK → 操作開始」は、カウントダウンを残した場合の **1.0 + 1.5 = 2.5秒 → 1.5秒** に短縮。初回プレイで最大4回 × 1.0秒 = **約4秒の待ち時間が消える**(カウントダウン中は T1 が止まっていたので、スコアへの影響は無い)。
