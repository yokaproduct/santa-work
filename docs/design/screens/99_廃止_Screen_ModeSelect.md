## 1. 画面の目的

> **【2026-09-07 ディレクター決定】`Screen_Title` は「ロゴとデザインだけ。機能は一切持たない」。
> したがってこの画面が実質的なホーム画面になる。**

**この画面が引き受けるもの**

| # | 役割 | 由来 |
|---|---|---|
| 1 | **モードの選択**(90秒モード / 12月に時間無制限) | もともとこの画面の役割 |
| 2 | **ハイスコアの表示** | **★`Screen_Title` から移管**(2026-09-07) |
| 3 | **最高ランクの表示** | **★同上**(§3.2) |
| 4 | **12月アップデートの告知** | **★同上** |
| 5 | 設定への導線 | もともとこの画面の役割 |
| 6 | **初回起動時の案内** | もともとこの画面の役割 |

**設計基準は3つ。**

1. **90秒モードのボタンが圧倒的に主役**であること(他の要素と大きさで差をつける)
2. **初回起動時は、そのボタンを押せばよいと一目で分かる**こと(§4.4)
3. **★役割が6つに増えたが、過密にしないこと**(§2.2 で検証)

> **⚠ この画面の追加で、起動からプレイ開始までのタップ数が 1 → 2 に増えた。**
> ただし**企画書 §1.1「『もう一回』が1タップで届く」は `Screen_Result` の責務**であり、
> そちらは**タイトルもこの画面も経由せず GamePlay へ直行**するため維持されている。
> 影響を受けるのは「アプリを起動して1回目を始めるとき」だけ(§8-1)。

### 1.1 遷移元 / 遷移先

| | 画面 | 条件 |
|---|---|---|
| 遷移元 | `Screen_Title` | タイトルをタップ(**アプリ起動時の唯一の経路**) |
| **遷移元** | **`Screen_Result`** | **「やめる」**(★2026-09-07 追加) |
| **遷移元** | **`Overlay_Pause`** | **「やめる」**(★同上。**セッション中断。スコアは記録しない**) |
| 遷移元 | `Screen_Settings` | 「もどる」 |
| **遷移先** | `Screen_GamePlay` | **「90びょう モード」**(カウントダウン 3.0秒) |
| 遷移先 | `Screen_Settings` | 「せってい」 |
| 遷移先 | `Screen_Title` | 「もどる」(**稀。意図的にロゴを見に来た場合だけ**) |

> **【2026-09-07 決定】`Screen_Result` と `Overlay_Pause` の「やめる」は、この画面へ戻る**

> **これによりプレイのループは「この画面 ⇄ GamePlay ⇄ Result」で完結し、`Screen_Title` を経由しない。**
> `Screen_Title` は**アプリ起動時に1回だけ通るアトラクト画面**になった。

**プレイのループ(2回目以降)**

**`ContentRoot` の高さ ≒ 1464 − 160(ヘッダ)= 1304px。**

**検証結果: 過密ではない。**

| 観点 | 判定 |
|---|---|
| 全要素の高さの合計 | 140 + 320 + 110 + 180 + 90 + 160 = **1000px**(全体1304pxの **77%**) |
| 余白の合計 | **304px**(23%)。要素間に20〜40px、下部に164 + 140px |
| **主役の優位性** | `PlayButton_Time90` は **320px** で、次に大きい `ComingSoonPanel`(180)の **1.8倍** ✓ |
| タップできる要素の数 | **2つだけ**(主役 + 設定)。**戻るを入れても3つ。**迷う余地がない ✓ |
| タップ領域 | 主役 900×320 / 設定 400×160 / 戻る 200×160。**いずれも160×160以上** ✓ |
| ボタン同士の間隔 | 主役の下端(530)と設定の上端(1004)まで **474px**。**誤タップの危険がない** ✓ |

### 3.2 ★記録表示(`Screen_Title` から移管)

| 条件 | `HighScoreValueText` | `BestRankValueText` |
|---|---|---|
| `santa.totalPlays == 0` | **「—」** | **「みならいサンタ」** |
| それ以外 | スコア(3桁区切り) | ランク名 |

> **「0」ではなく「—」にする理由**: 「0点だった」ように見えるのを避ける。
> `RecordPanel` 自体を非表示にする案は**採らない**(レイアウトが動くため)。

> **⚠ `santa.bestRankIndex` の使い道がここにしか無い。**

### 3.3 ★初回起動時は告知を出さない(新規)

**初回起動時、`FirstTimeHint`(初回案内)と `ComingSoonPanel`(12月告知)が同時に出ると、
初めて見る画面に「案内」と「まだ無い機能の予告」が並ぶ。**

> **`ComingSoonPanel` は `santa.firstLaunchDone == true` のときだけ表示する。**
> **初回プレイヤーに「まだ無い機能」を見せる必要はない。**まず1回遊ばせることに集中する。

**`CanvasGroup.alpha` で切り替えるので、レイアウトは動かない。**

### 3.1 ★時間無制限モードの枠を「グレーアウトしたボタン」にしない理由

ディレクターから「グレーアウトか非表示かを提案してほしい」との依頼があった。**プランナーの推奨は第3の案。**

| 案 | 内容 | 評価 |
|---|---|---|
| A. 非表示 | MVPでは何も置かない | **12月に画面へ要素を足すことになり、ディレクターの手調整が崩れる。**ガイドライン §7.2「広告バナー領域は後から足すと全画面のレイアウトが崩れる」と同じ失敗 |
| B. グレーアウトしたボタン | 押せないボタンを置く | **審査リスク。**App Store のガイドライン 2.1 / 4.2 では「機能しないUI」「未完成に見えるApp」が指摘対象になりうる。**押せるように見えて押せないものは、審査でもユーザーからも不評** |
| **C. 告知パネル(★推奨)** | **ボタンの形をしていない告知**。「12がつに とうじょう よてい」 | **レイアウト枠は先に確保でき、審査上も「機能しないボタン」にならない。**「まだ何かある」という期待も作れる |

> **推奨は C。** 12月に実装するときは、**この `ComingSoonPanel` を `PlayButton_Endless` に差し替える**
> (同じ位置・同じサイズ)。**ディレクターが調整した位置がそのまま使える。**

## 4. 処理内容

### 4.1 画面に入ったとき

```
1. SaveManager から highScore / bestRankIndex / totalPlays / firstLaunchDone を読む
2. RecordPanel に反映(totalPlays == 0 なら「—」/「みならいサンタ」。§3.2)
3. FirstTimeHint を alpha 0/1 で切替(firstLaunchDone == false なら表示)
4. ComingSoonPanel を alpha 0/1 で切替(firstLaunchDone == true なら表示。§3.3)
5. NewContentBadge は alpha 0(MVP)
6. BGM は bgm_title のまま(切り替えない)
7. AdDisplayPolicy に従いバナーを表示する(★この画面は表示する)
```

### 4.2 各要素を操作したとき

| 要素 | 操作 | 処理 |
|---|---|---|
| `PlayButton_Time90` | タップ | ① `se_button` ② **`santa.firstLaunchDone = true` を書き込む**(§4.3)③ `Screen_GamePlay` へ(`retry = false` → カウントダウン **3.0秒**)④ BGM を `bgm_gameplay` へ ⑤ バナーを非表示に |
| `SettingsButton` | タップ | ① `se_button` ② `Screen_Settings` へ |
| `BackButton` | タップ | ① `se_button` ② `Screen_Title` へ |
| `ComingSoonPanel` | タップ | **何も起きない**(`raycastTarget = false` なので、そもそもタップを受けない) |
| `RecordPanel` | タップ | **何も起きない**(表示専用。将来 `Screen_Records` を追加するならここを押せるようにする) |

### 4.3 ★`santa.firstLaunchDone` の意味が変わった

**`Screen_Tutorial` の廃止に伴い、このキーの意味を再定義する。**

| | 旧(Tutorial があった頃) | **新** |
|---|---|---|
| 意味 | チュートリアルを見た(またはスキップした) | **一度でもプレイを開始した** |
| 立てる場所 | `Screen_Tutorial` の完了 / スキップ | **`Screen_ModeSelect` の `PlayButton_Time90` を押したとき** |
| 使い道 | `Screen_Boot` からの自動遷移の判定 | **`FirstTimeHint` の表示判定** |

**キー名は変えない。** 変えるとマイグレーションが必要になるため(共通仕様 §10)。
**意味だけを変え、`SaveManager` のコメントに明記する。**

### 4.4 初回案内の演出

- `FirstTimeHint` を表示し、**`PlayButton_Time90` に軽い脈動演出**(スケール 1.0 ⇔ 1.03)を付ける。
- **点滅は毎秒2回まで**(光過敏性発作への配慮。共通仕様 §13-12)。
- **`RectTransform` を実行時に動かすことになるため、元の値を保存して必ず戻すこと**
  (共通仕様 §7.4 と同じ考え方)。**`localScale` の往復で表現するのが最も安全。**
- **押したら二度と出ない。** `firstLaunchDone` が立つため。

> **これがチュートリアル廃止後、唯一の「初回だけの案内」になる。**
> ここで伝えられるのは「**押す場所**」だけであり、**ゲームのルールは伝えられない**(§5 で扱う)。

## 6. 時間無制限モードへの設計余地(12月アップデート)

**10月末では実装しないが、以下を実装上の要件として明記する。**

### 6.1 実装上の必須要件

> **`GameSessionController` を「90秒固定」前提で作り込まないこと。**

```csharp
[CreateAssetMenu(menuName = "Santa/Game Mode Definition")]
public class GameModeDefinition : ScriptableObject
{
    [SerializeField] private string id;                 // "time90" / "endless"
    [SerializeField] private float  sessionDuration;    // 90.0 / ★0 なら無制限
    [SerializeField] private bool   recordHighScore;    // ハイスコアを記録するか
    [SerializeField] private bool   evaluateRank;       // サンタランクを出すか
    [SerializeField] private RankTable rankTable;       // モード別のランク表
    [SerializeField] private string titleTextKey;
    [SerializeField] private string descTextKey;
}
```

- **`GameSessionController.StartSession(GameModeDefinition mode, bool retry)`** という形にする。
- **セッション長は `mode.sessionDuration` から取る。**`GameBalanceSettings.sessionDuration` を直接読まない。
- **`Screen_Result` はモードを受け取り、`mode.evaluateRank` が false ならランク表示を出さない**ようにできること。
- **`MicroGameCatalog` / `MicroGameDefinition` はモードに依存しない**(同じ種目を両モードで使う)。

### 6.2 ★スコア設計が90秒を前提にしている(12月に必ず問題になる)

> **現在のスコア・コンボ倍率・サンタランクは、すべて「90秒で6〜14ミニゲーム」を前提に組まれている。**
> **時間が無制限だとスコアが無限に伸びるため、そのままでは成立しない。**

具体的には次が壊れる。

| 仕組み | 90秒モードでの前提 | 無制限モードだとどうなるか |
|---|---|---|
| **サンタランク閾値** | 理論最大 5,360点 に対し マスター 4,200 | **誰でも必ずマスターに到達する。**ランクが意味を失う |
| **コンボ倍率(10連〜=2.0)** | 理論最大 18〜42連 | **上限に張り付いたまま延々と続く。**倍率テーブルが機能しない |
| **ハイスコア** | 90秒での最高点 | **「長く遊んだ人が勝つ」だけの指標になる。**同じ棚に並べられない |
| **「速く解くこと自体が報酬」** | ミニゲーム数が増える | **時間が無限なら速さに意味がない。**本作のコア構造が消える |

**12月に決めるべきこと(未確定事項として残す)**

| # | 論点 | 選択肢の例 |
|---|---|---|
| E1 | **スコアを記録するか** | 記録しない(練習モード扱い)/ **別のハイスコアとして記録する** |
| E2 | **ハイスコアのキー設計** | `santa.highScore` は90秒モードのものとして残し、**12月に `santa.endless.*` を追加**(マイグレーション不要)/ 今からモード別キーにする |
| E3 | **サンタランクをどうするか** | 出さない / **時間あたりのスコア(1分あたり)で評価する** / 専用のランク表を作る |
| E4 | **終了条件は何か** | 手動終了のみ / **一定回数の誤答で終了**(= 本作で唯一の「失敗で終わる」モードになる)/ ミニゲーム数の上限 |
| E5 | **「誤答だけが失敗」を維持するか** | 無制限モードでは終了条件が必要なため、**誤答にペナルティを付ける可能性がある**。90秒モードと設計思想が分かれる |
| E6 | **結果画面を共用するか** | 共用 / 専用画面 |

> **プランナーの所見**: E4 と E5 が本質。**時間無制限モードは「終わり方」を持たないと成立しない。**
> 最も素直なのは「**誤答◯回で終了**」で、これは本作の「誤答だけが失敗」という設計思想と一貫する
> (90秒モードでは時間が終わりを決め、無制限モードでは誤答が終わりを決める)。
> **ただしこれは12月の企画として別途詰める必要がある。**
