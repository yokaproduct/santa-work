## 3. ゲームの基本構造

### 3-1. ミニゲームの構成

| # | 項目 | 決定 | 備考 |
|---|---|---|---|
| 構造-1 | **1ミニゲーム = 3問。3問正解でクリア** | | 1問ごとに種目が切り替わるのではなく、**同じルールを3回続けて処理してから次の種目へ移る**。※**M5だけ 3問×3ループ = 最大9問**(1問が個別には速く簡単なため。コンボの獲得上限は他種目と同じ3) |
| 構造-2 | **基準時間は全種目12秒に統一**(3問ぶん) | | 1問あたり約4秒だが**配分は自由**。1ミニゲームは ~~0.8+12+0.35 = 13.15秒~~ **★2026-09-15: 1.5+12+0.35 = 13.85秒**(§4-6) |
| 構造-3 | 1問の流れ | **業務提示0.8秒 → 12秒 → 判定演出0.35秒** → **★2026-09-15: 業務提示は1.5秒**(§4-6) | 一度「0.5秒の横スライドに置き換える」案が出たが撤回。横スライドはなし |
| 構造-4 | 誤答したとき | **次の問題へ進む。**3問正解するまで問題が供給される | 同じ問題はやり直さない |
| 構造-5 | **スコア** | **正解数だけをスコアにする** | 3問クリアできなくても正解したぶんは入る |
| 構造-6 | **コンボ** | **誤答したときだけリセット。時間切れは失敗としない(コンボ継続)** | **あくまで誤答だけが失敗** |
| 構造-7 | **難易度** | **レベル制を持たない。レベル選択の仕組みも作らない** | 問題ごとの当たり外れというランダム要素で緩急を作る。制限時間はプレイ中に短縮しない |
| 構造-8 | **出題順** | **連続で同じミニゲームが出ないようにし、あとはランダム** | 制約はこれ1つだけ。全種目を必ず1回出すといった保証はしない |
| 構造-9 | クリアボーナス | **付けない** | 3問揃えても追加点はなし。「クリア」は演出上の概念に留める |
| 構造-10 | **プロトタイプのスコープ** | **M1・M2は10レパートリー / M3・M5は6レパートリー** | **まずは動くこととバランス調整が優先。**M1・M2は手作りデータで**プールを使い切りうる**ため10に増やした。M3・M5はプロシージャル生成なので6パターンから無限に作れる |
| 構造-11 | 問題プールの枯渇時 | **先頭に戻って繰り返す** | M1・M2で1ミニゲーム内にプールを使い切った場合の安全網。10問あれば実際にはほぼ到達しない |
| 構造-12 | **M5のスコア換算** | **3問正解 = 1件100点** | コンボと同じ丸め方。M5も9問正解で300点になり**4種すべてが最大300点・最大3コンボで完全に揃う**。HUDの「しょり ◯けん」も同じ数え方 |
| 構造-13 | **M1の手紙の平均文字数** | **上限35文字は維持し、平均20〜23文字に抑える** | 35文字は「1問7.0秒」の枠で判断された分量。3問とも35文字だと21秒相当が必要で足りない。**「毎回35文字」にしないことが要点**。現在の3型カタログ(型A=12 / 型B=26 / 型C=30)は平均約23文字で、すでにこれを満たしている |

1プレイ90秒で **約6〜7ミニゲーム / 合計20問前後**。

### 3-2. この構造で自動的に解消した問題

1. **「1問7秒では読解ゲームとして厳しい」というM1の懸念** — 12秒をまとめて配分できるため、
   易しい問題で稼いだ余裕を難しい問題に回せる。加えて時間切れがコンボを切らないので、
   読み切れずに終わっても罰がない
2. **「M3の12秒×3回は90秒の44%を占める」という懸念** — 全種目が12秒に揃ったのでM3だけが突出しなくなった
3. **「M5では残時間ボーナスが構造的に発生しない」というプランナーの指摘** — 3問正解した時点で
   次のミニゲームへ移れるため、**速く解くこと自体が報酬になる**。別途ボーナスを用意する必要がない

### 3-3. 全種目に適用する設計原則

| # | 原則 | 内容 |
|---|---|---|
| 原則1 | **レベル制を持たない** | 難易度を段階制御しない。問題プールからランダムに引くだけ |
| 原則2 | **視線の着地点を不変にする** | 選択肢の位置・サイズ・数を問題ごとに変えない |
| 原則3 | **理不尽の線引き** | 「もう一度見れば分かる」は良い難しさ。「見ても一意に決まらない」は理不尽。ただし**「知らないものに出会う」ことは学びとして許容する** |
| 原則4 | **文字表記**(日本語版) | 教育漢字1026字まで + **全行分かち書き**。英語版は別途ルールが必要 |
| 原則5 | **説明がいらないほど単純なルールにする** | **種目ごとのチュートリアルを作らなくて済む水準を目指す。**説明が必要になった時点で、そのルールは複雑すぎると考える。判断に迷ったら**ルールを削るほうへ倒す** |

**原則5は素案に立ち返るもの**: 素案 §4 は「ゲーム開始直後にプレイヤーが**何をすればいいか分かる**こと。
複雑なルール説明を必要とするミニゲームは避ける」としていた。

**原則5に照らした現状の点検**:

| 種目 | 初見で分かるか | 説明が要りそうな点 |
|---|---|---|
| M2 住所 | **分かる** | ほぼなし。**4種で最も原則5を満たしている** |
| M1 手紙 | **分かる** | 型A・B・Cでルールは変わらない(常に「読んで4択から1つ」)ので、型が増えても説明は増えない |
| M5 ラッピング | おおむね分かる | **スキップ口の使い方**。「下の広い口へ入れる」という対応づけが初見で分かるかは要検証 |
| M3 重さ | **最も説明を要する** | ①合計を目標値**ちょうど**にする ②**複数選べる** ③**取り消せる** ④オーバーしても続けられる。積載メーターが①を視覚化するが、**②③は絵で伝わりにくい** |

**M3が原則5から最も遠い。** 4種で唯一「複数選択・取り消し可」を持ち、他3種(1タップで確定)と手触りが違う。
**複数選択はM3の中核**(合計を作る遊び)なので削れないため、**演出で伝えるのが現実的**。
打ち手の候補: 選んだ箱を持ち上げて「まだ確定していない」と見せる / メーターが目標値を超えたら赤くあふれさせ
「戻せる」と気づかせる / 初出カードに「もういちど おすと もどる」の1行だけ添える。

**ディレクターが示した基準の文面** — この分量が「ちょうどよい」:

```
きょうりゅうが 大好きです。
赤い きょうりゅうの
おもちゃが ほしい。
```

**型C「大量」の絶対条件**: 手紙にほしいものがたくさん書かれるが、**4択のうち該当するのは必ず1つだけ**。
2つ入れると正解が一意でなくなる。

**M1の未決**: 判定演出②の中身 / 英語版の設計 / 初期問題数と量産方法 / 在庫イラストの素材方式 /
1プレイでの出方。

### M2「住所でしわけろ」— 確認済み

| # | 論点 | 決定 | 備考 |
|---|---|---|---|
| M2-1 | **学習をどこで担保するか** | **ゲーム内で正解を教える必要はない。あとで自分で調べられる内容になっていればよい** | 「国名は調べれば分かるし、今の時代 画像検索もあるからどうとでも調べられる」。**プロジェクト全体に効く基準** |
| M2-2 | 誤答時の演出 | **押した地域が赤く沈むだけ。荷物は正解の地域へ飛ばさない** | プランナー案は不採用。M2-1により根拠が消えたため |
| M2-3 | 国名の表示 | **必ず表示する** | 調べる取っかかりを画面に残す。**「国旗のみ表示」は確定的に不採用** |
| M2-4 | **操作方式** | **世界地図の地域をタップする**。荷物は「毎回同じプレゼント包装のイラストに、国旗と国名のラベルが貼られている」形 | プランナーの「2列×3行のボックス」案を撤回 |
| M2-5 | 累積カウンタ | **地図の各地域に数値を累積する** | プレイ終了時、世界地図の上に業務の証跡が残る |
| M2-6 | 固定色 | **維持する**(詳細は追って整理) | 地域名テキストを併記し、色が識別できなくても解けるようにする |
| M2-7 | 掴み役としての設計 | **不要**。1問目をM2に固定する案は不採用 | 代わりにチュートリアルへ入れる候補とする |
| M2-8 | 大陸区分の典拠 | **日本の小学校社会科の6州区分。あそびかた画面への明記はしない** | 英語圏の標準は7大陸(6州+南極)だが**南極を出題しないため差が表面化しない**。**6州区分のままで英語版も問題ない** |
| M2-9 | 難易度 | **設計しない** | 「国の認知度は人によって違うので、それだけでばらつきは再現できている」 |
| M2-10 | **地図に描く線** | **国境線は描かない。州の区分線は描く。地図上に国名も入れない** | 州が当たっていれば正解というルール上、**区分線は必須要素**。国境線は係争地域の帰属を表明することになるため引かない |
| M2-11 | 地図の素材 | **タップしやすいように簡略化した世界地図をディレクターが用意する** | 「縦画面に世界地図をどう収めるか」は素材側で解決 |
| M2-12 | **タップの当たり判定** | **各地域の輪郭の内側だけがタップできる。輪郭の外は無反応**(不正解にしない) | 見た目と判定が完全に一致する |
| M2-13 | **除外国リスト** | **承認。C分類の国・地域は問題データから削除する** | 台湾・イスラエル/パレスチナ・ロシア・ウクライナ・北朝鮮・トルコ・エジプト・カザフスタン・キプロスほか |
| M2-14 | 初期の国数 | **プロトタイプでは10か国**(ただし6大陸それぞれから最低1か国ずつ入れる) | 全地域が最低1回は使われるようにする。※当初6か国としていたが、プール枯渇対策で10に増やした(構造-10) |
| M2-15 | **国旗素材** | **ディレクターが用意する。**プロトタイプ作成時は**画像枠だけ**を用意する | 外部リポジトリからの調達は行わない。素材の調達を待たずに実装を進められる |

**M2-12を無反応にする理由**: ①外した人は押し直すぶん時間を失うので自然なペナルティになる
②**反応がないこと自体から「輪郭の内側を押すものだ」と伝わり、次に同じミニゲームが来たときの学びになる**。
M2-1の「あとで自分で調べられればよい」という基準とも一貫している。

**州の区分線を引くときの注意**: 区分線が通る場所は6州区分の解釈が割れる場所と一致する
(ウラル山脈 / スエズ / パナマ地峡 / インドネシア周辺)。ただし**これらにまたがる国
(ロシア・トルコ・エジプト・カザフスタン等)はすべて出題から除外している**ため、
線の引き方が正誤に影響することはない。教科書の区分に沿って引けば足りる。

**地図素材に付く2条件(作成前に把握が必要)**:

1. **6地域をそれぞれ別の画像として書き出す。** 1枚のフラット画像では地域ごとの当たり判定・
   色の出し分け・カウンタ表示ができない
2. **小さい地域を実際の面積比より大きくデフォルメする。** 当たり判定が輪郭そのものになるため、
   **輪郭の大きさ = 押しやすさ**。**ヨーロッパとオセアニアが44×44ptを下回るおそれ**がある


**国旗を作るときの確認事項(ディレクター向けに引き継ぎ)**: 比率を原典どおりに保つ
(スイス1:1、ネパール非長方形などの例外あり。枠に合わせて引き伸ばさない)/ **国章ありの正式版を使う**
(メキシコ・スペイン等。簡略版は不正確または別国の旗になる)/ 配色は原典どおり /
影・光沢・はためきエフェクトを付けない / 国名表記は外務省表記に準拠。

### M4「プレゼントを数えろ」— **不採用**

**この種目は作らない。**

**理由**: プランナーの分析により、M4は**「難易度を健全に上げる軸」を構造的にほとんど持たない**ことが判明した。
企画書§5.4が挙げていた難易度手段はすべて理不尽側に落ちる:

- **複合条件**(「赤くてリボンがない」)は視覚探索を並列から直列に落とし、22個×0.25秒=**5.5秒が探索だけで消える**
- **重なり**は隠れた個体を原理的に数えられない
- **動き**は数えた個体を見失う
- **個数を増やす**のは情報量が増え、時間が線形に伸びる

加えて**計数速度は成人でほぼ生理的な定数**で練習しても速くならないため、上達を実感しにくい種目でもあった。

**他の種目へ引き継ぐこと**:

| 引き継ぐ内容 | 引き継ぎ先 |
|---|---|
| 包み紙の模様(水玉/ストライプ/星/無地/チェック) | **M5**。元々M4で色覚対策として導入しM5へ流用する計画だった。**M4がなくてもM5には必要**なのでM5側で用意する(素材+5点) |
| プレゼント箱のスプライト | **M5**。M4と共有する前提だったので**M5が単独で用意する** |
| **赤 × 緑を同時に使わない** | **全種目**。最も一般的な色覚特性(P型・D型)で識別できない。妨害色は 赤/青/黄/白/紫 で運用 |
| ジッター付きグリッド配置 | **12月の新種目**。複数オブジェクトを重なりなく散らす必要が出たときに使える |

**4種になったことの影響**:

- 90秒で約6〜7ミニゲームの枠に4種 → **各種目が1〜2回**出る計算。5種のときより収まりが良い
- **「毎回違う」感は薄れるリスク**がある。12月アップデートの種目追加で補う
- 「M1とM4を連続させない」という出題順の制約は**不要になった**
- アート素材が**約15点ぶん減る**(ただしM5が箱と模様を単独で持つため実質の削減はそれより小さい)
- 「数の認識・集計」という教育軸が**MVPから消える**。算数はM3(加算・組み合わせ)が担う

### M5「ラッピングしわけ」— 確認済み

| # | 論点 | 決定 | 備考 |
|---|---|---|---|
| M5-1 | **構成** | **1問 = 箱1個。3問 × 3ループ = 最大9問** | 12秒で9個なら**1個あたり約1.33秒**で、元の設計(1個約1秒)に近いペース。**先読みが成立する** |
| M5-2 | **コンボ** | **3問連続で当たったら1コンボ。最大9問正解で3コンボ** | 他3種は「3問正解=3コンボ」。**1ミニゲームあたり最大3コンボという上限が全種目で揃う** |
| M5-3 | **シュート** | **赤・青・黄の3択 + 下部に横長のスキップ口**(★2026-09-16: **赤・青・緑**に変更。§4-7) | たまに流れてくる**ゴミ**をスキップ口へ入れる |
| M5-4 | **カテゴリ** | **色 / 形の2種類。1ミニゲーム内では固定**(3問×3ループを通して同じカテゴリ) | 色の判別が速い人と形の判別が速い人がいるため、**どちらを引いたかがそのまま当たり外れになる**。レパートリーを増やすとばらつきも増える |
| M5-5 | 処理しきれなかった場合 | **コンボはリセットしない**(M3と同じ方針) | さばけたぶんのスコアは入る。**しきい値方式は不要になった** |
| M5-6 | **ゴミの個数** | **1ミニゲームに最低1個、最大3個** | 最低1個が保証されるのでスキップ口が毎回意味を持つ。最大3個は9問中の3分の1で、これ以上だと「仕分け」が「ゴミ探し」に変わる |
| M5-7 | プロトタイプのレパートリー | **6レパートリー** | 全種目共通の方針 |

**M5-1が「1問の定義」問題を解決した**: 「1問=箱1個で3問だけ」にすると12秒で3個になり、
ベルトがスカスカになって**M5の持ち味である先読みが失われる**ところだった。3ループにしたことで
元のペースが保たれている。

**M5-2でコンボの重みが釣り合った**: M5の1問は個別には速く簡単なので、3問まとめて1コンボにすることで
種目間の重みが揃う。プランナーが懸念していた「M5がコンボの処刑場になる」も、逆の「コンボ農場になる」も
**どちらも回避されている**。

**M5-3はプランナー案より優れている**: プランナーは「こわれた箱はどのシュートにも入れず素通しする」を
提案していたが、**「見逃したのか正解したのか分からない」**という問題があり補う演出が必要だった。
**スキップ口へ能動的に入れる方式なら、この問題が構造的に消える。**
「押さないでおく」という難しい抑制を要求しないのに、ゴミを見分ける判断は残る。

**M5-4を固定にした効果**: 9問を通して見本が変わらないため**先読みが最大限に働く**。
ループの境目で見本を読み直す必要がなく、切り替えを伝える演出も不要で実装も軽い。

**M5-5で「コンボの処刑場」問題が完全解消**: 取りこぼしは罰されず、間違えたときだけ罰される。

**M5の未決**: 操作方式(タップ統一かフリックを許すか)/ フィードバックの2層構成の承認 /
ベルトの流速と投入間隔(12秒で9個の配分)/ ゴミが何個混ざるか / 色と形の種類数。

## 4-2. ゲーム全体(画面・スコア・アート)

企画書 §3 / §7 / §8 を、確定事項に合わせて更新した。

| # | 論点 | 決定 | 備考 |
|---|---|---|---|
| 全体-1 | **スコア計算式** | **1問あたり = 基本点(100) × コンボ倍率**。最終スコア = Σ | **レベル係数を削除**(レベル制廃止)。**残時間ボーナスも削除** — 速さは「早く終われば次のミニゲームへ移れる」構造で既に報われており、二重に加点しない |
| 全体-2 | コンボ倍率 | 0〜2連=1.0 / 3〜5連=1.2 / 6〜9連=1.5 / 10連〜=2.0(仮値) | 1ミニゲームあたり最大3コンボ × 6〜7ミニゲーム = **理論上の最大は18〜21連**。テーブルとしては妥当 |
| 全体-3 | **BGMのテンポ** | **一定にする** | 企画書は「レベルに応じてテンポが上がる演出は忙しさの体感を最も安く高める手段。強く推奨」としていたが、**レベル制廃止で根拠が消えた** |
| 全体-4 | チュートリアルと初出カード | **両方残す** | チュートリアル = ゲーム全体のルール(90秒・3問クリア・コンボ・誤答だけが失敗)。初出カード = その種目のルールだけ。**守備範囲が違うので重複ではない** |
| 全体-5 | `Overlay_LevelUp` | **削除** | レベル制廃止。「テンポの区切り」の役割はミニゲームの切り替わり自体が担う |
| 全体-6 | 画面数 | **11画面**(うち`Screen_Records`は任意でMVP除外) | ミニゲームPrefabは4種 |
| 全体-7 | アセット点数 | 企画書187点 → **約177点** | M4削除(-8)と国旗減(-18)が、M1在庫増(+8)とM5増(+6)でほぼ相殺 |
| 全体-8 | 色覚多様性 | **色のみに依存する識別を全種目で禁止。赤 × 緑を同時に使わない** | 妨害色は 赤/青/黄/白/紫 で運用。**★2026-09-16: M5の色カテゴリ(赤・青・緑)だけ、模様の描き込みを必須条件として例外にした(§4-7)** |

**要対応 — サンタランクの閾値を引き直す必要がある**:

企画書の閾値(一人前1,200 / ベテラン2,200 / スーパー3,200 / マスター4,200)は
**レベル係数と残時間ボーナスが乗る前提の数字**だった。両方削除したため**現在の式では届かない**。

概算: 1プレイ約20問。全問正解でコンボが繋がり続けた場合の平均倍率を1.5とすると
**20 × 100 × 1.5 = 3,000点**が上限に近く、**マスター4,200は到達不可能**。
ScriptableObjectで後から調整できる形にしておき、仮値で進めるのが現実的。

**認識しておくべきこと — 「忙しさ」の演出手段がなくなった**:

レベル制廃止でゲーム内容が一定になり、BGMのテンポも一定にしたため、
**「だんだん忙しくなる」演出手段がすべてなくなった**。素案§14が目指す「めちゃくちゃ忙しいけど楽しい!」は
**ミニゲーム自体のテンポだけで作る**ことになる(90秒の短さ / 12秒で3問の密度 / 種目が次々切り替わること)。
プレイテストで「忙しさが足りない」となった場合の打ち手をあらかじめ考えておくとよい。

**未検討**: 読み物形式の「あそびかた」も別途必要か / チュートリアルの中身(何種目を扱うか・スキップ可否・
いつでも見返せるか)。

### M2 世界地図の組み込み(2026-09-10)

### 「赤 × 緑を並べない」ルールとの関係(M5-8)

全種目ルール(全体-8)は「P型・D型の色覚特性の人が**色だけで区別させられない**」ためのもの。
M5の色カテゴリは**模様(ハート / 丸 / 四角)だけでも正解できる**ので、ルールの目的は満たされる。**M5の色カテゴリに限り例外とする。**

- **例外の必須条件**: ①3色それぞれに決まった模様を**必ず**描き込む(透過版・本番の描き直しでも省かない)②白黒にしても表示サイズ(箱200px / 見本160px相当)で模様を見分けられる ③画像が無い間のプレースホルダ表示も模様を重ねる
- **模様をやめる場合は、この例外も無くなる**(色を赤・青・緑以外に戻す)。
- **M1など他の種目には広げない。**M1の「赤と緑を同一問題内で同時に使わない」は維持(M1の在庫アイコンには模様が無いため)。
- 詳細: `screens/23_MicroGame_Wrap.md` §5.2。

## 4-8. 文字の読みやすさ・設定画面の仮置き・全体音量(2026-09-16)

### 経緯

ディレクターから**「文字の色が背景と同化して読みにくいものが多い」**と指摘があった。
白地の仮画像(`hud_bg.png`・M3のそり統合画像)を置いたあとも、文字色が「暗い背景」前提のまま残っていたことが原因の一つ。
あわせて、**設定画面の仮置き**と**全体の音量の引き下げ**が指示された。実装は developer が並行して進めた。

**業務提示(ゲーム名表示)は同日中に方針が2回変わった。**
①最初の指示で「白背景」にし、取りまとめ役の判断で文字を黒にした → ②**ディレクター再指示で撤回し、「黒背景・白文字・ズームなどの動きなし」、白フラッシュも無効化**に決まった。
取りまとめ役が `PromptEffectSettings.asset` の値と `PromptText` の文字色で対応済み。**仕組み(コード・Prefab要素)は残し、値だけで演出を切っている。**

**当初の狙いとの差(経緯として残す)**: 業務提示は 2026-09-15 に、ディレクターの狙い「ショート動画風の、テンポが速く刺激の強い編集(いわゆるドパガキ系)」に沿って
パンチイン・揺れ・フラッシュ・ビートバンプを持つ1.5秒の演出として設計した(§4-6)。1.5秒という長さも `merry.wav`(1.42秒)の余韻まで入れる前提で、
**音のアクセントに画面の動きを合わせる設計**だった。今回の決定で画面の動きはほぼ無くなり(残るのは最後の0.18秒の文字フェードアウトだけ)、
**音と画面の同期は表示開始の瞬間だけ、「忙しさ」の演出は `merry.wav` と黒 → 問題画面の切り替えだけが担う**形になった。
**動かない文字を1.5秒見せることの「待ち感」はプレイテストで確認する**(`10_Screen_GamePlay.md` §12.1.1 / §9-22)。

## 4-13. 起動時フェードイン(2026-09-19)

### 経緯

- ディレクター指示(2026-09-19):「**ゲーム起動時に、フェードインからスタートする仕様にしてください。2秒くらいで設定してみて**」
- 2026-09-19 時点で `Screen_Boot` は未作成で、`InitialScreenBootstrap` が起動時に直接 `Screen_Title` を出している(§4-10)。
  **Unity Personal のためスプラッシュ(Unityロゴ)は消せず**、その直後にタイトルが出た瞬間から遊べる状態になっていた。

### ディレクター決定

| # | 論点 | 決定 |
|---|---|---|
| 起-1 | **起動時の入り方** | **フェードイン(黒 → 透明)からスタートする** |
| 起-2 | **長さ** | **2秒くらい**(= 既定 2.0秒。**調整前提の仮値**) |

### developer 対応(2026-09-19)

| 項目 | 内容 |
|---|---|
| 設定値 | **`GameBalanceSettings.BootFadeInSeconds` を新設**(既定 **2.0秒** / Inspector で調整可 / **`0` でフェードなし**)。※`GameBalanceSettings.asset` にはまだ値が書かれておらず、**コード側の既定値 2.0秒で動いている**(他の新設フィールドと同じ扱い)。Editor で一度開いて保存すれば明示的に書き込まれる |
| 置き場所 | **`Main.unity` の `UICanvas` 直下に常設オブジェクト `BootFadeLayer` を追加**(`ScreenLayer` / `OverlayLayer` と並ぶ)。**兄弟順は最後(最前面)**、全画面ストレッチ(`OverlayLayer` と同じ値) |
| 中身 | `CanvasGroup` + 黒の `Image`(**組み込みの白テクスチャのみ使用。実行時生成の Texture/Sprite は不使用**)+ 新規の `BootFadeController` |
| 触っていないもの | **画面Prefab と `ScreenFlowManager` は変更なし。**既存オーバーレイ(Pause / Countdown / MicroGameIntro)の優先順位ロジックにも触れていない |
| 画面遷移で再生されない理由 | `ScreenFlowManager` は `ScreenLayer` / `OverlayLayer` の子だけを生成・破棄するため、**`BootFadeLayer` は管理外の常設オブジェクトとして残る** |
| 動き | `Awake` で `alpha = 1` / `blocksRaycasts = true` → `Start` から **`Time.unscaledDeltaTime`** ベースのコルーチンで `alpha` を 1 → 0 → 完了時に `alpha = 0` / `blocksRaycasts = false` にしてから `SetActive(false)` |

### ★今後 `Screen_Boot` を実装するときの検討事項(確認事項として残す)

> **`Screen_Boot` を作ると「`Screen_Boot`(見せるものが無い画面)+ その上に黒のフェード」が重なる。**
> **この2つの関係を決めずに実装すると、下の見え方の事故が起きうる。**`01_Screen_Boot.md` §4.0 に詳細を記載した。

| # | 論点 | 何が起きうるか |
|---|---|---|
| 起-a | **どちらが先か** | フェードは `BootFadeController.Start()` で始まり、`Screen_Boot` の初期化と**同期していない**。初期化が 2.0秒より長引くと、**フェードが明け切った後に無地の `Screen_Boot` が見えたまま**になる |
| 起-b | **二重に暗くならないか** | `Screen_Boot` 側に独自の暗転・フェードを足すと**黒の上に黒**になり、体感の起動時間が伸びる |
| 起-c | **`LoadingIndicator` との関係** | 初期化が 1.0秒超で出す仕様(`01_Screen_Boot.md` §4.3)だが、**フェードが明けていないと黒に隠れて見えない** |
| 起-d | **UMP同意フォームとの関係** | 同意フォームは SDK 提供の**ネイティブUI**で `UICanvas` の外に出るため、**`BootFadeLayer` は被さらない**見込み(EU圏のみ。**要 developer 確認**) |

**プランナー推奨(未決)**: **フェードは「起動全体に掛かる1枚」として `BootFadeLayer` に一本化し、`Screen_Boot` 側には追加の暗転を持たせない。**
起-a はフェードの長さを初期化の想定時間より長めに取ることで吸収し、起-c は `LoadingIndicator` の表示条件を「フェード完了後に 1.0秒以上」と読み替えるのが素直。
